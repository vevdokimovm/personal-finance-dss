# FINPILOT — Вахтенный журнал (быстрый снимок «где мы сейчас»)

> # [!!!] ПРОТОКОЛ НЕПРЕРЫВНОСТИ — ЧИТАЙ ПЕРВЫМ, ЭТО ОБЯЗАТЕЛЬНО ДЛЯ КАЖДОГО КЛОДА
> **Не копи работу до конца батча. Собирай рабочий архив РАНО и ЧАСТО и отдавай через `present_files`.**
> Токены/контекст кончаются внезапно — если архив не скинут, работу нельзя ни закончить, ни передать
> на вахту, и всё встаёт на часы. Поэтому:
> 1. В начале крупной задачи — оценка объёма + **вероятность уложиться** (высокая/средняя/низкая).
> 2. Готовое отдавай ДО того, как браться за тяжёлый/творческий хвост.
> 3. По ходу переоценивай «успею/нет»; при росте риска — **немедленный чекпоинт-архив**.
> 4. WATCHLOG держи актуальным ПО ХОДУ (не в конце) — это точка передачи на другой аккаунт.
>
> **Полный протокол — `docs/session_continuity.md`. Нарушение = потеря работы и простой. Не пропускай.**

> **Что это и зачем.** Снимок-контекст для мгновенного входа в работу. Василий ведёт продукт на
> **4 аккаунтах Claude (V, J, M, S)** и в нескольких чатах внутри проекта; токены кончаются —
> вахту принимает другой аккаунт/чат. Этот журнал даёт принимающему быструю сводку: **где стоим,
> что сделано, что дальше, на какие грабли не наступать** — чтобы поднять картину с ОДНОГО архива,
> не читая 20k строк кода. (Метафора в тему бренда — штурман у штурвала.)
>
> **Принцип тонкости.** Журнал НЕ дублирует историю. Полная история версий — в `CHANGELOG.md`
> (каждый патч) и `docs/RELEASES.md` (эпохи). Направление и задачи — в `docs/ROADMAP.md`. Здесь
> только выжимка + ссылки.
>
> ## [!] ЖЁСТКОЕ ПРАВИЛО: §3 хранит РОВНО 10 последних версий, не больше
> §3 — это окно из **10 самых свежих версий, и только**. Добавляя новую версию сверху, СРАЗУ удаляй
> самую старую снизу, чтобы их всегда оставалось 10. Без этого журнал быстро разрастается и теряет
> смысл «быстрого снимка». Удалённое не пропадает — вся история живёт в `CHANGELOG.md` и
> `docs/RELEASES.md`. Это правило касается ИМЕННО этого файла: здесь старое именно УДАЛЯЕТСЯ.

> ## [!] Журнал ведётся НЕПРЕРЫВНО, по ходу работы
> Обновляется СРАЗУ по ходу (сделал подшаг → §0; нашёл грабли/факт → §4), а не «в конце сессии» —
> токены могут кончиться в середине батча. В любой момент журнал обязан отражать реальную текущую
> точку. **См. протокол непрерывности — `docs/session_continuity.md` (и баннер вверху файла).**

> **Как пользоваться (Василий).** Новому чату/аккаунту: этот файл (или его текст) + последний архив
> → «продолжай». Копия в чат — с версией в имени: `WATCHLOG finpilot_vX_Y_Z.md`. Архивная копия —
> `docs/WATCHLOG.md` без версии.

Костыль `obligation.replace(tzinfo=None)` оставлен намеренно — гасит aware-вход из Pydantic, это НЕ про
«сейчас». Полная tz-корректность (зона юзера → локальный календарь для дни-недели/внутримесячных
паттернов) — отдельный заход в слое паттернов, там же заведётся поле `tz` у User (сейчас его нет).
Вариант B (миграция timestamp-колонок на `timezone=True`) НЕ нужен для корректности приложения —
только для интеропа БД у вехи деплоя; шов готов (убрать `.replace(tzinfo=None)` в helper). Полное
обоснование развилки A/B (почему B — не требование корректности) — `docs/reports/adr/adr_002_datetime_storage.md`.

**JWT-ревокация (v4.26.0, раздел 4.4) — устройство и контракт.** Логика отзыва централизована в
`app/database/revocation.py`: точечный рубеж — блок-лист `is_token_revoked`/`revoke_token`/`purge_expired`;
массовый — предикат `tokens_invalidated_for(user, iat)` + `bump_tokens_valid_since`; конвертер
`epoch_to_naive_utc` нормализует JWT-таймстампы (int/float/aware-datetime) в naive-UTC. `dependencies`
и `routes_auth` таймстампы НЕ трогают — только зовут модуль (`revoke_token` принимает сырой `exp`).
Рубеж `tokens_valid_since` режется до секунды (iat — секундная гранулярность), сравнение строгий `<` —
немедленный re-login после logout-all проходит. Легаси-токены без `jti`/`iat` остаются валидными
(обратная совместимость, покрыто тестом).

**Инвалидация сессий при смене/сбросе пароля (v4.27.0, раздел 4.4) — устройство и дизайн-выбор.**
Подключена к тому же массовому рубежу `tokens_valid_since`. `change_password`: `bump_tokens_valid_since`
(валит другие устройства) + `_revoke_request_token` (точечно гасит текущий токен по `jti` — закрывает
sub-секундное окно округления рубежа: токен той же секунды иначе пережил бы строгий `<`) + чистка
auth-cookie + событие `password_changed`. `reset_password`: только `bump` (юзер не залогинен; текущего
токена/cookie нет; вход новым паролем проходит сразу — округление рубежа не задевает свежий токен).
Изменения ТОЛЬКО в `routes_auth.py`, миграций нет (механизм из 0027 переиспользован). **Дизайн-выбор
Option A — намеренный, НЕ переоткрывать:** для финпродукта (банковская планка) смена креденшелов валит
ВСЕ сессии, включая текущую — сильнее и ожидаемее «оставить текущую» (Google/GitHub). Option B
(сохранить текущую сессию) сознательно отклонён: требует ре-выпуска токена + нового cookie + чтобы
фронт подхватил новый токен, а фронт — отдельная веха (пока Jinja+vanilla JS). Инвалидация привязана к
УСПЕХУ смены (verify + update прошли); неверный текущий пароль → 400, рубеж не сдвинут. Карта линии для
слияния с другими вахтами — `docs/reports/merges/merge_manifest_v4_27_0.md`.

**Ротация ключа шифрования (v4.28.0, раздел 4.4) — устройство и эксплуатация.** `TokenCipher` под
капотом — `MultiFernet`. Ключи берутся из `settings.token_encryption_keys_list`: `TOKEN_ENCRYPTION_KEYS`
(через запятую, PRIMARY первым) → один `TOKEN_ENCRYPTION_KEY` → derive из `JWT_SECRET`. `encrypt` всегда
шифрует PRIMARY (первый ключ), `decrypt` перебирает весь набор, `rotate` перешифровывает токен primary.
Перешифровка существующих данных — `app/database/reencrypt.py::reencrypt_all`: колонки находятся
**интроспекцией** маппинга (`isinstance(col.type, EncryptedString)`), поэтому новое шифрованное поле
попадёт в перешифровку без правки модуля — не вести ручной список. Переписывает и старо-зашифрованные
(читаются прежним ключом набора), и legacy-незашифрованные (читаются как есть → шифруются primary).
**Эксплуатация ротации без простоя:** (1) сгенерировать ключ `Fernet.generate_key()`, поставить ПЕРВЫМ в
`TOKEN_ENCRYPTION_KEYS`, старый оставить вторым; (2) `python scripts/reencrypt_keys.py`; (3) убрать
старый ключ из набора. Миграций схемы нет — формат хранения тот же, меняется только ключ. `EncryptedString`
сохраняет обратную совместимость (decrypt вернул None → отдаёт значение как есть), так что включение
шифрования на ранее незашифрованных данных безопасно.

**Security-регрессии и старт-гард ключа (v4.29.0, раздел 4.4) — защитная сетка, не ослаблять.**
`tests/test_security_regressions.py` фиксирует инварианты харденинга: (1) security-заголовки на ЛЮБОМ
типе ответа — работает потому, что `SecurityHeadersMiddleware` зарегистрирован ВНЕШНЕ `CSRFMiddleware`
(порядок `add_middleware` в `main.py`: Rate→CSRF→SecurityHeaders→Logging; внешний обрабатывает response
последним), поэтому даже 403 от CSRF проходит через установку заголовков. Не менять порядок middleware
вслепую — заголовки на ошибках/отказах слетят. (2) CSRF-блок на всех изменяющих методах, с исключениями
Bearer/api-key/без-Origin (срабатывает по методу ДО роутинга — тестируется на любом пути). (3) **Старт-гард
ужесточён:** в production обязателен явный `TOKEN_ENCRYPTION_KEY` или `TOKEN_ENCRYPTION_KEYS` — без него
ключ шифрования деривится из `JWT_SECRET`, что лишает смысла ротацию (v4.28.0) и разделение ключей. Это
**намеренное требование деплоя** (`.env.example` обновлён) — не откатывать ради удобства локального прода.

**MFA/TOTP (v4.30.0, раздел 4.4) — устройство и инварианты.** Второй фактор на `pyotp`. Состояние на
User: `mfa_secret` (зашифрован `EncryptedString`) + `mfa_enabled`; пока `mfa_secret` задан, а
`mfa_enabled=False` — это «pending» (enroll сделан, confirm нет). Крипто — `services/mfa.py`, доступ к
данным — `database/mfa_store.py` (разделение как у revocation). **Ключевой инвариант — двухступенчатый
логин:** при `mfa_enabled` `/auth/login` после верного пароля НЕ ставит cookie и НЕ выдаёт сессионный
токен — возвращает `mfa_pending`-токен (purpose-claim, TTL 5 мин); полную сессию выдаёт только
`/auth/mfa/verify` после TOTP/recovery-кода. **Не выдавать сессию в login при включённом MFA** — это
вся суть фичи. Recovery-коды: 10 шт, bcrypt-хеш, одноразовы (`used_at`), показываются один раз при
confirm; и verify, и disable принимают TOTP ИЛИ recovery-код. **Связанный инвариант (purpose-guard):**
`get_current_user` отвергает ЛЮБОЙ токен с claim `purpose` — полная сессия его не имеет. Это держит
mfa_pending (и заодно email_verify/password_reset/telegram_link) вне сессионного доступа; не ослаблять
эту проверку, иначе промежуточный/одноразовый токен станет полноценным входом.

## §5. Жёсткие правила (чек-лист «не дрейфовать»)

1. **TDD** — тест → красный → реализация → зелёный, реально прогонять.
2. **`app/core/` не трогать** без согласования (исключение — `spending_advice.py`).
3. **Схемные изменения — на PostgreSQL** (SQLite молчит про FK).
4. **SemVer внутри вехи:** фича=MINOR, фикс=PATCH. Bump `APP_VERSION` + `CHANGELOG.md` каждый батч.
   Вехи (v4-v9) — крупные этапы, не классический SemVer (см. §2).
5. **Без массового реформата** кроме координированных окон (сейчас окно открыто — техдолг закрываем).
6. **ROADMAP — источник приоритетов, строго по порядку.** Не изобретать параллельную нумерацию.
7. **Без эмодзи.** Русская проза + английский код. По-братски, прямо, без канцелярита.
8. **НЕ объявляй невозможным, не проверив.** PostgreSQL/chromium/apt поднимаются здесь. Реально
   внешнее (cbr.ru 403, живой SMTP, деплой) — честно отметить.
9. **Перед «с нуля» — проверь, не сделано ли уже** (бэк часто опережает план).
10. **Вывод тестов — через `--junitxml`** (не `tail` по логу): итоговая строка не флашится надёжно.
    Парсить XML + exit code. (§4, `docs/pitfalls.md`.) **Что гонять и когда (узкий цикл vs полный) —
    `docs/test_run_optimization.md`; механика полного fast — `docs/sandbox_runbook.md` §7.**
11. **НИКОГДА не писать имена в гите / релизах / публичных артефактах** — официально безымянно.
12. **Тестирование мат-модели — СТРОГО вне проекта** (Opus 4.8, без памяти/инструкций → не biased).
13. **E2E добавляются с unit** для изменений фронта/API; CRUD-флоу обязаны иметь E2E.
14. **Разборы — АВТОМАТИЧЕСКИ по триггеру:** дефект в коде → инцидент (`docs/reports/incidents_summary.md`);
    искали, но дефекта нет → расследование (`docs/reports/investigations_summary.md`); повторная ошибка
    воркфлоу → pitfall (`docs/pitfalls.md`); найденный баг → карточка по `docs/reports/bug_report_template.md`.
15. **Слияние разошедшихся линий → консолидация, не переписывание истории.** Полная процедура,
    гейты и антипаттерны — **`docs/reports/merges/merge_and_fork_guide.md`**. Профилактика: синкать аккаунты чаще,
    координировать номера версий (версия закреплена за задачей, не за аккаунтом).
16. **Чекпоинт-дисциплина (непрерывность).** Не копить работу до конца батча: как только есть
    рабочее состояние — собрать архив + WATCHLOG и отдать через `present_files`. В начале крупной
    задачи — оценка объёма и **вероятность уложиться**; по ходу — переоценка, при росте риска
    немедленный чекпоинт. Готовое отдавать прежде тяжёлого хвоста. Протокол — `docs/session_continuity.md`.
17. **Отчёты — по единому диспетчеру** `docs/reports/reporting_policy.md` (триггер → тип → шаблон →
    папка → реестр). Конвенция имён всего — `docs/naming_convention.md`.
