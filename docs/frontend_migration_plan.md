## 1. Ключевые архитектурные решения

### 1.1. Стратегия миграции (*)

- **(A) Greenfield-to-parity** — собираем весь React-SPA в новом дереве репозитория; существующий
  Jinja-фронт работает параллельно всю дорогу; переключаемся на паритете. Чисто, без dual-stack
  костылей; учит React правильно (портфолио-фактор). Минус: «новое» не шипается до достижения паритета.
- **(B) Strangler-fig** — React монтируется рядом с Jinja, мигрируем экран за экраном, оба клиента
  живы. Всегда шипабельно, но dual-routing + общая auth-cookie на два стека + две сборки разом —
  лишний налог для соло-разработчика; inline-хаос и Jinja живут дольше.
- **(C) Big-bang** — стоп Jinja, переписать всё разом, cut-over. Быстрый чистый финал, если ничего
  не сломается; худший риск под дедлайн, длинный «тёмный» период. Не рекомендуется.

**→ Рекомендация: (A) greenfield-to-parity.** Ключевой довод: бэк уже чистый REST API, поэтому SPA —
отдельный клиент, и dual-stack (B) не даёт выигрыша, только сложность. Старый Jinja при этом **не
гасим** — он работает всю миграцию (оба клиента бьют в один API), а cut-over сводится к переключению
корневого `location` в nginx на собранную статику SPA — низкий риск, не «страшный релиз».

### 1.2. Типы API из OpenAPI-снапшота

Самый сильный и при этом бесплатный ход. В репо уже есть снапшот `docs/api/openapi.json` (**106 путей**,
генератор `tools/api_snapshot/dump_openapi.py`). Через `openapi-typescript` + `openapi-fetch` получаем
**полностью типизированный API-клиент, автовыведенный из контракта бэка**. Бэк поменялся → регенерируем
типы → TS-компилятор ловит рассинхрон до прода. Это фронт-аналог типобезопасности Decimal/Pydantic на
бэке. Снапшот из вехи 5 напрямую кормит веху 8 — связываем этапы, а не изобретаем DTO вручную.

### 1.3. Авторизация в SPA (*)

- **(A) Оставить cookie-based** (HttpOnly auth-cookie, как сейчас на бэке). HttpOnly устойчив к краже
  токена через XSS; бэк уже так делает. **Рекомендация.**
- (B) Токен в памяти — гибче для мобильного/сторонних клиентов, но уязвим к XSS-краже и требует
  переделки бэка. Не нужно (мобильного клиента в роадмапе нет).

Выбор (A) важен ещё и потому, что **именно здесь закрываются отложенные бэк-галки** `CSRF double-submit`
+ `SameSite=Strict`: React-клиент умеет читать и эхать CSRF-токен (чего не мог vanilla JS). См. §5.

### 1.4. Клиентское состояние

TanStack Query держит **серверное** состояние (запросы/кэш/синхронизация). Для UI-состояния — **старт на
React Context + local state**; Zustand добавляем **только** если появится сложное кросс-компонентное
клиентское состояние (YAGNI). Финансовый дашборд почти весь server-driven — Redux/Zustand с первого дня
был бы оверинжиниринг.

### 1.5. Хостинг и раздача (*)

Dev — Vite dev-server, проксирует `/api` на FastAPI (127.0.0.1:8000). Prod — собранная статика SPA
(`dist/`) раздаётся nginx; `/api` идёт на FastAPI (артефакты nginx уже готовы, веха 9). Cut-over =
переключить корневой `location` в nginx с Jinja-рендера на `dist/`. Раздача статики — cache-busting
уже принят в проекте (`?v={{ app_version }}`, для SPA — hashed-имена из Vite).

## 2. Фазы вехи 8

Порядок — по зависимости и ценности; детализируется при входе.

1. **Фаза 0 — фундамент.** Скаффолд Vite + React + TS в репо (дерево — решение §1.1); тулчейн
   (Vitest, Playwright-chromium, ESLint + Prettier — свой формат **с первого коммита**, поэтому правило
   «без массового реформата» тут не кусает); порт токенов из `ui_ux_design_standard.md` в CSS-переменные +
   подключение shadcn/ui; TanStack Query client; **генерация типов из `openapi.json`** (§1.2); фронт-джоб
   в fast-тир CI (typecheck + Vitest). Здесь же фиксируются открытые решения §1.
2. **Фаза 1 — визуальный поиск (Claude Design).** Скармливаем текущий Jinja-репо → Design вытащит
   существующий бренд/лого/токены из `frontend/static`; гоняем 2–3 направления редизайна на канвасе
   (dashboard + planning как якорные экраны); вход — `ui_visual_design_brief.md`; лочим направление →
   handoff-bundle в Claude Code.

   > **[!] ОБНОВЛЕНО 2026-07-31 (v7.8.0).** Пункт выше описывал передачу в Claude Code как
   > одностороннюю (handoff-bundle). С обновления Claude Design 17.06.2026 связь **двусторонняя**:
   > команда `/design-sync` в Claude Code тянет дизайн-систему из локальной кодовой базы в Design
   > (и обратно), а `/design` позволяет работать с проектами Design прямо из терминала. Требуется
   > Claude Code не ниже v2.1.181. Практическое следствие: 68 CSS-переменных из
   > `frontend/static/css/styles.css` не пересказываются словами, а импортируются — Design строит
   > на наших компонентах и сверяет вывод с нашей системой. Порядок шагов фазы 1 — в
   > `docs/frontend_milestone8_plan.md`, этап Э1.
3. **Фаза 2 — ядро экранов (по одному, TDD).** Порядок: сначала auth-флоу (login/register/reset —
   фундамент), затем dashboard, затем денежное ядро (transactions → obligations → goals → planning).
   Каждый экран = компонент + Vitest + Playwright E2E. **CRUD-флоу обязаны иметь E2E** (§5 #13 WATCHLOG).
   KaTeX — формулы с нижними индексами; Recharts — донат распределения плана / прогноз / спарклайны.
4. **Фаза 3 — вынос API-only возможностей (ГЛАВНАЯ ЦЕЛЬ вехи).** Колокольчик in-app уведомлений,
   household-оверлей, A/B, referral, UI энролла MFA (QR + recovery-коды), plan_tier/подписка, слои
   spending-advice, мастер импорта (мультибанк CSV/XLSX/PDF + подсказки «как найти выписку» прямо в UI),
   Telegram-привязка. Здесь закрывается разрыв «бэк опережает фронт».
5. **Фаза 4 — полировка + отложенные security-галки.** Тёмная тема (отдельная палитра, не инверсия),
   motion 150–250мс + `prefers-reduced-motion`, интерактивный онбординг, объяснялки «логика дохода» и
   «цели vs активы», красивые системные сообщения/виджеты, апгрейд UI прогнозирования, PDF-отчёт со
   страницы прогноза. **Тут закрываются** `CSP без 'unsafe-inline'` и `CSRF + SameSite` — см. §5.
6. **Фаза 5 — cut-over + приёмка.** Паритет достигнут → nginx переключается на SPA, Jinja в архив;
   приёмка по критерию «выглядит дорого» (`ui_visual_design_brief.md` §7), WCAG AA, все E2E зелёные,
   mobile ≥44px.

## 3. Рабочий метод — какая поверхность Claude под что

Связка, не «или-или»: канон живёт в Проекте, картинка рождается в Design, код собирает Claude Code,
handoff их сшивает. Первоисточник по экосистеме — `knowledge/guides/claude_infrastructure_methodology.md`
§12–13.

| Поверхность | Под какие фазы | Роль |
|---|---|---|
| **Проект** (где сидим) | все | Дом канона: ADR, доки, WATCHLOG, решения. Планирование фронта логируется тут |
| **Claude Design** | фаза 1 (+ точечно любой экран) | Визуальный поиск на канвасе → handoff-bundle. Читает кодбазу → строит дизайн-систему. Даёт фронт-код (HTML/CSS/JS), **не** бэк/БД/авторизацию |
| **Claude Code** | фазы 0, 2, 3, 4, 5 | **Реальная сборка в репо**: TDD, субагенты (planner/code-reviewer/tester/security-audit, §13), хуки = CI у правок. Тут ~90% вехи |
| **Cowork** | опционально | Не-кодовый мультифайл: контент онбординга, реструктуризация UI-доков |

Примечание: **Pencil** (pencil.dev) — сторонний инструмент, не продукт Anthropic; Figma-подобный канвас
в IDE поверх локального Claude Code CLI. Нативный аналог от Anthropic — Claude Design. Оба сходятся в одну
точку: финальный код всё равно строит Claude Code в репозитории.

## 4. Дисциплина (наследуется от проекта, не меняется)

1. **TDD обязателен** — Vitest (компоненты) + Playwright (E2E), CRUD-флоу обязаны иметь E2E.
2. **Merge-safety** — фронт это новое дерево, конфликт с бэком низкий; версии координируем (веха 8 = `v8.x.x`),
   массовых правок, ломающих диф, нет (§5 #7 WATCHLOG).
3. **Формат фронта** (Prettier/ESLint) ставим с первого коммита → ретро-реформата не будет (аналог правила
   «без `black .`» на бэке — тут решается настройкой формата на старте).
4. **SemVer** — фича = minor, фикс = patch; бамп `APP_VERSION` + `CHANGELOG.md` каждый батч.
5. **WATCHLOG** — в двух копиях (внутри архива + отдельным `.md` через `present_files`), чекпоинт-архивы рано.
6. **Гейты** — фронт-джоб в fast-тир (typecheck + Vitest); полный E2E + визуальная регрессия — full-тир (на Mac/CI).

## 5. Отложенные бэк-галки, которые закрываются именно здесь

Раздел кибербеза §4.4 в ROADMAP закрыт по бэк-коду (MFA — v4.30.0). Две галки **сознательно отложены до
вехи 8**, потому что физически требуют React-клиента:

| Галка | Почему ждала фронта | Где в плане |
|---|---|---|
| `CSP без 'unsafe-inline'` | Сейчас `script-src 'self' 'unsafe-inline'` из-за inline-JS в Jinja; inline уедет в React → чистый CSP (или nonce) | Фаза 4 |
| `CSRF double-submit + SameSite=Strict` | Double-submit требует клиента, который читает и эхает токен; vanilla этого не мог (`SameSite=lax` + Origin-проверка уже стоят) | Фаза 4, решение §1.3 |

Это не забытый хвост, а «заблокировано по дизайну» — веха 8 их разблокирует.
