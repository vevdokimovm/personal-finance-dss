# Телеметрия принятия совета: что писать и зачем

**Тип:** требование к продукту · **Заведено:** 2026-07-29 (v6.25.0) ·
**Обязательно ДО запуска** (волна 0, п. 0.6 плана добивки модели).

> Зачем. Раунд сертификации на живых данных (волна 2) меняет природу эталона:
> вместо консенсуса четырёх экспертов истиной становится **фактическое решение
> пользователя**. Без телеметрии у такого раунда будет вход, но не эталон — и его
> придётся отложить ещё на полгода, пока данные накопятся. Стоимость сейчас —
> один батч; стоимость упущения — полгода.

## Событие

На каждый показанный план:

| Поле | Смысл |
|---|---|
| `plan_id`, `user_id` | связь с планом и пользователем (обезличивается на выгрузке) |
| `model_version`, `app_version` | против какой версии модели сравнивать |
| `input_snapshot_hash` | хеш входа: доход, расходы, обязательства, цели, подушка, риск-профиль |
| `advice` | что советовала модель: сплит по трём бакетам + разовые ходы |
| `outcome` | `accepted` · `modified` · `ignored` |
| `modified_to` | если `modified` — во что человек изменил сплит |
| `shown_at`, `decided_at` | момент показа и момент решения |

## Что это даёт замерам

1. **Эталон вместо консенсуса.** `modified_to` против `advice` — прямое
   расхождение модели с практикой живого человека, без чистых сессий экспертов.
2. **Ось достоверности выше нынешнего потолка.** Коридор экспертов ограничивает
   ось 1 значением ~88; внешняя истина снимает это ограничение.
3. **Веса SAW из данных** (H6-1): распределение `modified_to` по риск-профилям —
   это и есть эмпирические предпочтения, которых сейчас нет.

## Правовая рамка — обязательна до сбора

Финансовый портрет — персональные данные по 152-ФЗ. Использование
пользовательских данных в тестировании требует основания и обезличивания,
описанных **до** начала сбора: достроить контур на уже собранных данных нельзя.
Требования — `docs/legal/README.md`, вопросы юристу — п. 2.1 плана добивки.

## Чего НЕ собирать

Продуктовые метрики активности (DAU, время на экране, глубина скролла) для
сертификации бесполезны: эталоном служит **решение** пользователя, а не его
поведение в интерфейсе. Смешивать их в одну таблицу — верный способ получить
свалку, из которой потом ничего не извлечь.
