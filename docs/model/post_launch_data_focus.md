# Что собирать о пользователях после запуска — по каждому незакрытому пункту

**Заведено:** 2026-08-13. **Зачем документ:** механизм сбора уже построен (телеметрия
принятия совета, волна 0 п. 0.6, `docs/model/telemetry_spec.md`, код дормантен до правового
контура 152-ФЗ) — но «собирать всё подряд» не отвечает ни на один конкретный вопрос. Этот
файл разбирает по каждому незакрытому пункту сертификации: что именно нужно, зачем, сколько
считать достаточным, и когда пункт можно закрывать.

## 0. Инфраструктура (уже готова, не нужно ничего строить заново)

- **Событие принятия совета** (`plan_advice_events`, миграция 0032) — на каждый показанный
  план: `advice` (что советовала модель), `outcome` (`accepted`/`modified`/`ignored`),
  `modified_to` (во что человек изменил), `model_version`, хеш входа. Это ЕДИНСТВЕННЫЙ
  источник для всех пунктов ниже — включать `TELEMETRY_COLLECTION_ENABLED` нужно один раз,
  дальше данные копятся сами.
- **Снимок модели** (`knowledge/model_validation/model_snapshot_v*.md`, п. 0.7) — фиксирует,
  какая версия канона/констант дала эти советы. Перевыпустить командой из
  `tools/model_validation/model_snapshot.py` на коммите фактического запуска в проде (текущие
  снимки — baseline, не финал).
- **Правовой контур обезличивания (152-ФЗ)** — ROADMAP §8.2а, задача юриста. Без него ничего
  из телеметрии нельзя использовать в анализе ниже, только хранить. **Это первый шаг, не
  последний** — заказать у юриста ДО того, как накопится достаточный объём для остального.

## 1. По каждому пункту

### H6-1 — веса SAW вырождаются на «экстремальных» осях (Волна 2, п. 2.3)

**Гипотеза:** слой B (портреты с двумя из трёх осей вырожденными — например, тонкая подушка +
нет целей) стабильно хуже трёх раундов подряд, потому что SAW-свёртка теряет различающую
силу, когда почти весь вес приходится на одну ось.

**Что собирать:** `modified_to` конкретно на портретах, где `Lt ∈ [1; 2)` (полоса тонкой
подушки — та же граница, что уже используется в модели) И либо целей нет, либо они уже
насыщены. Нужна именно ЭТА подвыборка, не общий поток событий.

**Сколько достаточно:** по прецеденту раунда 5 (309 метаморфических пар хватило для выводов
по устойчивости) — ориентир **300–500 событий именно в этой полосе**, не 300–500 вообще (при
типичной доле полосы ~5-10% от всех портретов это означает 3 000–10 000 показанных планов
суммарно).

**Как закрывается:** контрфакт — нормировка весов по числу «живых» (не вырожденных) осей,
сравнение с фактическим `modified_to` в этой подвыборке. Батч-оценка — 3 (уже в плане, §6
`model_completion_plan.md` п. 2.3).

### H6-2 — расхождение на «флоу-кромке» (Раунд 6, мини)

**Гипотеза:** решение модели дискретно (переключается резко) на портретах с потоком, близким
к нулю (`Rt` около границы допустимости), а реальные пользователи в этой зоне действуют
плавнее/иначе, чем модель предполагает.

**Что собирать:** `modified_to` на портретах с `|Rt| < 5% от дохода` (узкая полоса вокруг
нуля). Малый ожидаемый объём подвыборки — эта полоса реже полосы H6-1.

**Сколько достаточно:** мини-раунд формата (см. Волна 1, п. 1.1/1.2) — здесь событий может не
накопиться быстро; если через 3–6 месяцев после включения телеметрии подвыборка < 50 записей,
пункт стоит держать открытым дольше, не форсировать вывод на малой выборке.

**Как закрывается:** сравнение направления `modified_to` (в долг / в резерв / в цели) с тем,
что предсказывает модель на границе `Rt≈0`.

### H6-3 — порог токсичности долга (Волна 1, п. 1.1 — НЕ требует пользовательских данных)

**Что нужно НА САМОМ ДЕЛЕ:** один чистый эксперт, один узкий вопрос («при какой ставке долг
считать токсичным для целей снижения floor резерва»). Пользовательские данные здесь
опциональны, не блокер — это единственный пункт из H6, который можно закрыть БЕЗ ожидания
телеметрии, просто мини-раундом эксперта. Если данные всё же появятся раньше — полезно свериться,
но не ждать их специально.

### Волна 1, п. 1.2 — кромка ПСК (В1, юридический раскол)

Не про пользовательские данные — нужен третий голос с юридической квалификацией (раскол
экспертов 2/2 по вопросу, валидна ли ставка 300% против законного потолка 292%). Тот же
класс блокера, что тип Б ИИС-3 (ADR-017) — юрист/бухгалтер, не телеметрия.

### Волна 1, п. 1.3 — объяснительный раунд (объяснимость, ось 9)

Уже готово к раздаче (см. WATCHLOG v8.13.4): `docs/model/explainability_protocol.md` +
`docs/reports/testing/explainability_review_material_blind.md`. Не требует пользовательских
данных вообще — нужна отдельная чистая сессия/аккаунт для проведения (эта сессия не может —
полная память проекта). Актуально уточнить у владельца отдельно, не относится к сбору данных
после деплоя.

### Волна 2, п. 2.2/2.4 — раунды на живых данных (первый и второй)

**Что собирать:** весь поток `plan_advice_events`, без фильтра по полосам — это единственный
пункт, где нужен ОБЪЁМ, а не прицельная подвыборка. `outcome`/`modified_to` против `advice`
модели — это и есть новый эталон (замена консенсуса 4 экспертов).

**Сколько достаточно:** ориентир по прецеденту синтетических раундов — 12 000 сопоставлений
модель/эталон на прошлых раундах; на живых данных объём определяется реальным трафиком
продукта, не аналогичен синтетике. Практический порог — начинать анализ, когда набралось
**на порядок больше записей, чем уникальных сочетаний risk_profile × наличие кризиса ×
наличие целей** (грубо, чтобы на каждую комбинацию было что усреднять, не единичные случаи).

**Второй раунд (2.4)** — через полгода после первого, проверка устойчивости во времени (не
дрейфнули ли выводы) — тот же поток данных, второй срез.

## 2. Качественный сбор (не телеметрия — параллельно, из `model_completion_plan.md` §4а)

Уже задокументировано, не дублирую содержательно — только напоминание, что это ОТДЕЛЬНЫЙ от
телеметрии канал и не покрывается автоматическим событием:

- Дословные вопросы пользователей «почему так» → `docs/reports/ux/explainability_questions.md`.
- Случаи, где пользователь сделал не то, что советовала модель, **с его формулировкой почему**
  (не только факт `modified` — качественная причина, которую телеметрия не спрашивает).
- Портреты, где модель дала неожиданный совет → `docs/model/expert_certification/
  candidate_cases.md`.

## 3. Что НЕ собирать (уже зафиксировано в telemetry_spec.md, повторено явно)

Продуктовые метрики активности (DAU, время на экране, глубина скролла) — бесполезны для
сертификации, эталон здесь решение пользователя, не поведение в интерфейсе. Смешивать в одну
таблицу с событием принятия совета — верный способ получить свалку.
