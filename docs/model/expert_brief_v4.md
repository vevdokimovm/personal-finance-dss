## 1. Схема портрета

| Поле | Смысл |
|---|---|
| `id` | Идентификатор (`SP4-00000` … `SP4-11999`) — вернуть в ответе как есть |
| `income_total` | Суммарный доход, ₽/мес |
| `expense_total` | Расходы на жизнь БЕЗ платежей по кредитам, ₽/мес |
| `obligations[]` | Кредиты: `name` (тип продукта), `amount` (остаток тела, ₽), `interest_rate` (годовая ставка, доля), `monthly_payment` (₽/мес) |
| `goals[]` | Цели: `name`, `target_amount` (₽), `current_amount` (накоплено, ₽), `deadline` (ISO-дата или `null` = бессрочная) |
| `bliq` | Ликвидные накопления (подушка), ₽ |
| `r_bench` | Безрисковая альтернативная доходность (годовая, доля) |
| `risk_tolerance` | Риск-профиль 1–5 (1 консервативный … 5 агрессивный) |

Свободный месячный поток = `income_total − expense_total − Σ monthly_payment`.

## 2. Данные — как из реальной выгрузки. Правила `invalid` (читать внимательно)

В файлах намеренно присутствуют дефектные записи и дубли `id` — как в сырой
выгрузке из CRM. Правила (уточнены по итогам раунда 3, где эксперты разошлись
именно здесь):

1. **Дефектная запись** — та, которую нельзя однозначно прочитать как валидные
   финансовые данные: нарушен тип/знак/формат поля или отсутствует обязательное
   поле. Такую запись **не чинить и не додумывать**: `status=invalid`,
   `dom=none`, все суммы = 0, `lump=0`.
2. **Ставка выше 300% годовых — мусор**, а не «дорогой долг». Законный потолок
   ПСК микрозайма в РФ ≈ 292%; всё выше — дефект выгрузки.
3. **Отсутствие ключа ≠ `null`.** Если у цели нет поля `deadline` — это дефект
   записи (`invalid`). Явный `"deadline": null` — валидная бессрочная цель.
4. **Пограничные, но читаемые значения — НЕ дефект**: ставка 59% или 292%,
   доход 8 млн ₽/мес, дедлайн в прошлом, нулевая подушка, нулевой доход,
   `target == current` — всё это оценивается по существу.
5. **Дубли `id` бывают двух видов.** Часть дублей — битые записи (`invalid`).
   Часть — **две валидные записи с одним `id` и разными данными**: обе
   оцениваются по существу, каждая по своим числам. Мержить строки по `id`
   нельзя.
6. **На каждую ВХОДНУЮ СТРОКУ — ровно одна строка ответа, строго в порядке
   входа.** Сопоставление у координатора позиционное; `id` дублируются
   легитимно.

## 3. Что нужно решить по каждой валидной записи

1. **Диагностика**: свободный поток, ПДН, запас ликвидности в месяцах (укажите,
   от чего считаете — это ваш выбор), целевая подушка по риск-профилю.
2. **Стратегия по каждому кредиту** относительно `r_bench` (дорогой / дешёвый /
   токсичный — пороги ваши).
3. **Разовые ходы из накоплений** (`lump`): гасить ли кредит из подушки, закрыть
   ли цель, разместить ли излишек. Ограничение — реально доступная ликвидность.
4. **Месячный план** распределения свободного потока по направлениям:
   досрочное погашение долгов / резерв / цели / инвестиции.
5. **План по каждой цели** с проверкой достижимости к дедлайну.
6. **Итоговый статус и вердикт** одной строкой по-русски.

Если поток отрицательный — `status=deficit`, месячные бакеты нулевые, но разовые
ходы (`lump`) и вердикт всё равно дайте, если они уместны.

## 4. Методологические требования

1. **ДО обработки данных** письменно зафиксируйте методологию и все константы:
   пороги ПДН, целевая подушка по риск-профилю, спред «дорогого» долга над
   `r_bench`, критерий «токсичного» долга, правила разовых ходов, аллокация по
   риск-профилю, инструменты по горизонту цели, критерий `invalid`. Константы не
   меняются по ходу обработки.
2. Правила **детерминированные и одинаковые** для всех портретов; обработка
   **программная и полная** (все 12 000, не выборка).
3. Явные ветки для граничных случаев: нулевой доход, нулевые расходы, дефицит,
   перегруженность долгами, перефинансированные цели, цели без дедлайна,
   просроченные дедлайны, отсутствие целей/кредитов, нулевая подушка.
4. **Контроль сохранения сумм**: месячные бакеты в сумме не превышают
   `max(0, свободный поток)`; разовые ходы не превышают доступную ликвидность.
   Отчитайтесь о числе нарушений — должно быть 0.
5. **Сверьте JSONL с карточками** минимум на 3 случайных портретах программно.

## 6. Формат основного ответа — СТРОГО CSV

Шапка обязательна, разделитель — запятая, без пробелов, без CRLF, ровно 12 000
строк данных, порядок строк = порядку входа:

```
id,status,dom,res,debt,goal,inv,lump,confidence
SP4-00000,deficit,none,0,0,0,0,150000,4
SP4-00001,ok,goals+,2000,0,25000,10000,0,3
SP4-00002,invalid,none,0,0,0,0,0,5
```

| Колонка | Значение |
|---|---|
| `status` | `ok` (поток ≥ 0) · `deficit` (поток < 0) · `invalid` (дефектная запись) |
| `res` / `debt` / `goal` / `inv` | ₽/мес в резерв / на досрочное погашение / в цели / в инвестиции |
| `dom` | крупнейший бакет: `debt` · `reserve` · `goals+` (цели + инвестиции) · `none` |
| `lump` | суммарные разовые ходы из накоплений, ₽ (0 — если не предлагаете) |
| `confidence` | **новое:** ваша уверенность в решении по этой строке, 1–5 (1 — «монетка, кейс на границе», 5 — «однозначно»). Считается вашим движком детерминированно: правило уверенности зафиксируйте в методологии |

Суммы — в рублях, без разделителей тысяч. Никакого текста вне CSV.

Зачем `confidence`: в прошлом раунде эксперты дали два противоположных
«лагеря» решений, и было невозможно отличить принципиальную позицию от
кейса на кромке порога. Уверенность позволяет взвесить консенсус и
проверить гипотезу «где эксперты сами не уверены — там и расходятся».

## 7. Чек-лист `dataset_review_v4.md` (два прохода)

**Проход 1 — популяция:** (а) дескриптивные статистики всех денежных и счётных
полей (mean, σ, min, p10, p50, p90, p99, max); (б) корреляции Пирсона и Спирмена
между доходом, расходами, платежами, подушкой и суммами целей; (в) формы
распределений — асимметрия, эксцесс, проверка лог-нормальности дохода (KS);
(г) категориальные и счётные распределения — риск-профиль, `r_bench`, число
кредитов и целей, горизонты дедлайнов, готовность целей.

**Проход 2 — границы и структура:** (д) перепись граничных состояний (нулевой
доход/расходы/подушка, ровно нулевой поток, ПДН на границе, дедлайн в день среза
и просроченный, `target == current`, перефинансирование); (е) реалистичность
кредитов: согласованность **типа продукта со ставкой, сроком и остатком**
(аннуитет), присутствие МФО-сегмента, потолок ПСК; (ж) реалистичность целей:
связь суммы с именем и с доходом; (з) целостность: NaN, дубли `id` (различить
битые и валидные), лишние/недостающие поля.

**Итог:** (и) пронумерованные проблемы `P1..Pn` — каждая с числовым
доказательством и последствием для тестирования; (к) что в датасете **хорошо**
(явным списком — чтобы это не потерялось при переделке); (л) конкретные
рекомендации следующей итерации генератора.

Все числа считать программно, скрипт приложить.

## 8. Приёмочные гейты датасета (`dataset_acceptance_v4.md`)

Проверьте датасет как внешний аудитор инструмента — **до** того как оценивать
портреты, и отчитайтесь «прошло/не прошло» с числами по каждому пункту:

1. Целостность: нет NaN/None в денежных полях, нет отрицательных сумм вне
   намеренно дефектных записей, все обязательные ключи на месте.
2. Дубли `id`: сколько, какие — битые или валидные пары.
3. Аннуитетная согласованность: для каждого кредита срок, восстановленный из
   (остаток, ставка, платёж), лежит в разумных пределах для его типа продукта.
4. Ставки: распределение по продуктам, доля выше потолка ПСК.
5. Непрерывность `r_bench` (число уникальных значений) и его диапазон.
6. Дедлайны: сколько относительно даты среза в прошлом/сегодня/будущем, есть ли
   горизонты > 5 лет.
7. Размер выборки: хватает ли наблюдений на каждую страту, по которой вы
   собираетесь делать выводы (см. power analysis в методичке).

## 9. Выборка обоснований (`expert_opinions_sample_v4.md`)

40 портретов, отобранных **стратифицированно и детерминированно** (например,
каждый 300-й id — способ отбора зафиксируйте). По каждому:

- вход в человекочитаемом виде (доход, расходы, кредиты, цели, подушка, риск);
- ваши метрики (поток, ПДН, запас в месяцах, целевая подушка);
- решение: разовые ходы + месячный сплит + план по целям;
- **проза-обоснование: почему именно так** (2–4 предложения);
- **ручная сверка**: совпадает ли решение движка с тем, что даёт ваша
  собственная методология «на бумаге» для этого портрета; расхождения — явно.

## 10. Журнал допущений (`assumptions_log_v4.md`)

Каждое место, где данные допускают больше одной честной трактовки, — отдельная
пронумерованная запись `A1..An`:

- что именно неоднозначно (поле, ситуация, пример `id`);
- какие трактовки возможны;
- какую выбрали и **почему**;
- сколько записей затронуто (число, посчитанное программно).

Зачем: в прошлых раундах допущения тонули внутри методологии, и при разборе
расхождений было не отличить «другая философия» от «иначе прочитал поле».

## 11. Чувствительность к собственным константам (`sensitivity_v4.md`)

Прогоните свой движок повторно, сдвигая **по одной** ключевой константе на
±20% (или на ближайший разумный шаг): порог «дорогого» долга, порог
«токсичного», целевая подушка, минимальный порог разового хода, пороги ПДН.
Для каждого сдвига укажите:

- долю портретов, у которых изменилась доминанта (`dom`);
- долю, у которых изменился `status`;
- топ-3 kind/ситуации, где эффект максимален.

Зачем: это отделяет ваши **принципиальные** позиции от артефактов конкретной
цифры. Константа, сдвиг которой меняет 40% решений, — не «настройка», а сама
методология; константа с эффектом 2% — шум, и спорить о ней бессмысленно.

## 12. Прогноз расхождений (`disagreement_forecast_v4.md`)

Одна страница до того, как вы увидите чужие ответы (вы их и не увидите):
в каких зонах датасета вы ожидаете расхождений с другими независимыми
экспертами и почему; какие ваши решения считаете спорными; где, по-вашему,
«правильного ответа» не существует и есть только школа мысли.

Зачем: прогноз проверяется постфактум против фактических зон спора — это
калибровка самопознания эксперта и быстрый указатель для координатора.
