# Веха 8 — пошаговый план фронтенда с промптами

> **Назначение.** Это операционный документ: что делать, в каком порядке, на какой поверхности,
> какой моделью, каким промптом и по какому критерию считать шаг закрытым. Заведён, чтобы вахта
> не собирала контур заново и чтобы четыре аккаунта не разошлись в инструментах.
>
> **Источник решений** — `docs/reports/adr/adr_011_milestone8_tooling.md` (контур) и три методички
> в `docs/research/`. Стратегия миграции — `docs/frontend_migration_plan.md`. Эстетика —
> `docs/ui_visual_design_brief.md`. Нормы — `docs/ui_ux_design_standard.md`.
>
> **Правило чтения.** Промпты копируются дословно. Они намеренно короткие: у Opus 5 и Sonnet 5
> сокращённый системный промпт, и длинные инструкции с примерами работают хуже, чем ссылка на
> артефакт в репозитории. Богатый референс (тест, схема, рубрика) сильнее описания словами.

## §1. Маршрутизация модель × усилие

Отказ от «всегда Opus 5 на max». Обоснование и цифры — `docs/research/claude_models_and_token_economics.md`.

| Класс задачи | Модель | Effort |
|---|---|---|
| Дизайн-система, токены, архитектура SPA, сложные экраны (`planning`, `dashboard`) | Opus 5 | high |
| Трудный баг, нестандартная миграция, разбор регрессии | Opus 5 | xhigh |
| Компонент по готовому паттерну, перенос экрана, рутинный рефактор | Sonnet 5 | medium |
| Тесты Vitest на готовый компонент, фикстуры, моки | Sonnet 5 | medium |
| Ротация WATCHLOG §3, CHANGELOG, переименования | Haiku 4.5 | low |
| Код-ревью PR | пара: Sonnet (полнота) + Opus 5 (точность) | medium / xhigh |

`max` — только политика эскалации на дорогом падении, не режим по умолчанию: он дороже `high`
почти вдвое ради двух пунктов индекса. Effort держать постоянным внутри сессии — его смена
инвалидирует кэш промпта.

**Не писать в промптах** «добавь шаг проверки», «используй субагента для верификации» — Opus 5
верифицирует себя сам, и такие инструкции дают двойную работу. Зато **явно указывать длину**:
ответы и артефакты по умолчанию длиннее, чем нужно, и effort их не укорачивает.

   безвозвратно.
2. Выключить дубли плагинов: из пары `code-review` / `pr-review-toolkit` оставить второй;
   `chrome-devtools-mcp` включать точечно, для E2E хватает `playwright`.
   `semgrep` и `security-guidance` — НЕ дубли, держать оба.
3. Перед длинной сессией выключать нерелевантные коннекторы в меню «Search and tools»:

4. Настроить статус-строку Claude Code с процентом контекста и остатком окна — единственный

**Шаг 0.6 — эстафета чатов.** Новый чат начинать на **~70%** заполнения, а не на стене:
своя сводка лучше машинного сжатия на 95%, которое теряет числа, код и ранние инструкции.
Роль сводки у нас уже выполняет WATCHLOG §0 «RESUME POINT» — держать его актуальным.
Аварийная процедура для умирающего чата — `docs/research/context_management_three_levels.md` §9.

```
/plugin

```

### Э3 — Пилотный экран

**Где:** Claude Code. **Модель:** Opus 5 / high, потом Sonnet 5 / medium.

Берётся один некритичный экран и проводится через весь конвейер целиком: компонент → тест →
визуальная проверка → критика дизайна → аудит доступности. Смысл — доказать пайплайн до того,
как на нём поедут все экраны.

**Шаг 3.1. Реализация.**
```
Перенеси экран <имя> на React по выбранному направлению. Только семантические токены.
Данные — через сгенерированные хуки TanStack Query. Формы — React Hook Form + Zod.
Компоненты — Radix через shadcn/ui.
```

**Шаг 3.2. Визуальная проверка.**
```
Открой экран на 1440 и на 390 пикселей ширины, сними скриншоты, найди расхождения с макетом
и почини. Скриншоты через Playwright, не через accessibility-снапшот.
```

**Шаг 3.3. Критика.**
```
> design-critic проверь экран <имя>
```

**Шаг 3.4. Доступность.**
```
> a11y-auditor проверь экран <имя>
```

**Шаг 3.5. Оформить повторяемое как скиллы, а не как раздувание `CLAUDE.md`.**
После того как пилотный экран прошёл конвейер, процедура устоялась — её место в скилле.
Предложенный набор: `finpilot-react-component`, `finpilot-fastapi-endpoint`,
`finpilot-152fz-guard`, `finpilot-katex-formula`, `finpilot-test-coverage`,
`finpilot-migration`. Механика: имя и описание грузятся всегда (~80 токенов), тело — только
при срабатывании. Описание должно говорить **когда** применять, иначе скилл не сработает;
проверяется eval-тестами через `skill-creator`.

```
> skill-creator создай скилл finpilot-react-component по паттерну экрана <имя>.
  Описание должно срабатывать на создание и правку компонентов React и НЕ срабатывать
  на бэкенд. Сгенерируй eval-тесты на оба случая и прогони.
```

**Гейт Э3:** оба субагента без замечаний уровня «блокер»; Vitest на доменной логике экрана
зелёный; Playwright-сценарий проходит; скриншот-эталон зафиксирован.

### Э7 — Безопасность и производительность

**Где:** Claude Code. **Модель:** Opus 5 / high.

- CSP на nonce из FastAPI. Известная мина: Radix использует инлайновые стили, строгий
  `style-src 'self'` ломает Dialog и ScrollArea. Если nonce не протаскивается — оставить
  `style-src 'unsafe-inline'` и завести техдолг явной записью, а не молча.
- Токены: access в памяти, refresh в httpOnly + Secure + SameSite куке с ротацией.
- Заголовки: HSTS, `frame-ancestors 'none'`, Referrer-Policy, Permissions-Policy, nosniff.
- Никаких внешних CDN и шрифтов Google — всё своё, локально. Это и 152-ФЗ, и устойчивость.
- Проверить, что ни один секрет не попал в бандл под префиксом `VITE_`.
- Гейты: Lighthouse CI, лимит веса чанков. Целевые значения — LCP до 2.5 с, INP до 200 мс,
  CLS до 0.1 на 75-м перцентиле; стартовый JS дашборда до 250 КБ в gzip.

**Гейт Э7:** заголовки на месте, `unsafe-eval` отсутствует, бюджеты держатся.

## §4. Что режется при отставании

Порядок отказа, если срок поехал больше чем на 20%:

1. Тёмная тема — переносится на веху 9.
2. Второстепенные экраны (справка, настройки, юридические тексты) остаются на Jinja2.
3. Диаграмма Санкея — остаётся только составной столбец.
4. Визуальная регрессия — сокращается до трёх ключевых экранов.

**Не режется никогда:** онбординг, дашборд, план распределения, экран согласия, дисклеймер
при ПДН выше 50%, доступность уровня AA на этих экранах.

## §5. Реестр рисков

| Риск | Индикатор | Действие |
|---|---|---|
| Недооценка срока | проскальзывание вехи больше 20% | резать по §4 |
| CSP ломает Radix | падают Dialog/ScrollArea | техдолг с явной записью, не молчать |
| Компрометация npm-зависимости | предупреждение аудита, странный postinstall | откат по lock-файлу, ротация токенов |
| Раздут контекст агента | `claude doctor` показывает перерасход | выключить лишние плагины |
| Расхождение контракта | падает contract-diff | чинить до продолжения, не обходить |
| Дрейф между аккаунтами | разные контуры в разных чатах | сверяться с ADR-011 |

## §6. Дисциплина, которая легко теряется

- Верификатор не совпадает с автором: писал Opus 5 — ревьюит пара, а не он сам.
- Скриншот дороже снапшота доступности: снимать пиксели только когда нужны пиксели.
