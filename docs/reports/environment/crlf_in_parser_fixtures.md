# Репорт: CRLF в фикстурах парсера FINPILOT

**Дата:** 2026-07-30 · **Репозиторий:** `personal-finance-dss`
**Статус:** не сломано, но одна нормализация от того, чтобы сломаться незаметно
**Что делать:** добавить `.gitattributes` (готовый текст в §4)

---

## 1. Что видно

При каждом коммите версии git печатает семь предупреждений:

```
warning: in the working copy of 'app/data/statement_templates/sber.csv',
  CRLF will be replaced by LF the next time Git touches it
```

Файлы:

| Файл | Роль |
|---|---|
| `app/data/statement_templates/sber.csv` | эталонный шаблон выписки Сбера |
| `app/data/statement_templates/tinkoff.csv` | эталонный шаблон Тинькофф |
| `app/data/statement_templates/universal_split.csv` | универсальный табличный формат |
| `docs/model/expert_certification/iterations/2/S/recommendations.csv` | фикстура сертификации |
| `docs/model/expert_certification/iterations/3/M/worst_mismatches_DEMO.csv` | фикстура сертификации |
| `docs/model/expert_certification/iterations/5/S/expert_allocations_v5.csv` | раздача экспертам |
| `docs/model/expert_certification/iterations/5/V/expert_allocations_v5.csv` | раздача экспертам |

---

## 2. Что происходит

У файлов виндовые переводы строк (`\r\n`). В репозитории настроено преобразование к LF —
скорее всего через `core.autocrlf` или наследованный `.gitattributes` с `text=auto`.
Git предупреждает: **при следующем касании** этих файлов он заменит CRLF на LF.

Само предупреждение безобидно. Опасна тихая замена, когда она произойдёт.

---

## 3. Почему это важно именно здесь

Это не любые данные, а **эталоны парсера выписок**. Их роль — быть неизменным образцом,
с которым сравнивают результат разбора.

Три конкретных риска:

**Golden-тесты.** Если сравнение идёт побайтово или по хешу, замена `\r\n` → `\n` меняет
и байты, и хеш. Тест падает, диффа в содержимом нет — искать будешь долго, потому что
глазами файл не изменился.

**Логика парсера на границах строк.** Если разбор где-то опирается на `\r` (например, при
чтении с `newline=''` или при ручном сплите), поведение изменится на файлах, которые
«не менялись».

**Воспроизводимость сертификации.** Фикстуры итераций — исторический материал: раздачи
экспертам, зафиксированные несоответствия. Их назначение — воспроизводимость прошлых
раундов. Нормализация задним числом означает, что прогнать раунд 2 на тех же данных
уже нельзя: данные другие.

---

## 4. Решение

Файл `.gitattributes` в корне `personal-finance-dss`:

```gitattributes
# Фикстуры парсера и сертификации — бинарно-стабильные эталоны.
# Git не нормализует их переводы строк: замена CRLF→LF меняет байты и хеши,
# из-за чего падают golden-тесты и теряется воспроизводимость прошлых раундов.
app/data/statement_templates/*.csv        -text
docs/model/expert_certification/**/*.csv  -text
```

`-text` = «не считать текстом, ничего не преобразовывать».

---

## 5. Проверка после правки

```bash
# 1. Предупреждений больше нет
git add -A && git status

# 2. Git подтверждает атрибут
git check-attr text -- app/data/statement_templates/sber.csv
#   → app/data/statement_templates/sber.csv: text: unset

# 3. CRLF на месте (14 = \r в hex; ищем 0d 0a)
head -c 200 app/data/statement_templates/sber.csv | xxd | grep -c '0d0a'
```

Если п.3 даёт 0 — нормализация уже произошла раньше, и эталоны надо восстановить из тега,
где они ещё с CRLF.

---

## 6. Отдельно: где ещё посмотреть

- **Тесты парсера.** Если сравнение идёт по хешу — зафиксировать это в комментарии
  рядом с тестом, чтобы связь «хеш ↔ переводы строк» была явной.
- **Генерация шаблонов.** Если эталоны генерируются скриптом, он должен писать CRLF
  осознанно (`newline='\r\n'`), а не как получилось от платформы.
- **Остальные `.csv` в репе.** Список выше — те, о которых предупредил git при этих
  коммитах. Полная проверка: `git ls-files --eol | grep crlf`.

---

## 7. Границы этого репорта

Диагноз поставлен **по выводу git**, а не по содержимому файлов и не по коду тестов:
у автора репорта доступа к репозиторию `personal-finance-dss` нет. Утверждение «CRLF
в этих файлах» — надёжное (это буквально сказал git). Утверждение «сломает golden-тесты» —
условное: зависит от того, как устроено сравнение. Пункт 5 даёт способ проверить.

---

> **Одной строкой:** у семи эталонных `.csv` виндовые переводы строк, git готовится их
> тихо нормализовать; для фикстур парсера это меняет байты и хеши, поэтому закрепить
> `-text` через `.gitattributes` до того, как нормализация случится сама.

### Исправление предыдущей редакции этого раздела

В версии v7.2.0 здесь было написано обратное — что все семь файлов уже LF и что
перед коммитом `.gitattributes` надо сверяться с `git ls-files --eol`, иначе
закрепится случайное состояние. **Это было неверно.**

Причина ошибки — в самой проверке, а не в файлах. Проверка выполнялась так:

```python
d = p.read_bytes()[:300]
print('CRLF' if b'\r\n' in d else 'LF')     # ← внутри heredoc
```

Скрипт передавался в Python через shell-heredoc, и экранирование удвоилось:
до интерпретатора долетел литерал из четырёх символов `\r\n`, а не байты
возврата каретки и перевода строки. Такая последовательность в файле не
встречается никогда, поэтому проверка **всегда** отвечала «LF» — независимо от
содержимого. Ложноотрицательный результат, выглядящий как достоверный.

Правильная проверка читает файл целиком и считает вхождения:

```python
d = p.read_bytes()
crlf, lf = d.count(b"\r\n"), d.count(b"\n") - d.count(b"\r\n")
```

Урок шире самого случая: **проверка, написанная через слой экранирования,
обязана быть проверена на заведомо положительном примере.** Если бы рядом
стоял файл, про который точно известно, что он CRLF, инверсия вскрылась бы
сразу. Занесено в `docs/pitfalls.md` как PIT-012.
