# Покрытие фронта — замер и что он говорит

**Дата:** 06.09.2026 · **Версия:** v9.2.0 · **Команда:** `cd frontend && npm run test:coverage`

## Зачем замер, а не «добавить тестов»

Владелец 24.07.2026: «мало тестов на фронт против бэка» — 1949 против 543 на тот момент.
Роадмап поставил условие: **прежде чем наращивать число, посчитать покрытие по строкам
и сравнить с бэкенд-гейтом (90 %)**; «больше тестов» без этого — работа ради счётчика.

🔴 **Покрытия фронта не существовало вовсе:** провайдер не был установлен, в `vite.config.ts`
секции `coverage` не было. Соотношение тестов обсуждалось год, а величина, по которой
его следует судить, ни разу не снималась.

## Числа

| | v9.2.0, первый замер | после тестов хуков бюджетов |
|---|---|---|
| строки | 68.62 % | **69.59 %** |
| ветки | 69.73 % | 69.87 % |
| функции | 52.50 % | 53.72 % |

Бэкенд-гейт — **90 %** строк. Разрыв ≈ 20 пунктов.

## 🔴 Главное: разрыв не размазан, он сосредоточен в одном слое

| слой FSD | покрытие строк |
|---|---|
| `shared` | 97.4 % |
| `features` | 93.4 % |
| `widgets` | 92.0 % |
| `pages` | 79.2 % |
| **`entities`** | **7.2 %** |
| `routes` | 0 % |
| `app` | 0 % |

**Четыре верхних слоя уже на уровне бэкенд-гейта или выше.** Утверждение «мало тестов
на фронт» верно ровно про один слой — и это худший слой из возможных: `entities/*/api`
целиком состоит из хуков, разговаривающих с бэкендом. Там живут ключи кэша, инвалидация,
разбор ошибок.

🔴 **Ошибка в этом слое не роняет ничего и не видна глазами.** Неверный ключ инвалидации:
запрос уходит, ответ приходит, экран показывает **старые** данные. Человек добавил бюджет,
увидел прежний список, добавил ещё раз. Ручная проверка такое не ловит вовсе — а именно
ручной проверкой фронт и принимался.

Подтверждение из истории: дефект `error.status` (v9.1.0, нашло ревью) жил ровно здесь —
у ошибок сгенерированного клиента не было кода ответа, и все проверки `error.status === 401`
всегда давали false. Тесты этого не ловили, потому что конструировали `{status: 401}` руками —
фикстуру, которой в рантайме не бывает (PIT-031).

## Что исключено из замера и почему

`src/shared/api/generated/**` (артефакт hey-api), `routeTree.gen.ts` (артефакт TanStack Router),
`main.tsx` (точка входа: монтирует и всё), `*.test.*`, `*.d.ts`.

Считать покрытие по сгенерированному клиенту значит измерять генератор, а не написанные
нами тесты. **Что именно исключено — важнее самого числа:** без этого списка процент
регулируется тем, сколько кода сгенерировано, и растёт от бездействия.

## Вывод для планирования

Ответ на «мало тестов» — **не наращивать счётчик, а закрыть `entities`**. Слои `routes`
и `app` с нулём — отдельный разговор: там декларации маршрутов и провайдеры, и покрывать
их юнит-тестами значит проверять фреймворк; их закрывает E2E.

Первый шаг сделан: `useBudgets` — 7 тестов, слой сдвинулся на процент по всему фронту.
Остальные девять хуков (`useAuth`, `useTransactions`, `useObligations`, `useGoals`,
`useLiquidAssets`, `useNotifications`, `useConsents`, `usePlanHistory`, `useHouseholds`) —
та же работа, около 300 непокрытых строк.
