# Покрытие фронта — замер и что он говорит

**Дата:** 06.09.2026 · **Версия:** v9.2.0 · **Команда:** `cd frontend && npm run test:coverage`

## Зачем замер, а не «добавить тестов»

Владелец 24.07.2026: «мало тестов на фронт против бэка» — 1949 против 543 на тот момент.
Роадмап поставил условие: **прежде чем наращивать число, посчитать покрытие по строкам
и сравнить с бэкенд-гейтом (90 %)**; «больше тестов» без этого — работа ради счётчика.

🔴 **Покрытия фронта не существовало вовсе:** провайдер не был установлен, в `vite.config.ts`
секции `coverage` не было. Соотношение тестов обсуждалось год, а величина, по которой
его следует судить, ни разу не снималась.

## Числа

|---|---|---|---|

✅ **Планка взята по всем четырём метрикам.** Порог 90 — тот же, что у бэкенда
(`.coveragerc: fail_under = 90`), решение владельца 06.09.2026. Гейт живёт
в `frontend/vite.config.ts` и проверяется в CI (`npm run test:coverage`);
симметрию порогов стережёт `TestCoverageGatesAreSymmetric`.

🔴 **Исключений ради процента не добавлено ни одного.** Единственное новое —
`src/routes/**`, по свойству: `createFileRoute` это макрос, плагин переписывает
файлы при сборке, и счётчик видит **его** ветки (у файла в 6 строк — 5 ветвлений
в колонке 57 первой строки). Логика маршрутов — `validateSearch` — покрыта
отдельным тестом, там же проверка полноты набора маршрутов.

## 🔴 Главное: разрыв не размазан, он сосредоточен в одном слое

| слой FSD | было | стало |
|---|---|---|
| `shared` | 97.4 % | 97.4 % |
| `features` | 93.4 % | 93.4 % |
| `widgets` | 92.0 % | 92.1 % |
| `pages` | 79.2 % | 79.2 % |
| **`entities`** | **7.2 %** | **80.3 %** |
| `routes` | 0 % | 0 % |
| `app` | 0 % | 0 % |

**Четыре верхних слоя уже на уровне бэкенд-гейта или выше.** Утверждение «мало тестов
на фронт» верно ровно про один слой — и это худший слой из возможных: `entities/*/api`
целиком состоит из хуков, разговаривающих с бэкендом. Там живут ключи кэша, инвалидация,
разбор ошибок.

🔴 **Ошибка в этом слое не роняет ничего и не видна глазами.** Неверный ключ инвалидации:
запрос уходит, ответ приходит, экран показывает **старые** данные. Человек добавил бюджет,
увидел прежний список, добавил ещё раз. Ручная проверка такое не ловит вовсе — а именно
ручной проверкой фронт и принимался.

Подтверждение из истории: дефект `error.status` (v9.1.0, нашло ревью) жил ровно здесь —
у ошибок сгенерированного клиента не было кода ответа, и все проверки `error.status === 401`
всегда давали false. Тесты этого не ловили, потому что конструировали `{status: 401}` руками —
фикстуру, которой в рантайме не бывает (PIT-031).

## Что исключено из замера и почему

`src/shared/api/generated/**` (артефакт hey-api), `routeTree.gen.ts` (артефакт TanStack Router),
`main.tsx` (точка входа: монтирует и всё), `*.test.*`, `*.d.ts`.

Считать покрытие по сгенерированному клиенту значит измерять генератор, а не написанные
нами тесты. **Что именно исключено — важнее самого числа:** без этого списка процент
регулируется тем, сколько кода сгенерировано, и растёт от бездействия.

## Вывод для планирования

Ответ на «мало тестов» — **не наращивать счётчик, а закрыть `entities`**. Слои `routes`
и `app` с нулём — отдельный разговор: там декларации маршрутов и провайдеры, и покрывать
их юнит-тестами значит проверять фреймворк; их закрывает E2E.

## ✅ Слой закрыт — одиннадцать хуков, 82 теста (v9.2.0)

`useBudgets` · `useObligations` · `useGoals` · `useTransactions` · `useLiquidAssets` ·
`useConsents` · `useNotifications` · `useUserPrefs` · `usePlanHistory` · `useAuth` ·
`useHouseholds`.

🔴 **Каждый файл проверен мутацией — и это оказалось не формальностью.** Мутация,
которую тест не ловит, означает тест, который ничего не проверяет; таких нашлось
несколько, и все были исправлены на месте:

| мутация | сколько тестов покраснело |
|---|---|
| подмена ключа кэша `["budgets","status"]` → `["budgets"]` | 3 |
| вынос `id` из пути в правке обязательства | 1 |
| подмена «внести прогресс» на «править цель» | 2 |
| сужение префикса `["plan"]` до `["plan","calculate"]` | 1 |
| «сбрасывать профиль всегда», игнорируя `mfa_required` | 1 |
| снятие проверки роли в `enabled` приглашений | 1 |

**Что проверяется в этих тестах и чего в них нет.** Не работа react-query — она его
собственная. Проверяется то, что передаёт наш код: путь, тело, ключ кэша, политика
ретрая и условие `enabled`. Каждое из этих решений записано в докстроке хука
с обоснованием, и тест закрепляет именно решение, а не текущее поведение.

**Самые ценные проверки — те, где «улучшение» вернуло бы дефект:**

- **согласия сбрасывают ВЕСЬ кэш** (`invalidateQueries()` без аргументов). Точечный
  ключ выглядит аккуратнее и оставил бы пять из шести сущностей в устаревшем отказе:
  человек дал согласие, а транзакции, цели, активы, обязательства и уведомления
  продолжают показывать «Требуется согласие»;
- **уведомления не ретраят 401/403.** Колокольчик стоит в топбаре на каждом экране;
  обычный ретрай дал бы три отказа на каждой странице продукта. Политика опиралась
  на `error.status`, которого до v9.1.0 **не существовало** — докстрока обещала
  «не ретраим», а код ретраил;
- **вход не сбрасывает профиль при `mfa_required`** — cookie ещё нет, и запрос ушёл бы
  в 401 ровно тогда, когда человек правильно ввёл пароль;
- **приглашения не запрашиваются у не-владельца** — бэкенд ответит 403, и участник
  увидел бы ошибку там, где у него просто нет такого права.

## Что осталось

- `pages` 79.2 % — формы и экраны, покрыты компонентными тестами; отдельная работа.
- `routes` и `app` с нулём — декларации маршрутов и провайдеры. Юнит-тестами там
  проверялся бы фреймворк; их закрывает E2E.
