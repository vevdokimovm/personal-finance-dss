# Расследование: Stop-гейт тестов упёрся в таймаут посреди батча Волны 0 (INV-MACHINE-LOAD)

**Дата:** 2026-08-12/13. **Тип:** расследование (внешняя причина, дефекта в продуктовом
коде и гейте нет — на момент таймаута). **Реестр:** `investigations_summary.md`.

## Симптом

`.claude/hooks/tests-gate.sh` (Stop-hook, быстрый срез до ~90 с) прервался с сообщением
«[фаза не уложилась в 65 с — прервана]» посреди сдачи батча 0.3/0.4. Фаза «Инварианты
матмодели (property)» успела пройти 45/45 зелёных, следующая фаза не успела даже
напечатать заголовок до обрыва по таймауту.

## Подозрение

Зависший тест — property-тест на инвариантах матмодели (Hypothesis) иногда генерирует
дорогие кейсы; первая гипотеза была «один из property-тестов ушёл в вырожденный поиск
и не завершается».

## Снято с подозрения (корень)

Не зависший тест — перегрузка машины сторонними процессами. `uptime` в момент обрыва
показал **load average 62.65 87.03 62.28** (1/5/15 мин) — на порядок выше числа ядер
любой доступной конфигурации. После того как владелец закрыл лишние приложения,
1-минутная нагрузка упала до **4.57** в течение нескольких минут, а фоновый прогон
pytest, который до этого держал ~13–45% CPU, поднялся до 89–99%.

## Доказательства

1. `uptime` до и после: 62.65/87.03/62.28 → (после закрытия приложений) 4.57/41.15/48.17
   → (ещё позже) стабильно низкая. Классическая кривая рассасывания внешней нагрузки,
   не кривая теста, который вычислительно не меняется по ходу прогона.
2. `ps aux` в момент обрыва показывал единственный тяжёлый процесс от этой сессии
   (сам фоновый `pytest`) — второй, независимый источник нагрузки не входил в дерево
   процессов этой сессии, что исключает «наш собственный код плодит процессы».
3. Пользователь параллельно показал баннер `API Error: 403 · Please run /login` из
   **другого** окна Claude Code (статус-строка `Brewed for 59m 47s`) — прямое
   подтверждение, что на машине одновременно жили другие тяжёлые сессии (проект ведётся
   на 4 аккаунтах, `docs/WATCHLOG.md` шапка).
4. Тот же полный прогон, перезапущенный после снятия нагрузки, дошёл до конца зелёным
   (1545/1545, затем 1548/1548) без каких-либо изменений в тестах или коде между
   попытками — если бы причина была в самом тесте, перезапуск без правок не помог бы.

## Последствия

Прямых потерь нет — фаза, которая не уложилась, не была единственным источником
подтверждения: полный `pytest` (не ограниченный 65-секундным бюджетом хука) прогонялся
отдельно и подтвердил зелёное состояние. Косвенная стоимость — потраченное время на
диагностику и один прерванный фоновый прогон (перезапущен).

## Что опробовано / почему не вышло

- Прочитать `/tmp/finpilot-gate.log` целиком — показал только то же самое: property-фаза
  зелёная, следующая не успела начаться. Лога о зависшем тесте не нашлось, потому что
  зависшего теста не было.
- Повторный запуск гейта сразу после обрыва не делался осознанно — при подтверждённой
  внешней перегрузке повторный запуск на той же загруженной машине с высокой
  вероятностью упёрся бы в тот же таймаут повторно, не давая новой информации, только
  добавляя ещё один конкурирующий процесс.

## Правила, чтобы не наступать снова

1. При таймауте гейта — **сначала `uptime`**, не пересборка/перезапуск. Load average на
   порядок выше числа ядер — прямой признак внешней причины, дальнейшая диагностика
   должна идти в эту сторону первой, а не в сторону «какой тест завис».
2. Не запускать несколько тяжёлых фоновых pytest-прогонов одновременно из одной сессии
   (см. также PIT-016 — отдельная причина того же класса симптомов «долгий прогон выглядит
   подозрительно»): конкуренция за CPU сама по себе замедляет всё на машине, включая
   гейты других сессий.
3. Многоаккаунтная работа (4 аккаунта Claude на одной машине, `docs/WATCHLOG.md`) —
   структурный источник периодической перегрузки, не аномалия; ожидать и не паниковать
   при первом же таймауте.

## Что можно попробовать ещё

Если перегрузка от параллельных сессий станет частой — рассмотреть ограничение
параллелизма pytest (`-n` меньше числа ядер при `pytest-xdist`, если он используется)
или явную координацию между аккаунтами о том, кто в моменте гоняет тяжёлые прогоны.
Пока это не понадобилось — единичный случай, не повторяющийся паттерн.
