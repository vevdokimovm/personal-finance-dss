# Расследование: первый реальный прогон PostgreSQL-матрицы в CI встал на 60+ минут (INV-CI-PG-HANG)

**Дата:** 2026-08-19. **Версия кода:** v8.25.1. **Стоимость:** ~10 шагов проверки через `gh`
(список прогонов, статусы джоб, статусы шагов, отмена, разбор лога отменённого прогона) ≈15-20k
токенов (оценка). **Тип:** расследование (причина внешняя — сетевой флюк раннера GitHub Actions;
попутно найден и починен один реальный, но некритичный дефект конфигурации CI). **Реестр:**
`investigations_summary.md`.

## 1. Вопрос / подозрение

`docs/GLOSSARY.md` (регистро-баг) чинился в v8.25.1 — впервые за всю историю проекта job
`Быстрый (postgresql)` в CI дошёл дальше `preflight`. Джоба «Быстрые тесты + покрытие» на
Postgres реально прошла (`success`) — первое подтверждение, что PostgreSQL-специфика кода
(типы, миграции, `ORDER BY`/`ILIKE`-отличия от SQLite) в порядке за все версии v8.20-v8.25.1
разом. Следующий шаг, «E2E-smoke (chromium)», завис — не завершался **56+ минут**, потом
**60+ минут**, при том что по всей документации (`docs/testing_infrastructure.md`, ROADMAP)
весь `fast`-тир заявлен как «секунды/минуты». Страшная гипотеза: сам батч v8.20-v8.25
(шесть версий, никогда не проверенных матрицей) сломал что-то в связке приложение↔Postgres
именно на уровне E2E — не юнит/интеграционных тестов, а реального сетевого стека, и завис
навсегда (например, приложение зависло в ожидании подключения к БД, которое никогда не
приходит).

## 2. Краткий вывод (TL;DR)

**Дефекта в продуктовом коде нет.** Реальная причина зависания — сетевой флюк GitHub-раннера
при обращении к зеркалам пакетов Ubuntu во время `playwright install --with-deps chromium`:
лог шага обрывается на строке `Get:5 https://archive.ubuntu.com/ubuntu noble-security InRelease`
и больше НИ ОДНОЙ новой строки за все 60+ минут вплоть до ручной отмены. Попутно (не причина
зависания, но реальный дефект CI-конфигурации, не продукта) найден и починен неверный
health-check у сервис-контейнера Postgres: `pg_isready -U finpilot` без `-d` проверяет
несуществующую базу «finpilot» вместо `finpilot_test` — health-check не проходил НИ РАЗУ за
всё время жизни контейнера (~72 минуты), хотя реальным тестам это не мешало.

## 3. Гипотезы

- **A. Батч v8.20-v8.25 сломал что-то в связке приложение↔Postgres на уровне сети/подключений**
  (например, приложение не освобождает соединение и E2E-раннер бесконечно ждёт свободный слот).
- **B. Зависший Playwright/браузер** — `chromium` не смог стартовать в контейнере раннера
  (частая причина зависаний E2E в CI — недостающие системные библиотеки).
- **C. Сетевая инфраструктура раннера** — GitHub-hosted runner не смог достучаться до
  внешних ресурсов (пакетные зеркала, CDN), и что-то внутри цепочки установки зависло без
  таймаута вместо явной ошибки.
- **D. Health-check Postgres не проходит → GitHub Actions бесконечно ждёт «healthy» сервис
  перед стартом шага, который зависит от него.**

## 4. Ход расследования

1. `gh run view <id> --json jobs` — джоба «Быстрые тесты + покрытие» на Postgres имеет
   `conclusion: success`. Это сразу ослабляет гипотезу A: если бы связка приложение↔Postgres
   была сломана батчем v8.20-v8.25, юнит/интеграционные тесты (которые тоже бьют по реальной
   БД через `TestClient`) отловили бы это первыми — они прошли чисто.
2. Замер по времени: шаг «E2E-smoke (chromium)» стартовал `2026-08-19T08:27:10Z`
   (`gh api .../jobs/<id>` → `steps[].started_at`), на момент третьей проверки
   (`2026-08-19T09:23:39Z`) — 56 минут на одном шаге без какого-либо продвижения по статусам
   соседних шагов (`Post Run actions/setup-python@v5` и далее — всё ещё `pending`).
3. Логи ЖИВОГО прогона через `gh run view --log` / `gh api .../jobs/<id>/logs` недоступны —
   GitHub Actions отдаёт логи только после завершения джобы (`404`/«still in progress»). Ждать
   до истечения таймаута (в `ci.yml` `timeout-minutes` не был задан НИ У ОДНОЙ джобы → дефолт
   GitHub 360 минут = 6 часов) означало бы либо ждать часами, либо гадать вслепую.
4. **Решающий шаг:** `gh run cancel <id>` на обоих прогонах (main + тег `v8.25.1`) — после
   отмены логи стали доступны. `gh run view --job <id> --log | grep "E2E-smoke"` показал
   ПОЛНЫЙ вывод шага вплоть до отмены:
   ```
   08:27:10 Installing dependencies... (playwright install --with-deps chromium)
   08:27:11 Get:1..13 (apt update — несколько источников успешно получены)
   08:27:41-49 Ign: http://azure.archive.ubuntu.com/... (несколько повторов Ign — зеркало игнорируется)
   08:27:48 Hit: https://archive.ubuntu.com/ubuntu noble InRelease
   08:27:49.148 Get:5 https://archive.ubuntu.com/ubuntu noble-security InRelease [126 kB]
   09:28:25.796 ##[error]The operation was canceled.
   ```
   Между `08:27:49.148` и отменой в `09:28:25.796` — **ровно ноль новых строк лога за час.**
   `apt-get update` (внутренний вызов `playwright install --with-deps`) завис на скачивании
   одного конкретного индекса пакетов с `archive.ubuntu.com`, не вернув ни ошибку, ни таймаут.
   Это снимает гипотезы A и B: до запуска браузера/тестов дело не дошло вообще — процесс встал
   на установке ОС-зависимостей, до `pytest -m e2e` код дошёл бы только следующей строкой
   команды, которая не выполнилась.
5. Проверка гипотезы D (health-check): лог финального шага «Stop containers» дампит весь
   stdout контейнера `postgres:16` за время его жизни — непрерывные
   `FATAL: database "finpilot" does not exist` каждые ~5с (совпадает с `--health-interval 5s`)
   от старта контейнера (`08:16:42`) до самой отмены. Реальная причина —
   `--health-cmd "pg_isready -U finpilot"` без `-d`: `pg_isready`/libpq по умолчанию
   подставляют имя БД = имени пользователя, если `-d` не задан явно, а `POSTGRES_DB` в этом же
   блоке — `finpilot_test`, не `finpilot`. **Но:** джоба «Быстрые тесты + покрытие» на этом же
   контейнере УСПЕШНО подключилась к `finpilot_test` через явный `DATABASE_URL` — то есть
   сломанный health-check не блокировал доступ к реальной БД, только вводил в заблуждение
   Docker-уровневый статус «healthy» (который в данном pipeline, судя по всему, не является
   жёстким гейтом старта шагов — иначе не прошла бы и предыдущая джоба). Гипотеза D как
   «причина зависания E2E-smoke» отброшена; как «реальный, но не блокирующий дефект
   CI-конфигурации» — подтверждена и починена отдельно (см. §5).

## 5. Корень / вывод

**Зависание — гипотеза C, подтверждена.** Сетевая проблема на стороне инфраструктуры
GitHub-hosted раннера (недоступность/подвисание одного из зеркал `archive.ubuntu.com` при
`apt-get update` внутри `playwright install --with-deps`) — граница «от нас не зависит»:
это не код проекта, не конфигурация приложения, а транзитная проблема сети раннера в момент
конкретного прогона. Косвенное подтверждение границы: РОВНО тот же симптом (зависание на
идентичном шаге) наблюдался ОДНОВРЕМЕННО в обоих независимых прогонах (main-ветка и тег
`v8.25.1`) — если бы дело было в тестовых данных или коде конкретной ветки, поведение двух
разных прогонов не совпало бы так синхронно; совпадение говорит о том, что оба уткнулись в
одну и ту же внешнюю проблему инфраструктуры в одно и то же время.

**Побочный, реальный дефект — health-check Postgres-сервиса.** `pg_isready -U finpilot`
(без `-d finpilot_test`) не является дефектом продукта, но искажает Docker-статус
контейнера (никогда не «healthy», хотя БД полностью рабочая) — почищено в `ci.yml`.

**Структурный пробел, который сделал диагностику дороже, чем должна была быть.** Ни у одной
джобы `ci.yml` не был задан `timeout-minutes` — при реальном зависании (как в этом случае)
GitHub ждал бы штатные 6 часов, прежде чем сам прервал прогон и открыл логи. Добавлены разумные
`timeout-minutes` на все шесть джоб (5/25/15/10/60/90 минут по ожидаемой длительности каждой) —
следующее подобное зависание будет видно и разбираемо в разумные сроки, а не через часы ожидания
или ручную отмену вслепую.

## 6. Что это НЕ (снятые подозрения)

- **Не связка приложение↔PostgreSQL.** Реальные тесты (unit+integration+property) на Postgres
  прошли чисто — код проекта корректно работает с PostgreSQL 16 за все версии v8.20-v8.25.1.
- **Не зависший/сломанный Playwright-браузер и не зависший тест.** Процесс не дошёл даже до
  запуска браузера — встал на установке системных пакетов ДО `pytest -m e2e`.
- **Не блокирующее следствие сломанного health-check.** Неверный `pg_isready` — реальный, но
  отдельный, некритичный дефект: он не помешал ни одному реальному тесту подключиться к БД.

## 7. Профилактика / что запомнить

- При зависании CI-шага дольше ожидаемого — сразу проверять `started_at` конкретного шага
  (`gh api repos/.../actions/jobs/<id>`), не только статус джобы целиком: соседний шаг мог уже
  давно закончиться, а завис именно следующий.
- Логи ЖИВОГО прогона GitHub Actions недоступны через `gh`/API — единственный способ их
  увидеть без ожидания до дефолтного 6-часового таймаута — отменить прогон (`gh run cancel`,
  безопасно и обратимо: прогон просто перезапускается по новому пушу/вручную).
- `timeout-minutes` — обязателен на каждой джобе CI, не только «удобство»: без него зависание
  по внешней причине (как здесь) превращается в многочасовое ожидание вместо быстрого сигнала.
- Если такой же apt-mirror-флюк повторится ещё раз — рассмотреть добавление ретрая/таймаута
  вокруг самого `apt-get`/`playwright install --with-deps` (например,
  `timeout 300 playwright install --with-deps chromium || playwright install --with-deps chromium`
  — повтор один раз) — не сделано в этом батче, канал для следующего повтора, если он случится.

## 8. Уроки

- Решающим шагом оказалась не аналитика, а **отмена прогона** — до неё вообще не было доступа к
  диагностическим данным; правило «нет данных — не гадай, добудь их» применимо и к CI, не только
  к тестам локально.
- Синхронное зависание ДВУХ независимых прогонов на одном и том же шаге в одно и то же время —
  сильный сигнал «внешняя причина», отдельный от «наш код в этой ветке сломан» (одна ветка не
  сломала бы вторую независимую).
