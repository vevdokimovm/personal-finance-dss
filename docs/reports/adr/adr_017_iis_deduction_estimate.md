# ADR-017: Реальный расчёт вычета ИИС типа А — диагностика, не решение

Дата: 2026-08-13 · Статус: Accepted · Батч: v8.18.0 (канон v3.8.0 → v3.9.0)

> Продолжение ADR-014 (вариант B — общая текстовая нота, без знания статуса счёта
> пользователя). Владелец попросил довести дальше: реальный расчёт суммы вычета, не
> просто упоминание, что он существует. Красная линия та же, что у ADR-016 (лавина
> долгов) — новая диагностика вычисляется ПОСЛЕ ранжирования, никогда не влияет на то,
> какая альтернатива побеждает. Это и есть способ обойти архитектурный риск, из-за
> которого ADR-014 остановился на варианте B: ADR-008 предупреждал именно о пороговом
> эффекте лимита ИИС **в решении**, не в тексте объяснения уже принятого решения.

---

## Контекст

ADR-014 нашёл: у модели нет ни одного персонализированного налогового расчёта, только
статичный множитель НДФЛ в $r_{\text{bench}}$ (§10.2) и (с v8.14.2) общая текстовая нота
`IIS_NOTE` в инвестиционном трансе (§13) — не знает тип счёта пользователя, использованный
лимит года, ничего не считает, просто напоминает про существование льготы.

Вариант C (полный налоговый слой из ADR-014) был отклонён целиком — но у отклонения было
ДВЕ разные причины, смешанные в одну:
1. Новые поля пользовательского ввода (тип ИИС, использованный лимит) — это НЕ архитектурный
   риск, просто новый вход, тот же класс, что `income_history` (ADR-015) или `risk_tolerance`.
2. Пересчёт **эффективной доходности** транша с учётом вычета — вот это ДЕЙСТВИТЕЛЬНО риск:
   если эффективная доходность входит в сравнение альтернатив, лимит 400 000 ₽/год становится
   пороговым критерием (ADR-008), способным дать неоптимальный совет на границе лимита при
   шаге решётки 10%.

ADR-014 отклонил оба пункта вместе, хотя рискован только второй. Этот ADR разделяет их:
пункт 1 — делаем; пункт 2 — по-прежнему нет, но обходится способом ниже.

## Красная линия: почему расчёт вычета НЕ должен входить в сравнение альтернатив

Если бы `estimate_iis_deduction` как-то влиял на выбор победителя (например, «предпочесть
альтернативу с большим вычетом при равном utility»), лимит 400 000 ₽/год стал бы пороговым
критерием SAW-свёртки задним числом — ровно тот сценарий, о котором предупреждал ADR-008.
Пользователь на границе лимита (внёс 380 000 ₽) получил бы резко разный совет в зависимости
от того, попадает ли следующий рубль в оставшиеся 20 000 ₽ — при шаге решётки 10% это может
дать заметно неоптимальный результат именно на границе.

**Правило:** вычет ИИС — чистая диагностика для УЖЕ выбранной альтернативы, вычисляется
ПОСЛЕ ранжирования (`annotate_investment_tranche` уже вызывается после `rank_alternatives` —
см. `app/services/planning.py`), никогда не входит в `utility`/`floor_level`/сортировку.
Гарантия по конструкции кода: `estimate_iis_deduction` — чистая функция без побочных
эффектов, вызывается из `annotate_investment_tranche`, которая не читается `ranking.py`.

## Что технически МОЖЕТ безопасно меняться

Новые поля пользовательского ввода в `user_prefs` (`iis_type`, `iis_contributed_this_year`)
— обычное расширение схемы, тот же класс, что `income_history`/`risk_tolerance`. Формула
вычета — детерминированная арифметика по тексту закона (НК РФ, факт, не мнение экспертизы).

## Предлагаемая формула

Только для типа А — там закон однозначен и не требует трактовки:
$$ \text{eligible} = \min(\text{amount},\ \max(0,\ 400\,000 - \text{contributed\_this\_year})) $$
$$ \text{deduction} = 0.13 \cdot \text{eligible} $$

где $\text{amount}$ — сумма инвестиционного транша уже ВЫБРАННОЙ альтернативы (не входит в
выбор, только описывает его). Для типа Б и ИИС-3 численный расчёт **не делается** — правила
ИИС-3 (поэтапное увеличение срока владения, частичное смешение льгот А/Б) сформулированы в
законе с переходными положениями, которые я не берусь корректно закодировать без риска
выдать неверную цифру пользователю; для этих типов остаётся качественная текстовая нота
(тот же уровень, что ADR-014 вариант B), не выдуманное число.

## Варианты

**A. Ничего не делать сверх ADR-014 (отклонено).** Оставляет доступное дешёвое улучшение
на столе — числовой расчёт для типа А закону не требует трактовки, спорной позиции нет.

**B. Численный расчёт для типа А диагностикой после решения (выбрано).** Не трогает
решётку/ADR-008, даёт реальную персонализированную цифру вместо общей фразы.

**C. Полный вариант C ADR-014 — вычет меняет выбор альтернативы (отклонено, как и в
ADR-014).** Ровно тот риск, которого избегает красная линия выше.

**D. Численный расчёт для всех типов, включая приблизительные правила ИИС-3 (отклонено).**
Риск выдать пользователю неверную налоговую цифру перевешивает пользу — закон по ИИС-3 имеет
переходные положения, которые не хочется угадывать без юридической сверки. Текстовая нота
честнее приблизительного числа.

## Выполнено

1. ✓ **Новые поля** — `user_prefs.iis_type` (`none`/`A`/`B`/`three`, default `none`),
   `user_prefs.iis_contributed_this_year` (Numeric, default 0). Миграция 0033.
2. ✓ **`app/core/investment.py::estimate_iis_deduction`** — чистая функция, формула выше.
3. ✓ **`annotate_investment_tranche`** — новые опциональные параметры `iis_type`/
   `iis_contributed_this_year`; при типе А заменяет общий `IIS_NOTE` на персонализированную
   фразу с реальной суммой вычета.
4. ✓ **Красная линия** — тест, что `Rt`/`Dt`/`best["id"]`/`utility` не меняются в
   зависимости от `iis_type`/`iis_contributed_this_year` (варьирование входа не меняет
   решение, только текст транша).
5. ✓ **Канон** — §13 расширен (формула + красная линия), §17 (нет новых констант — 400 000/
   0.13 уже были текстом), §19 (v3.8.0 → v3.9.0).

## Ограничения

- Только тип А. Тип Б/ИИС-3 — текстовая нота, не число (см. вариант D выше).
- Не учитывает, есть ли у пользователя официальный доход, облагаемый НДФЛ, из которого вычет
  вообще можно получить (вычет — это возврат УЖЕ УПЛАЧЕННОГО налога, не подарок) — цифра
  показывает МАКСИМАЛЬНО ВОЗМОЖНЫЙ вычет по закону, не гарантированный для конкретного
  пользователя. Стоит сформулировать явно в тексте UI, не только в ADR.
- `iis_contributed_this_year` — пользователь вводит сам, модель не может это проверить
  (нет интеграции с брокером/ФНС) — доверие ко входу, как и остальные пользовательские данные.

## Когда пересмотреть

Если после запуска реальная телеметрия (волна 0, п. 0.6 — когда включится) покажет
значимую долю пользователей с типом ИИС-3 — стоит вернуться и либо найти юридическую
консультацию по переходным правилам, либо явно спросить пользователя о деталях его счёта
вместо расчёта. До этого момента — текстовая нота для типа Б/3 остаётся потолком.
