# Гейты, которых не было: десять дефектов между «локально зелено» и красным CI

**Тип:** разбор инцидента · **Период:** 24–25.09.2026 · **Версии:** v9.13.15 … v9.13.18
**Итог:** прогон по тегу `v9.13.18` (36102456685) — **зелёный целиком**, восемь джоб из восьми.
**Предшественник:** `ci_red_on_tags_for_a_month.md` (месяц красного на тегах, визуальная регрессия).

---

## 1. Что видел владелец

Дословно, в трёх репликах за сутки:

> «ты уже прогнал вроде все тесты гита здесь локально все они прошли как ты сказал
> но ты задеплоил и там УПАЛО БОЛЬШЕ ТЕСТОВ ЧЕМ ПАДАЛО ДО ЭТОГО»

> «мы весь день пытаемся выполнить одну сраную задачу пройти гейты. буквально»

> «как тако возможно что ты ТЕПЕРЬ ГОНЯЕШЬ ТЕСТЫ ВСЕ ГИТА ЛОКАЛЬНО ЗДЕСЬ 1 В 1
> НО ВСЕ РАВНО ОНИ ПАДАЮТ ТАК ЕЩЕ И БОЛЬШЕ ЧЕМ БЫЛО»

Эти три вопроса — не риторика, у каждого есть точный технический ответ, и все три ответа
в разделе 3. Главный из них: **«1 в 1» было неправдой**, и неправдой в трёх независимых
местах одновременно.

---

## 2. Почему красного стало БОЛЬШЕ после починок

Это первое, что нужно понять, иначе весь разбор читается как история провала.

🔴 **GitHub останавливает джобу на ПЕРВОМ упавшем шаге.** Пока падал шаг №1, шаги
№2…№14 не исполнялись **ни разу** — их отказы существовали, но были невидимы. Каждая
починка открывала следующий слой, и число красных галок росло, хотя дефектов
становилось меньше.

| Прогон | Что падало | Что из-за этого не исполнялось |
|---|---|---|
| до v9.13.11 | визуальная регрессия (28 из 72) | live-a11y, фронтовые E2E, bandit, pip-audit, нагрузка |
| v9.13.13 | флейк firefox | то же |
| v9.13.14 | bandit, 5 находок | pip-audit, нагрузка |
| v9.13.16 | `ModuleNotFoundError: defusedxml` | **весь pytest целиком, до первого теста** |
| v9.13.17 | тесты гейта следа | — |
| **v9.13.18** | — | **зелено целиком** |

Последняя строка таблицы — и есть ответ на «почему так долго»: слоёв было десять.

## 3. Десять дефектов

Порядок — тот, в котором они вскрывались. У каждого: что было, чем доказано, чем закрыто.

### Д1. Шаг не падал на первой упавшей команде

**Было.** GitHub исполняет блок `run:` через `bash --noprofile --norc -eo pipefail`;
флаг `-e` валит шаг на первой же неудаче. `tools/ci_local.py` звал
`subprocess.run(shell=True)` — это `/bin/sh` **без** `-e`, и код возврата шага равнялся
коду **последней** команды.

**Замер.** Шаг «Тесты + покрытие ядра» — это `coverage run -m pytest` и следом
`coverage report`. pytest дал `1 failed, 2436 passed`, `coverage report` прошёл порог
и вернул ноль → **шаг помечен зелёным на упавших тестах**.

**Это дословный ответ на «локально всё прошло, а в гите упало больше».**

**Закрыто.** Оболочка и флаги повторяют GitHub дословно. Три теста, включая `pipefail`.

### Д2. Фильтр установки выбрасывал шаги, которые ПРОВЕРЯЮТ продукт

**Было.** `bandit`, `pip-audit` и нагрузочный smoke записаны в воркфлоу как две строки:
поставить инструмент и тут же проверить. Регулярка видела `pip install` в первой строке
и пропускала **весь шаг**. Три проверки из четырнадцати не исполнялись локально ни разу.

**Рецидив.** Тот же класс закрыли в v9.13.14 — но частным случаем (`playwright install`
убрали из фильтра), а не правилом. Через один батч класс вернулся на трёх других шагах.

**Закрыто.** Правило: шаг пропускается, только если установка — **все** его команды.

### Д3. В венве не было `pip`

**Было.** Венв собран через `uv`; `pip install -q pip-audit` падал
командой-не-найдена за 0.0 с. Даже будь фильтр исправен, эти шаги не запустились бы.

**Закрыто.** `ensurepip` + симлинк `pip` → `pip3`.

### Д4. Семь уязвимостей в зависимостях

Найдены `pip-audit`, впервые дошедшим до исполнения:

| Пакет | Было | Стало | Идентификаторы |
|---|---|---|---|
| `cryptography` | 48.0.1 | 50.0.0 | PYSEC-2026-3552, 3553, 3554 |
| `pydantic-settings` | 2.14.1 | 2.14.2 | CVE-2026-58203 |

Ядро зелёное после мажорного подъёма (2440 passed).

### Д5. Нагрузка мерила отказ доступа, а не продукт

**Было.** Юрблок L1 (v8.40.0) сделал `consent` обязательным полем регистрации —
`locustfile` его не слал: **100 % отказов `register HTTP 422`**. После починки вскрылся
второй слой: все защищённые ручки отвечали `403 consent_required`, потому что сценарий
не выдавал отдельное согласие на финансовые данные. Продукт вёл себя верно.

**Закрыто.** Сценарий проходит путь пользователя целиком; выход 0, ноль отказов.
Заведён гейт `tests/test_loadtest_matches_contract.py` — тело регистрации сверяется
со схемой `RegisterRequest` разбором кода.

### Д6. Отпечаток дерева не видел правок содержимого

**Было.** `tree_hash` считал `sha256(HEAD + git status --porcelain)`, а `--porcelain`
печатает только СТАТУС файла (` M путь`). Файл, уже числящийся изменённым, можно было
править после зелёного прогона сколько угодно.

**Замер.** Правка `docs/WATCHLOG.md` после прогона оставила отпечаток `2c74eab99bd8a6cf`
неизменным до и после.

**Закрыто.** Хешируется содержимое каждого изменённого файла. Восемь тестов, включая
стабильность отпечатка на неизменном дереве.

### Д7. Параллельный прогон был невозможен

**Было.** `conftest` кладёт адрес временной SQLite в `os.environ`, а воркеры `xdist` —
дочерние процессы, которые это окружение **наследуют**: условие «создать базу, если
адрес не задан» у них не срабатывало, и восемь воркеров создавали схему в одном файле
(`table transactions already exists`).

**Замер.** После изоляции по `PYTEST_XDIST_WORKER`: **9 мин 19 с против 26 мин 12 с**.

🔴 Команды CI не менялись: `-n` только для локального цикла, вердикт снимается
последовательным прогоном.

### Д8. Шаг нагрузки не переживал второй прогон подряд

**Было.** Шаг поднимал `uvicorn &` и не гасил никогда. На раннере процесс умирает вместе
с машиной, локально оставался сиротой на порту 8000 — следующий прогон бил в СТАРЫЙ
процесс со старой базой и получал `register HTTP 500`. Дефекта в коде не было вовсе.

**Закрыто.** Порт освобождается до старта, сервер гасится по `trap ... EXIT`.
Проверено двумя прогонами шага подряд.

Это ровно вопрос из чек-листа `preflight`: «сработает ли на втором прогоне подряд,
когда результат прошлой работы лежит на диске?».

### Д9. Гейт следа не был подключён

**Было.** `ci_local_failures` написана в v9.13.14 вместе с шестью тестами — и
**не вызывалась из `preflight.run()` ни разу**. Тесты звали функцию напрямую, поэтому
зелёное покрытие означало «функция работает», а не «правило исполняется».

**Следствие.** Полтора батча подряд `preflight` печатал «механические проверки: чисто»
при КРАСНОМ следе с чужого дерева. Механизма, которым закреплено правило владельца
«гейты гита прогоняются здесь и целиком», физически не существовало — при том что
CHANGELOG v9.13.14 объявил его работающим.

**Закрыто.** Семь тестов на ФАКТ ВЫЗОВА, а не на поведение функции.

### Д10. `defusedxml` не объявлен в requirements

**Было.** v9.13.14 перевела разбор XML от ЦБ на `defusedxml` (закрытие находки bandit
B314) — и пакет не попал в `requirements.txt`. Локально стоял в венве → прогон зелёный;
на чистом раннере `conftest` не импортировался **вообще**, четыре джобы из девяти падали
до первого теста.

**Закрыто.** Пакет объявлен; заведён гейт `tests/test_imports_are_declared.py` — сверяет
каждый сторонний импорт `app/` с requirements разбором кода. Импорты под
`try/except ImportError` считаются намеренно опциональными (`plaid`).

**Гейт сразу нашёл вторую мину того же класса:** `starlette` импортируется напрямую
в `app/middleware.py` и держался на транзитивности от FastAPI — объявлен явно.

### Д11 (бонус). Тесты гейта следа не исполнялись в CI

**Было.** Гейт намеренно молчит при `CI=true` (следа на раннере нет и быть не может),
а тесты ожидали отказ и получали пустой список. Падали **все до одного** — с момента
написания в v9.13.14. Видно не было: джоба умирала раньше, на Д10.

**Закрыто.** Автофикстура снимает признак раннера; тесты, проверяющие поведение В CI,
выставляют переменную сами. Проверено прогоном с `CI=true`: 44 passed.

## 4. Корень: окружение, а не команды

Девять из одиннадцати дефектов — частные случаи одного:

🔴 **Локальный прогон повторял КОМАНДЫ воркфлоу, но не его ОКРУЖЕНИЕ.**

Расхождение всегда в одну сторону: у разработчика пакетов больше, чем объявлено.

**Замер после сведения окружений:**

| Окружение | Пакетов |
|---|---|
| `.venv-ci` (строго по requirements, как раннер) | **94** |
| рабочий венв | **158** |

**64 лишних пакета**, о которых CI не знает. `defusedxml` был одним из них.

**Решение владельца, дословно:**

> «СДЕЛАЙ ОКРУЖЕНИЕ ОДНО ПРАВИЛЬНОЕ И ТУТ И ТАМ И УВИДИШЬ ОШИБКИ ЛОКАЛЬНО
> И ПОФИКСИШЬ СРАЗУ»

**Сделано.** `tools/ci_local.py` гоняет гейты в `.venv-ci`. След прогона несёт поле
`environment`: зелёный след из рабочего венва больше не притворяется зелёным из чистого.

🔴 **Чего это НЕ закрывает.** Разницу ОС (раннер ubuntu, станция macOS): apt, пути,
браузеры. Docker на машине отсутствует. Закрыт измеренный источник расхождения,
не все возможные.

## 5. Класс ошибки, повторившийся трижды за двое суток

> **Проверка написана, покрыта тестами — и НЕ ИСПОЛНЯЕТСЯ.**

1. **Д2** — шаг выбрасывался фильтром до запуска.
2. **Д9** — функция гейта не вызывалась из точки входа.
3. **Д11** — тесты гейта не работали в среде, для которой писались.

Ни покрытием, ни тестами самой проверки этот класс не ловится: тест на функцию
подтверждает, что функция работает, а не что её зовут. **Ловится только проверкой
факта вызова** — и только такой тест теперь стоит на `preflight`.

Родственный класс из прошлого разбора — «гейт заявлен как проверяющий X, но X
не проверяет» (PIT-016, шрифт v8.39.0, CJK-канарейка). Общее у них: зелёный вердикт
означает «не проверялось», а не «проверено и верно».

| Полных локальных прогонов | 5, из них 3 потеряны впустую |

| Дефектов найдено | 11 |
| Уязвимостей закрыто | 7 |
| Новых гейтов заведено | 5 |

**Из трёх потерянных прогонов два — процедурная ошибка вахты, а не свойство проекта:**
тяжёлый прогон запускался ради проверки, которую статический гейт делает за 3 секунды
(строчка версии в README), и не прибирались осиротевшие процессы от предыдущего прогона.

🔴 **Правило, оплаченное этим: ДЕШЁВОЕ ПЕРВЫМ.** Перед длинным прогоном гонять
`preflight`, `revision_check`, `flake8`, `mypy`, тесты церемонии и гигиены — весь набор
укладывается в 8–16 секунд и ловит ровно тот класс, на котором вахта обожглась дважды.

## 7. Что теперь стоит между нами и повторением

| Механизм | Против чего |
|---|---|
| `bash -eo pipefail` в прогоне | Д1 — падение внутри многострочного шага |
| Фильтр по ВСЕМ командам шага | Д2 — проверка, выброшенная как установка |
| `.venv-ci` + поле `environment` в следе | корень — расхождение окружений |
| `tests/test_imports_are_declared.py` | Д10 — необъявленная зависимость |
| `tests/test_loadtest_matches_contract.py` | Д5 — сценарий отстал от схемы |
| `tests/test_tree_hash_sees_content.py` | Д6 — правка после зелёного прогона |
| `tests/test_preflight_calls_stamp_gate.py` | Д9 — проверка не вызывается |
| `tests/test_ci_local_uses_clean_venv.py` | прогон в «богатом» венве |
| `trap ... EXIT` в шаге нагрузки | Д8 — сирота на порту |
| изоляция по `PYTEST_XDIST_WORKER` | Д7 — общая база у воркеров |

## 8. Что осталось открытым

1. **Разница ОС** между станцией и раннером. Закрывается контейнером; Docker
   на машине не установлен. До тех пор локальный зелёный остаётся сильным признаком,
   но **вердикт снимает `python -m tools.ci_verdict` с прогона ПО ТЕГУ**.
2. **Дублирование `core` и `fast`**: обе джобы гоняют `pytest -m fast`, отличаясь только
   файлом покрытия. На раннере они параллельны, локально — час подряд.
3. **Бейдж CI показывает только ветку по умолчанию.** Прогоны по тегам, где идёт полный
   тир (мультибраузер, визуал, a11y, security), в него не попадают в принципе. Закреплён
   за `main` явно (`?branch=main`), рядом добавлен бейдж последнего тега.
