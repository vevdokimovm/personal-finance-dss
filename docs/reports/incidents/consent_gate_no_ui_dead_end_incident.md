# Post-mortem: гейт согласия на финданные не имел UI — каждый новый пользователь упирался в непроходимую стену (SEV1, near miss), 2026-08-19

Авторы: сессия 2026-08-19. Статус: Final.

## Summary

Бэкендовый гейт `require_financial_consent` (`app/api/_consent_guard.py`, введён v7.5.0,
2026-07-30) корректно требует отдельное согласие на обработку финансовых данных для шести
роутеров (transactions/obligations/goals/liquid_assets/budgets/telemetry). Замысел с самого
начала был явным: «403 с машиночитаемым телом, чтобы фронт показал экран согласия» (CHANGELOG
[7.5.0]). Этот экран **не существовал вообще** ни разу за 26 дней и минимум 15 версий продукта
(v7.5.0 → v8.25.2), включая весь батч CRUD-паритета (v8.25.0), который прямо добавлял формы
создания финансовых записей. Результат: **каждый новый зарегистрированный пользователь**, дав
единственное обязательное при регистрации согласие (ПДн), при первой же попытке открыть
`/obligations`, `/assets`, `/goals` или `/transactions` получал 403 и заглушку «Проверьте
соединение и попробуйте ещё раз» — тупик, из которого не было ни одного пути через интерфейс.
`POST /api/consents/{consent_type}` был сгенерирован клиентским SDK и не вызывался НИОТКУДА во
фронтенде — реальный обходной путь существовал только через curl.

## Impact

- **Фактическое воздействие на данный момент: ноль** — продукт не запущен публично (подтверждено
  ранее в этой же сессии: nginx с v8.9.0 прячет соответствующие маршруты от обычного доменного
  трафика). Это near miss, не реальный инцидент с пострадавшими пользователями.
- **Потенциальное воздействие при публичном запуске без этой находки — SEV1-эквивалент.** Не
  деградация, а полная и постоянная блокировка ключевой функции продукта (создание любой
  финансовой записи) для 100% новых пользователей, без обходного пути в UI. Продукт называется
  «система поддержки принятия решений в персональных финансах» — без единой финансовой записи
  он не может выполнить свою единственную функцию ни для одного нового пользователя.
- **Длительность окна риска:** минимум 26 дней (2026-07-30, v7.5.0 → 2026-08-19, момент
  обнаружения), 15+ версий продукта, включая весь видимый прогресс вехи 8 (React-фронтенд).

## Timeline (даты)

- **2026-07-30 (v7.5.0)** — гейт `require_financial_consent` введён на бэкенде. Замысел UI
  зафиксирован в CHANGELOG явно: «Отказ — 403 с машиночитаемым телом… чтобы фронт показал экран
  согласия, а не текст ошибки». Frontend на этот момент ещё не существует (React SPA стартует
  v8.4.0).
- **2026-08-05…2026-08-15 (вехa 8, Э2-Э8, до v8.25.0)** — React-экраны транзакций, обязательств,
  целей, активов построены и получают формы создания (CRUD-паритет батч 1, v8.25.0). Ни на одном
  этапе никто не заметил и не воспроизвёл сценарий «только что зарегистрированный пользователь
  пытается создать первую запись» — все проверки (design-critic, a11y-auditor, ручные прогоны в
  браузере) выполнялись на существующих демо-аккаунтах/сессиях, где согласие либо уже было дано
  вручную, либо проверка шла на гостевом/демо-режиме (который сознательно НЕ гейтится — см.
  Contributing factors).
- **2026-08-14 (v8.24.1)** — гейт согласия добавлен ЕЩЁ на один роутер (`budgets_router`).
  CHANGELOG формулирует это как «был единственным из пяти финансовых роутеров без него» —
  формулировка, зафиксировавшая периметр в пять, хотя фактически (после этого патча) под
  гейтом шесть роутеров, включая `telemetry_router` — периметр в комментариях разошёлся с кодом
  (см. отдельный пункт ROADMAP §9.0 «C», разбор откуда взялась именно пятёрка — не переоткрывать
  здесь, это отдельная, не менее важная задача).
- **2026-08-19** — по прямому запросу владельца: «Проверь эмпирически, не по докам: может ли
  только что зарегистрированный пользователь создать хоть одну финансовую запись через React».
  Гипотеза владельца была сформулирована ДО эмпирической проверки, по чтению кода
  (`app/core/legal.py:29`, `app/api/router.py:40-54`, отсутствие использования
  `grantApiConsentsConsentTypePost` во фронтенде) — эмпирическая проверка (Playwright,
  headless-браузер, реальный backend+frontend, реальная регистрация) подтвердила её на 100%:
  `POST /api/auth/register` → 201, следующий же `GET /api/obligations` → 403
  (`code: "consent_required"`), проверка `/profile` подтвердила — там не было ни слова про
  согласие или финансы, хотя серверное сообщение ошибки утверждало обратное («можно дать в
  настройках профиля»).
- **2026-08-19 (та же сессия)** — рабочий минимум согласия реализован (не полный экран L3):
  `entities/consents`, `ConsentRequiredPanel` вместо старой заглушки на всех четырёх списках,
  блок «Согласия» в `ProfilePage`. Design-critic и a11y-auditor прогнаны на новый код (стандартная
  церемония батча) — нашли и починили 5 блокеров дизайна и 3 нарушения AA до сдачи.

## Detection

Обнаружено **владельцем**, не автоматической проверкой и не одним из специализированных агентов
проекта (`design-critic`, `api-contract-guard`) — оба существовали на момент, когда гейт получил
UI-фронт (v8.25.0), но ни разу не были нацелены на сценарий «путь совершенно нового
пользователя». `design-critic`/`a11y-auditor` оценивают то, что УЖЕ отрендерено — если экран
согласия не существует как артефакт, нечего критиковать; `api-contract-guard` сверяет
использование API с контрактом OpenAPI, но не проверяет «используется ли вообще каждый
эндпоинт контракта» (обратное направление проверки). Прямая цитата владельца, зафиксировавшая
масштаб находки: «если бы не независимый эксперт в другом чате, то не заметили и в прод бы
ушла — это треш, это прямо очень очень плохо».

## Root cause

**Технической причины/бага в смысле "код делает не то, что задумано" здесь нет** — гейт работает
ровно так, как спроектирован в v7.5.0. Причина — **пропущенная часть замысла**, зафиксированная
в CHANGELOG словами, но никогда не превращённая в задачу с чекбоксом ни в одном плане вехи 8
(`docs/frontend_milestone8_plan.md`, ROADMAP §8.2). Формы создания записей (батч CRUD-паритет)
строились и проверялись на happy path (пользователь с уже данными согласиями), а не на пути
принципиально нового пользователя.

**5 Whys:**
1. Почему новый пользователь не мог создать запись? — 403 от гейта согласия, нет UI для его
   прохождения.
2. Почему не было UI? — Задача «построить экран/контрол согласия» никогда не была заведена как
   отдельный пункт плана вехи 8 — она подразумевалась текстом CHANGELOG v7.5.0, но не стала
   явным чекбоксом ROADMAP.
3. Почему это не всплыло при сдаче батча CRUD-паритета (v8.25.0), который прямо строил формы
   создания финансовых записей? — Ручная проверка в браузере (design-critic/a11y-auditor,
   ручной прогон) шла на сессии/аккаунте, где согласие уже было дано раньше в ходе разработки —
   путь «только что зарегистрированный, ничего не дававший согласия пользователь» не был частью
   сценария проверки.
4. Почему сценарий «совсем новый пользователь» не входит в стандартную проверку батча? — Нет
   класса тестов, который явно требует: «взять чистое состояние (свежая регистрация,
   демо-режим), пройти реальный, полный путь до конца — не мок, не отдельная функция, реальный
   HTTP+браузер». design-critic/a11y-auditor оценивают экран, который уже отрендерился; никто
   не проверял, доходит ли пользователь до этого экрана вообще, с нуля.
5. Почему такого класса проверок нет в процессе? — Церемония батча (CLAUDE.md правило 1, TDD)
   гарантирует, что НАПИСАННЫЙ код соответствует НАПИСАННЫМ тестам — она структурно не может
   поймать пробел «функциональность не написана вообще, хотя была задумана» (не баг реализации,
   а дыра в объёме задачи). Это тот же класс провала, что 41-дневный красный CI
   (`ci_blocking_gate_red_41_days.md`) с другой стороны: там локальная проверка расходилась с
   реальной средой выполнения; здесь проверка «в принципе работает интерфейс» расходилась с
   «работает ли он для реального нового пользователя», потому что никто не смотрел с этой
   стороны.

## Contributing factors

- **Демо/гостевой режим сознательно не гейтится** (`_consent_guard.py:58-60` — «демо-данные не
  относятся к определённому субъекту, 152-ФЗ неприменим») — это правильное решение само по себе,
  но оно означало, что ЛЮБАЯ проверка на демо-данных (а UI вехи 8 в основном демонстрировался и
  проверялся именно на демо-кейсах вроде «anna», «ekaterina») никогда не наткнулась бы на этот
  гейт — demo-путь и путь реального нового пользователя разошлись, и все проверки шли по первому.
- **Миграция `0031` перенесла согласие СУЩЕСТВУЮЩИМ пользователям** (v7.5.0) — то есть на момент
  введения гейта уже существующие тестовые/девелоперские аккаунты автоматически получили
  согласие задним числом. Единственная категория, которая НЕ могла его получить автоматически —
  пользователи, зарегистрированные ПОСЛЕ v7.5.0 — то есть именно те немногие тестовые аккаунты,
  которые кто-то создавал бы в процессе разработки вехи 8, физически не могли столкнуться с
  проблемой, если разработка шла на аккаунтах, заведённых до миграции.
- **Периметр гейта задокументирован неточно** (CHANGELOG v8.24.1: «единственный из пяти
  финансовых роутеров» при фактических шести после этого патча) — косвенный симптом того же
  класса небрежности: описание в прозе не совпадает с кодом, и никто не сверял. Отдельная задача
  (ROADMAP §9.0, пункт C) — не путать с этим инцидентом, но тот же паттерн.

## Resolution

- **Митигация:** нет отдельной — воздействия на реальных пользователей не было (продукт не
  запущен публично).
- **Фикс (реализован в этой же сессии, v8.25.3):** рабочий минимум согласия — не полный
  L3-экран (сознательное решение владельца, чтобы не блокировать батч 2 длинной задачей):
  - `entities/consents/api/useConsents.ts` — хуки `useConsents`/`useGrantConsent`/
    `useWithdrawConsent` поверх уже существовавшего, но не использовавшегося SDK.
  - `entities/consents/ui/ConsentRequiredPanel.tsx` — вместо старой заглушки «проверьте
    соединение» на 403 гейта согласия, на всех четырёх списках (obligations/assets/goals/
    transactions): объяснение + кнопка «Дать согласие» здесь и сейчас.
  - `pages/profile/ProfilePage.tsx` — блок «Согласия»: статус (Дано/Не дано), дата выдачи,
    кнопка Дать/Отозвать с undo-тостом (тот же паттерн, что удаление обязательства/актива).
  - Design-critic и a11y-auditor прогнаны на новый код ДО сдачи (стандартная церемония) — нашли
    и починили 5 блокеров (дублирующийся акцент, отсутствие визуального признака у критичного
    статуса, отзыв согласия без danger-варианта/undo, молчаливый отказ мутаций, текст,
    противоречащий кнопке под ним) и 3 AA-нарушения (`disabled`+`aria-busy` роняли фокус в
    `<body>`, неудача мутации не объявлялась, успех менял содержимое без переноса фокуса).
- **Фикс процесса — НЕ сделан в этом батче, вынесен в Action items.**

## Lessons learned

- **Что сработало хорошо:** гипотеза была сформулирована по чтению кода ДО эмпирической
  проверки — точная (три независимых сигнала в коде указывали в одну сторону:
  `REQUIRED_AT_REGISTRATION`, периметр `_FIN`, неиспользуемый SDK-метод), эмпирика её
  подтвердила без сюрпризов. Это модель, а не совпадение: чтение кода даёт гипотезу, реальный
  прогон — доказательство; порознь каждое из двух было бы слабее.
- **Что сработало плохо:** находка пришла из ВНЕШНЕГО источника (владелец, по итогам разбора в
  отдельном чате) — не из процесса разработки самого батча, который построил затронутый код.
  Стандартная церемония (design-critic, a11y-auditor, ручная проверка в браузере) на трёх разных
  UI-батчах вехи 8 (включая тот, что прямо строил CRUD-формы) не поймала этот класс проблемы,
  потому что ни один из них не тестировал путь «пользователь с нуля».
- **Где повезло:** продукт не запущен публично — цена находки сейчас это время на фикс, а не
  испорченный первый опыт реальных пользователей и потерянное доверие к продукту, который
  обещает работать с их деньгами.

## Action items

- [ ] **Новый обязательный класс тестов — «полный эмпирический путь реального нового
  пользователя»** (прямое поручение владельца, зафиксировано этим пунктом и в ROADMAP): не мок
  отдельной функции, а реальный HTTP + реальный браузер (Playwright, как в этой сессии) с
  чистого состояния — регистрация → первое действие в каждой ключевой области продукта →
  проверка реального кода ответа/экрана, не предположения. Придумать и перечислить ВСЕ
  реалистичные сценарии (не только «согласие на финданные») — где ещё в продукте может быть
  разрыв между «задумано» и «доступно из UI с нуля». Список сценариев и сам блок тестов —
  отдельная задача, не входит в этот батч; см. `docs/ROADMAP.md` §9.0, пункт E (заведён этой
  же сессией).
- [ ] **Замысел, зафиксированный только в прозе CHANGELOG, должен становиться явным чекбоксом
  плана/ROADMAP в момент, когда он записывается**, не оставаться скрытым обязательством. Нет
  отдельного технического фикса для этого пункта — дисциплина, не код.
- [ ] Периметр гейта согласия (пять vs шесть роутеров) — отдельный разбор,
  ROADMAP §9.0 пункт C, не путать с этим инцидентом, но использовать тот же случай для
  калибровки: прежде чем писать «единственный из N», сверяться с кодом, не с памятью о
  прошлом патче.
- [x] Рабочий минимум UI согласия — реализован, v8.25.3 (см. Resolution выше).
