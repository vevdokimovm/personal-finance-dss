# INC-NULL-DEADLINE — «чеховское ружьё» под NOT NULL: три латентных дефекта на бессрочных целях

**Тип:** Post-mortem, near miss (выстрела в прод не было) · **Severity:** SEV3 (потенциально SEV2:
один из дефектов — гарантированный 500 на пользовательском эндпоинте) · **Найден:** 2026-07-12,
батч v6.5.0 при работе над ROADMAP §6.3 (nullable-дедлайн) · **Закрыт:** v6.5.0.
**Авторы:** вахта M. **Статус:** Final.

## Summary

Канон мат-модели допускает бессрочную цель (`deadline: null`), а колонка `goals.deadline` была
`NOT NULL`. Ограничение схемы работало **предохранителем**: пока NULL физически не мог попасть в
данные, три дефекта в коде-потребителе не проявлялись. Снятие `NOT NULL` (плановая задача §6.3)
одновременно снимало предохранитель — и все три выстрелили бы сразу. Дефекты найдены и закрыты в
том же батче, до пользователя ничего не дошло. Один из них (D3) **уже стрелял** — в демо-контуре,
тихо, искажая объяснение плана.

## Impact

- **Прод:** 0. Ни один дефект не достиг пользователя: два были заперты схемой, третий жил только
  в демо-витрине.
- **Что было бы после миграции без фикса:** `/api/spending-advice` → `HTTP 500` у **любого**
  пользователя, у которого есть хотя бы одна бессрочная цель и положительная экономия (D1);
  порядок списка целей, расходящийся между локалкой и продом (D2).
- **Что уже происходило:** в разборе плана бессрочная цель показывалась как «до дедлайна ~12 мес»
  (D3) — ложь в объяснении при численно корректном расчёте.

## Detection

Не алертом и не тестом — **приёмом вахты по чек-листу задачи**. §6.3 требовал «миграция + матрица
SQLite/PG + тесты»; вместо правки одной колонки был выполнен обход **всех потребителей** колонки
(`grep deadline` по `app/`, а не по модели). Обход и вскрыл D1–D3. Существующий suite (1078 fast)
не поймал бы ни одного: тесты гоняют цели **с** дедлайном, а на матрице SQLite порядок NULL
«правильный» случайно.

## Root cause

**Корень:** `NOT NULL` использовался как источник истины о домене, при том что канон уже допускал
бессрочные цели. Код-потребитель писался под неявное «дедлайн есть всегда», и это допущение нигде
не было выражено — ни типом, ни тестом. Ограничение БД молча его подпирало.

Пять «почему»:

1. Почему упал бы `/spending-advice`? → `round(None, 1)` и сортировка `float` против `None`.
2. Почему туда пришёл `None`? → колонка стала nullable.
3. Почему код не был к этому готов? → писался, когда дедлайн был обязателен.
4. Почему рассинхрон не заметили? → канон (бессрочные цели можно) и схема (`NOT NULL`) — разные
   артефакты, между ними не было исполняемой сверки.
5. Почему не было сверки? → инварианты стенда проверяют **математику** модели, а не соответствие
   **схемы БД** канону. Это дыра в гейтах, а не невнимательность.

## Дефекты

### D1 — CRASH: `/spending-advice` падает на бессрочной цели (был бы SEV2)

`app/core/spending_advice.py::analyze_goal_impact`:

- `months_to_deadline=round(g.months_to_deadline, 1)` → `TypeError: type NoneType doesn't define
  __round__ method`;
- `impacts.sort(key=lambda i: (-priority, i.months_to_deadline))` → `TypeError: '<' not supported
  between instances of 'float' and 'NoneType'`.

Детерминированный 500, не флаки. Сработал бы у первого же пользователя с бессрочной целью.

**Фикс:** `months_to_deadline: float | None` в `GoalRecord`/`GoalImpact`; `on_track` для цели без
срока = «есть темп пополнения» (успевать некуда — отставания не бывает); в сортировке бессрочные
уходят в конец через `float("inf")`.

### D2 — SILENT DIVERGENCE: порядок целей расходится между SQLite и PostgreSQL

`app/database/crud.py::get_goals` сортировал `ORDER BY goals.deadline ASC`. Стандарт SQL не
фиксирует место NULL, и СУБД решают по-разному. Замер (тот же набор строк, обе СУБД):

```
SQLite      ORDER BY deadline ASC            -> ['бессрочная', 'срочная', 'дальняя']
PostgreSQL  ORDER BY deadline ASC            -> ['срочная', 'дальняя', 'бессрочная']
SQLite      ORDER BY deadline ASC NULLS LAST -> ['срочная', 'дальняя', 'бессрочная']
PostgreSQL  ORDER BY deadline ASC NULLS LAST -> ['срочная', 'дальняя', 'бессрочная']
```

То есть локальная разработка (SQLite) показывала бы бессрочные цели **первыми**, прод
(PostgreSQL) — **последними**. Класс дефекта тот же, что в `postgres_incident_postmortem.md`:
SQLite молча прощает то, на чём прод ведёт себя иначе.

**Фикс:** порядок задан явно — `Goal.deadline.asc().nullslast()`; тест сортировки гоняется на
обеих СУБД (матрица), проверено локально на PostgreSQL 16.

### D3 — EXPLAINABILITY LIE: бессрочная цель объяснялась как «срок 12 месяцев» (уже стреляло)

`app/core/goals_priority.py::_months_left` возвращал защитный фолбэк `12.0` на любое
нераспознанное значение, включая `None`. Численно это случайно совпало с правильной семантикой
(`u_s = max(1, 12/12) = 1.0` — минимальная срочность, ровно то, что нужно бессрочной цели), но:

- в разбивке `goal_breakdown` наружу уходило `months_left: 12.0` — UI объяснял бессрочную цель как
  «до дедлайна ~12 мес»;
- путь к `None` уже существовал: демо-роут строит цели из `months_left: int | None`
  (`routes_demo.py`) — то есть дефект был **достижим и работал** в витрине, тихо.

Это прямое попадание в приоритет продукта (объяснимость — ответ на UT-001 «чёрный ящик, нечего
проверить»): цифра в объяснении не соответствовала данным.

**Фикс:** семантика бессрочной цели задана явно — `months_left_or_none` (None = срока нет) и
`urgency_of` (бессрочная → `u_s = 1.0` отдельным правилом, а не побочным эффектом фолбэка).
Фолбэк `12.0` оставлен только для действительно битого значения. Канон дополнен: §11.2
`math_model_v3_2_0.md`.

## Contributing factors

- **Костыль в демо маскировал проблему.** Портрет «Наталья» имел цель с дедлайном «сегодня + 3650
  дней», а в описании портрета значилось «бессрочная цель». Витрина и данные разошлись, и это
  выглядело как норма. Костыль снят (`deadline=None`).
- **Защита была частичной и потому убаюкивала.** `notifications.goals_near_deadline` и
  `surplus.py` **уже** проверяли `deadline is not None`, `instrument_for_horizon` принимал
  `float | None`. То есть None ожидали в трёх местах из шести — рассинхрон выглядел как «всё
  учтено».

## Resolution

Миграция `0029_goal_deadline_nullable` (batch-режим — SQLite не умеет `ALTER COLUMN`), модель,
схемы (внутренний API и B2B `GoalDTO`), CRUD, ядро, spending-advice, UI (поле необязательно,
рендер «бессрочная»), демо. Новый файл `tests/test_goals_open_ended.py` — 14 тестов, покрывают все
три дефекта, гоняются на SQLite и PostgreSQL. Ревизионный гейт: пин миграций 28 → 29.

## Lessons learned

- **Что сработало:** задача §6.3 была сформулирована как «миграция + матрица + тесты», а не
  «сделать колонку nullable». Формулировка заставила обойти потребителей — этим и вскрылось.
- **Где повезло:** D1 нашёлся при написании теста, а не в проде. Стоимость находки — минуты;
  стоимость выстрела — 500 у живого пользователя на финансовом продукте.
- **Главный урок (правило).** Ограничение схемы (`NOT NULL`, `CHECK`, FK) — это **предохранитель
  на коде**, а не описание домена. Снимая ограничение, снимаешь предохранитель: сначала обходишь
  **всех потребителей колонки** (`grep` по имени колонки во всём `app/`, не по модели), потом
  меняешь схему. Ослабление ограничения — всегда операция по коду, а не по БД.
- **Дыра в гейтах:** канон и схема БД не сверяются автоматически. Инварианты стенда (I1–I14)
  проверяют математику, ревизионный гейт — ссылки и счётчики; «канон допускает X, а схема
  запрещает X» не ловит никто. Кандидат в ревизию: ось «канон ↔ схема БД».
