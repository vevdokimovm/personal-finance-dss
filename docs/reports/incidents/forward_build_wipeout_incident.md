# INC — Forward-build wipeout: репозиторий стёрт до огрызка при публикации

- **ID:** INC-FWD-BUILD-WIPEOUT
- **Дата:** 2026-07-05
- **Severity:** CRITICAL (потеря целостности main на GitHub; коммиты/теги/релизы v5.20.0–v5.23.0 — огрызки)
- **Статус:** причина найдена и доказана; исправление и восстановление выданы
- **Данные:** НЕ потеряны — все деревья в архивах целы, восстановление полное

## TL;DR

Публикатор `finpilot_publish.sh` при forward-build искал корень распакованного архива
через `find "$WORK" -maxdepth 1 -mindepth 1 -type d | head -1`. Архивы v5.20.0+ были
упакованы **без обёртки** `finpilot_vX_Y_Z_intl/` — содержимое лежало прямо в корне zip
(11 папок: app/, docs/, deploy/ …). `head -1` выхватывал **первую попавшуюся папку**
(`deploy/`), а `rsync -a --delete "$src/" "$REPO/"` делал репозиторий равным ей — из 623
файлов оставалось 6 (deploy/systemd). Каждый пуш начиная с v5.20.0 стирал проект.
v5.19.0 уцелел случайно: у него в корне zip была ровно одна папка-обёртка, и `head -1`
взял именно её.

## Симптом

На GitHub коммиты v5.20.0 и далее содержат почти пустое дерево (только `deploy/systemd`,
6 файлов). Линейка релизов визуально «поехала». Владелец: «какая-то херня задушилась».
При этом сами архивы в Downloads выглядят нормальными по размеру (~8.9 МБ).

## Диагностика (три уровня, эмпирика)

1. **Структура архивов.** Распаковка всех шести: v5.19.0 — 620 файлов с обёрткой
   `finpilot_v5_19_0/`; v5.20.0–v5.23.0 — 623/623/624/630/634 файла **без обёртки**,
   содержимое в корне zip (11 папок верхнего уровня). Версии в `app/config.py` совпадают
   с именами. **Деревья целые** — потери данных нет.
2. **Код публикатора.** Строки поиска корня: `src="$WORK/finpilot_v${under}_intl"` →
   при отсутствии обёртки fallback `find … | head -1` → далее `rsync -a --delete`.
   Ожидается обёртка; её нет — fallback берёт произвольную папку.
3. **Воспроизведение.** Прогон логики на реальном архиве v5.20.0: обёртка не найдена →
   `head -1` вернул `deploy/` → внутри `systemd/` (6 файлов) → rsync --delete оставил бы
   в репо ровно 6 файлов. **Точное совпадение с тем, что на гите.**

## Root cause

Двойная причина:
- **Расхождение формата упаковки.** Архивы v5.20.0+ паковались как `zip . ` (содержимое без
  корневой папки), тогда как публикатор ждёт обёртку `finpilot_vX_Y_Z_intl/`. Формат разошёлся
  между тем, что производит упаковка, и тем, что ожидает потребитель.
- **Небезопасный fallback потребителя.** `head -1` от списка папок + `rsync --delete` = мина:
  при неожиданной структуре архива команда молча делает репозиторий равным случайной подпапке
  вместо fail-loud. Нет sanity-check, что выбранный корень вообще похож на репозиторий.

## Механизм (пошагово)

1. `unzip finpilot_v5_20_0_intl.zip -d $WORK` → в `$WORK` лежат app/, docs/, deploy/ … (без обёртки).
2. `$WORK/finpilot_v5_20_0_intl` не существует → fallback.
3. `find $WORK -maxdepth 1 -mindepth 1 -type d | head -1` → `$WORK/deploy`.
4. `rsync -a --delete "$WORK/deploy/" "$REPO/"` → содержимое репо = содержимое deploy = `systemd/`.
5. `git add -A && git commit -m "vX"` → коммит фиксирует удаление всего проекта.
6. Повтор на каждой следующей версии.

## Масштаб

- Затронуто на GitHub: коммиты/теги/релизы **v5.20.0, v5.21.0, v5.22.0, v5.22.1, v5.23.0** (огрызки).
- Последнее целое состояние main: **v5.19.0** (620 файлов).
- Локальные архивы всех версий — целые (потери исходников нет).

## Устранение (выдано)

1. **Публикатор укреплён** (`finpilot_publish_private.sh`):
   - Надёжный поиск корня: (1) обёртка `finpilot_vX_Y_Z_intl/`; (2) содержимое прямо в корне
     архива; (3) единственная папка верхнего уровня. Корень принимается, только если содержит
     маркеры репо (`app/` + `CHANGELOG.md`).
   - **Fail-loud**: если корень не похож на репозиторий — версия пропускается, репо **не тронут**
     (никакого rsync --delete по случайной папке).
   - Сохранён прошлый фикс: детект рабочего python (обход заглушки Xcode CLT).
2. **Архивы переупакованы** с обёрткой `finpilot_vX_Y_Z_intl/` (double safety) — содержимое
   деревьев байт-в-байт прежнее, изменена только внешняя структура.
3. **Восстановитель** (`finpilot_restore.sh`): диагностирует битые теги (нет `app/config.py`),
   откатывает main на последний целый тег, сносит битые теги+релизы (локально + GitHub),
   запускает пофикшенный публикатор для чистого rebuild из целых архивов.

## Профилактика (чтобы больше НИКОГДА)

- **PIT: единый формат архива.** Все архивы паковать с обёрткой `finpilot_vX_Y_Z_intl/`. Имя
  обёртки = имя zip без расширения. Потребитель ищет её напрямую.
- **PIT: деструктив только после sanity-check.** Любой `rsync --delete` / массовое удаление —
  только если целевой источник прошёл проверку маркеров (здесь: `app/` + `CHANGELOG.md`).
  Иначе fail-loud, ничего не трогать. Никогда не выводить «корень» через `head -1` от списка.
- **PIT: проверять дерево тега после публикации.** После пуша — `git ls-tree` целевого тега на
  наличие `app/config.py`; расхождение = стоп.

## Личное

Корень на мне: архивы паковались без обёртки, разойдясь с форматом, который ждёт публикатор.
Хрупкий fallback превратил это в стирание репо. Оба конца закрыты: и упаковка приведена к
единому формату, и потребитель больше физически не может снести репозиторий по кривому корню.
