# Инцидент: гейты в CI были красными почти два месяца, и вахта трижды объявила их зелёными

**Тип:** инцидент · **Дата разбора:** 24.09.2026 · **Версии починки:** v9.13.4 … v9.13.11
**Нашёл:** владелец, трижды, последний раз — скриншотом списка проверок
**Классы:** ложное «сделано» · проверка не того объекта · дефект, невидимый локально

---

## 1. Что произошло, одной строкой

**Прогон CI по тегу падал на каждом релизе с 29.07.2026** — это видно в истории прогонов
без исключений. Вахта за сутки **трижды** заявила, что CI зелёный, и каждый раз это
оказывалось неправдой по новой причине.

---

## 2. Хронология заявлений и опровержений

| Когда | Что заявила вахта | Чем опровергнуто |
|---|---|---|
| v9.13.3 | «блокирующие джобы CI зелёные» | локальный прогон ≠ CI: 26 красных на раннере |
| v9.13.9 | «все блокирующие джобы зелёные, подтверждено прогоном» | смотрела прогон по **ветке**, где «Полный» пропускается |
| — | — | владелец прислал скриншот: 2 failing, 3 in progress |

🔴 **Общий знаменатель всех трёх: вахта проверяла не тот объект.** Сначала не ту среду
(ноутбук вместо раннера), потом не тот прогон (ветка вместо тега). Оба раза вывод звучал
одинаково уверенно.

---

## 3. Измерение: сколько это длилось

Команда: `gh run list --limit 200 --json headBranch,conclusion,createdAt`, отбор прогонов,
где `headBranch` начинается с `v` (то есть запусков по тегу).

| | |
|---|---|
| самый старый прогон по тегу в истории | **29.07.2026** |
| прогонов по тегу с вердиктом `failure` подряд | **все, без единого зелёного** |
| период | **29.07.2026 → 24.09.2026, почти два месяца** |
| чем падало до сегодня | шаг «Мультибраузерные E2E» в джобе «Полный» |
| чем стало падать сегодня | шаг «Установка браузеров» — новая, внешняя причина |

🔴 **Владелец назвал это сам, дословно: «это уже месяц не могло решиться до того как мы
делали исследования».** Замер подтверждает и уточняет: не месяц, а почти два.

---

## 4. Три независимые причины, найденные при разборе

### 4.1. Эталон скриншота не разделён по браузерам — главная и самая долгая

`tests/full/test_visual_regression.py` складывал эталон в файл `{страница}__{тема}.png`,
**без имени браузера**. Тир `full` гоняет chromium, firefox и webkit по очереди:

1. chromium приходит первым, эталона нет → создаёт и **пропускается**;
2. firefox и webkit сравнивают **свой** рендер с **чужим** эталоном;
3. рендер шрифтов и высота полной страницы у движков разные → **различий 100 %**,
   при пороге 2 % — падение.

Отсюда ровно **28 падений из 72 параметров** в каждом прогоне по тегу.

🔴 **Почему это не ловилось локально:** в песочнице гоняется один chromium, и механизм
отрабатывает штатно — «создал эталон → следующий прогон совпал». То есть тест был зелёным
у любого, кто проверял его на своей машине, и красным всегда, где браузеров больше одного.

**Починка (v9.13.11):** имя эталона содержит браузер —
`{страница}__{тема}__{браузер}.png`. Проверено двумя проходами chromium: первый создаёт
эталоны с новым именем, второй сравнивает — 4/4 зелёных.

### 4.2. Тот же тест ставил тему ключом снесённой Jinja-версии

Там же: `localStorage.setItem('finpilot-theme', ...)`. Продукт с v8.45.0 читает `fp-theme`
в формате Zustand persist. Значит «тёмный» снимок снимался **в светлой теме**, и половина
покрытия по темам была фикцией.

🔴 **Этот же дефект в соседнем файле починили ещё в v8.45.0** (`test_a11y_axe.py`,
там он прямо описан в комментарии). В визуальной регрессии он дожил до сегодня — потому
что файл не входит в обычный прогон и падал по другой, более громкой причине (§4.1),
которая его маскировала.

### 4.3. Сегодняшняя внешняя причина: apt-репозиторий Microsoft отдаёт 403

`playwright install --with-deps` зовёт `apt-get update`; образ раннера `ubuntu-24.04`
несёт репозиторий `packages.microsoft.com`, который 24.09.2026 начал отвечать
`403 Forbidden` («The repository … is no longer signed») → `apt-get update` ненулевой →
«Failed to install browsers», код 100 → джоба красная, все её шаги пропущены за 42 секунды.

К нашему коду отношения не имеет. **Починка (v9.13.10):** чужой источник и его ключ
снимаются перед установкой, во всех трёх местах, где ставятся браузеры.

## 5. Почему красное прожило два месяца, хотя было видно

Три механизма, каждый сам по себе безобиден:

1. **Джоба «Полный» не запускается на ветке.** Повседневная работа идёт в `main`,
   там её нет вовсе — красное появляется только в момент выпуска.
2. **Красное в момент выпуска выглядит как часть выпуска.** Тег ставится последним
   действием батча; к этому моменту вахта уже отчиталась и переключилась.
3. 🔴 **Рядом всегда стоял ещё один красный крестик — `pylint` с `continue-on-error`.**
   Индикатор, который всегда в одном положении, перестаёт быть индикатором: на его фоне
   настоящее красное неотличимо от привычного. Это и есть цена «информационной» джобы.

**Починка механизма (v9.13.10):** `pylint` переведён с «информационно» на **храповик
оценки** — `--fail-under=9.6` держит достигнутые 9.61/10 и падает при регрессе. Красный
крестик теперь означает регресс, а не фон.

---

## 6. Что из этого следует — правила

> **П-1. «Зелено локально» не является утверждением о CI.** Это разные среды: на раннере
> нет `~/repos/base-repo`, нет `pdftotext` и `tesseract`, не собран фронт в части джоб,
> браузеров три вместо одного. Вывод о CI делается **только по прогону CI**.

> **П-2. Вердикт снимается с прогона ПО ТЕГУ и по ВСЕМ джобам.** Прогон по ветке —
> подмножество: «Полный» там пропускается. Формулировка «все блокирующие зелёные»
> обязана называть, какой прогон проверялся.

> **П-3. Постоянно красная «информационная» джоба запрещена.** Либо порог-храповик,
> либо джобы нет. Вечный крестик маскирует настоящее красное — измерено этим инцидентом:
> два месяца.

> **П-4. Тест, который на одной конфигурации создаёт эталон, а на другой сравнивает,
> обязан разделять эталоны по конфигурации.** Браузер, ОС, разрешение — всё, что меняет
> рендер, входит в имя файла.

## 7. Контрмера уровня «машина», а не «правило»

По шкале эскалации `docs/reports/recurrence_ledger.md` §1 этот класс («сделано объявлено
без проверки») повторился достаточно раз, чтобы прозы было недостаточно. Поэтому заведён
инструмент: **`python -m tools.ci_verdict`** — он сам находит прогон по последнему тегу,
печатает все джобы и выходит ненулевым, если хоть одна не `success` (кроме `skipped`).
Отчёт о зелёном CI теперь делается командой, а не памятью вахты.

---

## 8. Что осталось открытым

- вердикт по прогону тега **v9.13.11** на момент записи не получен — он и будет первым
  настоящим зелёным, если §4.1–4.3 закрыты полностью;
- эталоны скриншотов в CI создаются заново при первом прогоне после правки: **первый
  прогон по новой схеме пропустит визуальную регрессию** (эталонов с новым именем ещё нет),
  и только следующий начнёт реально сравнивать. Это ожидаемое поведение, но означает,
  что зелёный первого прогона слабее зелёного второго — и об этом надо помнить, объявляя
  победу.
