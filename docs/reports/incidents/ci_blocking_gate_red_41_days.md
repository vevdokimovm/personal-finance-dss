# Post-mortem: блокирующий гейт CI был красным 41 день подряд, 65 релизов не проверены (SEV2)

Авторы: сессия 2026-08-19 (по прямому запросу владельца — «изучи вопрос, как давно это было»).
Статус: Final.

## Summary

Блокирующий гейт CI (`preflight` + матрица `fast` sqlite/postgresql — unit+integration+property+
e2e-smoke, порог покрытия 90%) был красным на КАЖДОМ пуше в `main` и на КАЖДОМ теге релиза
непрерывно **41 день** (2026-07-09 → 2026-08-19), от `v5.25.0` до `v8.25.1` включительно —
**65 версий продукта** выпущено без единого зелёного прогона блокирующего гейта. Причина — в
обоих случаях один и тот же класс бага (регистро-чувствительность путей к `docs/glossary.md`),
дважды: сначала в одном направлении, затем (после неполного фикса) в другом. Всё это время
единственной защитой оставались локальные прогоны на macOS одной сессии за раз — тот же класс
машины, на которой баг структурно невидим.

## Impact

- **Длительность:** 41 день (2026-07-09T04:59Z — 2026-08-19, момент этого разбора).
- **Затронуто релизов:** **65** тегированных версий (`v5.25.0` … `v8.25.1`; посчитано по
  `gh api repos/.../actions/runs`, уникальные `vX.Y.Z` в `display_title` прогонов на `main` в
  этом окне — точная цифра, не оценка).
- **Что конкретно не проверялось:** блокирующий гейт падал на шаге `revision_check`
  («Revision gate») — ДО запуска `pytest` вообще. Это значит: не просто «PostgreSQL-матрица не
  проверена» — **весь unit+integration+property набор не запускался в CI ни разу за 65 версий**,
  ни на SQLite, ни на PostgreSQL. Единственная проверка, которая реально происходила, — локальные
  прогоны той сессии, что делала конкретный батч (как правило SQLite, macOS).
- **Деньги/SLA:** продукт не в проде (`docs/public_mirror_state.md`), прямого влияния на
  пользователей нет. Влияние — на достоверность процесса: правило 1 CLAUDE.md («TDD… ничего не
  отдавать до зелёного») формально соблюдалось (локальный `preflight`/pytest были зелёными), но
  расчёт на CI как на независимую вторую проверку не работал молча весь этот период.

## Timeline (UTC)

- **2026-07-09T04:59:30Z** — первый красный прогон в этой серии: `v5.25.0`, джоба
  «Быстрый (sqlite)» падает на шаге `revision_check` — `[FAIL (4)] Битые ссылки`:
  `docs/onboarding.md`, `docs/ROADMAP.md` (×2), `docs/WATCHLOG.md` → все ссылались на
  **строчный** `docs/glossary.md`, реальный файл на диске в тот момент, судя по всему, был
  недоступен под этим именем (обратное направление того же класса бага, что будет в августе).
  На этот момент джобы `preflight` в CI ещё не существовало — гейт `revision_check` вызывался
  прямо внутри джобы `fast`.
- **2026-07-09 → 2026-08-07** (29 дней) — гейт красный на каждом пуше без исключения (за
  вычетом четырёх «success» записей 07-20/08-03/08-10/08-17 — это **не** реальные прогоны кода:
  еженедельный `schedule`-триггер (Пн 03:00 UTC) запускает ТОЛЬКО джобу `deep`, у которой
  `preflight`/`fast`/`lint` даже не входят в условие запуска — «success» здесь означает
  «мутационный тест технически завершился», не «код проверен»; ложный сигнал благополучия
  для любого, кто смотрел бы на список прогонов бегло).
- **2026-08-07 (v8.4.1)** — предпринята попытка фикса: «Дубль глоссария по регистру» —
  ссылки на заглавный `GLOSSARY.md` приведены к строчному `glossary.md` в `README.md`,
  `docs/README.md` (×3), `docs/WATCHLOG.md`. Фикс НЕПОЛНЫЙ: в самом тексте `WATCHLOG.md`,
  описывающем инцидент («заглавный `GLOSSARY.md` и строчный `docs/glossary.md`...»), осталось
  историческое упоминание пути `docs/GLOSSARY.md` заглавными буквами — на macOS `Path.exists()`
  регистронезависим, ссылка казалась рабочей локально; на Linux CI — снова битая ссылка, теперь
  в обратном направлении относительно 07-09.
- **2026-08-07 → 2026-08-19** (12 дней) — гейт остаётся красным, симптом идентичен
  (`revision_check` → «битая ссылка -> docs/GLOSSARY.md», `docs/WATCHLOG.md:1012`), фикс
  v8.4.1 не восстановил зелёный CI, хотя выглядел как решение проблемы в CHANGELOG.
- **2026-08-19, ~08:00Z** — владелец сообщает о симптоме («preflight падает на Linux, не
  воспроизводится на macOS»), приводит точную гипотезу (регистронезависимая APFS).
- **2026-08-19T08:16Z (v8.25.1)** — фикс: `_exists_with_matching_case()` в `revision_check.py`
  сверяет каждый сегмент пути через `os.listdir()` вместо `Path.exists()` — регистр теперь
  проверяется одинаково на macOS и Linux; сам текст-первоисточник в `WATCHLOG.md` переписан без
  битого пути. `preflight` в CI впервые за 65 версий проходит **success**.
- **2026-08-19, обнаружение глубины проблемы** — по прямому вопросу владельца («как давно это
  было, если 50+ версий») — полный разбор истории 274 прогонов CI через `gh api`, точная цифра
  65 релизов и 41 день подтверждены документально (этот отчёт).

## Detection

Обнаружено **владельцем**, не мониторингом и не процессом проекта — он лично заметил, что
`preflight` красный на Linux и попросил проверить. Ни один из инструментов проекта (preflight,
WATCHLOG-ритуал, deploy.sh) не поднял тревогу за 41 день — это отдельный, самый важный пункт
находок (см. Contributing factors и Action items).

## Root cause

**Технический корень (симптом, не причина процесса):** `LinkChecker` в
`tools/revision/revision_check.py` использовал `(root / ref).exists()` для проверки ссылок на
файлы — на регистронезависимой файловой системе (APFS, macOS; весь проект разрабатывается на
четырёх аккаунтах Claude, все на macOS, `docs/WATCHLOG.md` шапка) это молча резолвит
`docs/GLOSSARY.md` в реально лежащий `docs/glossary.md` и не видит рассинхрона. На Linux
(регистрочувствительная ФС — GitHub Actions раннеры) та же ссылка бьётся. Технически починено в
v8.25.1 — см. CHANGELOG.

**Процессный корень (5 Whys):**
1. Почему гейт был красным 41 день? — Потому что баг регистра путей ловился локальным
   `preflight` иначе (точнее — не ловился), чем в CI.
2. Почему разница между локальным и CI результатом не была замечена сразу? — Потому что после
   каждого пуша/тега никто не проверял статус CI как часть ритуала сдачи батча.
3. Почему проверка статуса CI не входит в ритуал? — Церемония батча (CLAUDE.md правило 4:
   `VERSION`/`app/config.py`/`CHANGELOG.md`/`WATCHLOG.md`/`ROADMAP.md`) требует **локального**
   `python -m tools.preflight` перед сдачей, но нигде не требует свериться с реальным статусом
   прогона на GitHub — предполагается (неявно), что «локально зелёный» ⇒ «CI зелёный».
4. Почему это предположение оказалось неверным именно здесь? — Потому что класс бага
   (регистро-чувствительность файловой системы) структурно невидим на платформе, где ведётся
   вся разработка (macOS), и виден только на платформе, где реально гоняется CI (Linux) — то
   есть развели ОДНУ вещь (проверку ссылок) на ДВЕ платформы с разным поведением и не сверяли их
   результат друг с другом.
5. Почему никто не заметил рассинхрон за 41 день, ведь `gh run list` показывал failure? —
   `deploy.sh` пушит версии в GitHub автоматически, никак не завязан на статус CI (пушит
   независимо от результата предыдущего прогона); ни WATCHLOG, ни ROADMAP, ни один хук в
   `.claude/hooks/` не проверяет актуальный статус GitHub Actions. Единственный способ узнать —
   зайти на GitHub и посмотреть список прогонов вручную, чего никто не делал 41 день.

**Корень процесса:** в системе НЕТ ни одной точки, которая после пуша версии сверяется с
реальным результатом CI и поднимает тревогу при красном. Локальный `preflight` и CI считались
эквивалентными без механизма, который бы эту эквивалентность подтверждал или опровергал.

## Contributing factors

- **Вся разработка — на macOS** (4 аккаунта Claude, одна и та же ОС) — единственная платформа,
  где ведётся работа, структурно не видит именно этот класс багов (регистр путей). Если бы хоть
  одна сессия регулярно работала на Linux/в Docker локально, баг проявился бы раньше.
- **`deploy.sh` не проверяет статус CI перед пушем** — версии уходят на GitHub автоматически по
  готовности локального архива, независимо от того, зелёный ли предыдущий прогон.
- **Ложное благополучие от еженедельного `schedule`-прогона.** Четыре записи «success» в истории
  CI за этот период — не связаны с реальной проверкой кода (см. Timeline), но при беглом
  просмотре `gh run list` создают впечатление «иногда всё же зелёное», что могло притупить
  бдительность, если бы кто-то и посмотрел на список прогонов мельком, не разбирая, какая именно
  джоба отработала.
- **Джоба `preflight` появилась в CI только в v7.4.0 (2026-07-30)** — то есть 21 из 41 дня
  красный статус вообще не был выделен в отдельный «быстрый провал», проблема пряталась внутри
  джобы `fast` наравне с остальными шагами — сложнее было заметить именно этот класс проблемы
  на фоне остальных потенциальных причин красного статуса.
- **Неполный фикс v8.4.1 остался незамеченным именно потому, что фон уже был красным.** Если бы
  CI был зелёным до v8.4.1, новая красная строка после него бросилась бы в глаза немедленно
  («было зелено, стало красно — что сломал коммит?»). На фоне «и так красное 29 дней» новая
  красная строка неотличима от старой — эффект «сигнал тревоги, который никто не слышит,
  потому что он и так всегда орёт» (alert fatigue в чистом виде, только для CI, не пейджера).
- **Ни у одной джобы `ci.yml` не было `timeout-minutes`** (найдено и починено в этой же сессии,
  отдельный разбор `docs/reports/investigations/ci_full_pg_matrix_hang_investigation.md`) —
  косвенный симптом того же самого пренебрежения обратной связью от CI: если бы кто-то регулярно
  ждал/смотрел результаты прогонов, отсутствие таймаута на зависающих шагах обнаружилось бы
  гораздо раньше.

## Resolution

- **Митигация:** нет отдельной — красный статус не блокировал никакую реальную поставку
  (продукт не в проде), только скрывал недостоверность заявления «CI подтверждает батч».
- **Фикс корня (технический), v8.25.1:** `_exists_with_matching_case()` вместо `Path.exists()`
  в `LinkChecker` — регистр путей проверяется одинаково на macOS и Linux. Регрессионный тест
  `tests/test_repo_revision.py::test_link_checker_catches_case_mismatch_even_on_case_insensitive_fs`
  (red→green, TDD).
- **Фикс сопутствующего (CI-инфраструктура), v8.25.2:** `timeout-minutes` на всех шести джобах
  `ci.yml`; здоровый health-check Postgres-сервиса; убран декоративный `|| true` у locust-шага
  (детали — CHANGELOG [8.25.2], `docs/reports/investigations/ci_full_pg_matrix_hang_investigation.md`).
- **Фикс процесса — НЕ сделан в этом батче, вынесен в Action items ниже** (это единственное, что
  реально закрывает КЛАСС проблемы «локально зелёно ≠ CI зелёно остаётся незамеченным»,
  технические фиксы выше закрывают только этот конкретный случай).

## Lessons learned

- **Что сработало хорошо:** когда вопрос был задан прямо («как давно?»), ответ нашёлся быстро и
  точно — вся история сохранена в GitHub Actions API, 274 прогона, ничего не потеряно. Разбор
  занял чуть больше десятка вызовов `gh api`, не часы археологии.
- **Что сработало плохо:** 41 день — очень много для гейта, который называется «блокирующий».
  Название подразумевает, что он ЧТО-ТО блокирует; по факту он не блокировал ничего, потому что
  никто не смотрел на его результат перед тем, как продолжать работу.
- **Где повезло:** реальных регрессий в продуктовом коде, которые прошли бы мимо CI за эти 65
  версий, не обнаружено (насколько можно судить по тому, что джоба «Быстрые тесты + покрытие»
  на PostgreSQL 2026-08-19 прошла чисто на всём накопленном коде v8.20-v8.25.1 сразу после
  починки — если бы там было массовое расхождение SQLite/PostgreSQL, оно всплыло бы здесь).
  Это везение, не заслуга процесса — гарантий на будущее оно не даёт.

## Action items

- [ ] **Добавить проверку статуса CI в церемонию сдачи батча** (CLAUDE.md правило 4 /
  `docs/WATCHLOG.md`) — после пуша тега сверяться с `gh run list`/`gh run view`, что реальный
  (не `schedule`) прогон на этой версии зелёный, ПРЕЖДЕ чем считать батч закрытым. Без этого
  пункта технический фикс в v8.25.1 гарантирует только «этот конкретный баг не повторится», не
  «следующий класс расхождения macOS/Linux будет замечен быстрее, чем через 41 день».
- [ ] **`deploy.sh` — рассмотреть проверку статуса предыдущего CI-прогона перед пушем новой
  версии** (хотя бы предупреждение, не обязательно жёсткий блок — решение по механике за
  владельцем, это не код этого репозитория).
- [ ] **Не полагаться на список прогонов `gh run list` бегло** — при любой сверке статуса CI
  проверять, какая именно джоба отработала (`schedule`-прогоны гоняют только `deep`, не
  подтверждают ничего про `fast`/`preflight`) — задокументировано этим разбором, канал для
  будущих сессий.
- [x] Технический фикс регистро-чувствительности — v8.25.1 (закрыт).
- [x] `timeout-minutes` + health-check + декоративный `|| true` — v8.25.2 (закрыт).
