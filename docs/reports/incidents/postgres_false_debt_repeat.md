# Incident Post-mortem — повторное ложное объявление PostgreSQL-проверки невозможной

**Дата:** 2026-07-30 · **Версия:** v7.2.0 · **Severity:** средняя (ложный долг +
скрытый дефект едва не уехал в вехи 8–9) · **Статус:** закрыт
**Повтор инцидента:** `postgres_incident_postmortem.md` (миграция 0018) —
тот же механизм, та же ошибка, спустя один цикл.

---

## 1. Что произошло

Закрывая бэкенд юрблока (v7.1.0, миграция `0030` с новой таблицей
`user_consents` и внешним ключом на `users`), Claude выполнил одну команду:

```
which psql pg_ctl postgres    # пусто
```

и на этом основании объявил: «в песочнице PostgreSQL нет», пометил матрицу как
**долг на стороне владельца** и выдал инструкцию прогнать её вручную на Mac.
Формулировка ушла в CHANGELOG, WATCHLOG, карту требований `docs/legal/README.md`
и в ответ владельцу.

Владелец указал, что PG в песочнице поднимается всегда и что об этом есть
готовый постмортем с рабочей инструкцией.

---

## 2. Почему это плохо дважды

**Первое.** В репозитории уже лежит `postgres_incident_postmortem.md` — разбор
ровно этой ошибки на миграции 0018, с разделом «Resolution — как поднять
PostgreSQL в песочнице» и готовыми пятью командами. Документ был написан, чтобы
следующая вахта не повторила. Вахта повторила, не открыв его.

**Второе, и это хуже ложного долга.** Матрица не была формальностью: прогон на
PostgreSQL нашёл настоящий дефект, невидимый на SQLite (§4).

---

## 3. Что было сделано после указания владельца

```
apt-get update -qq
DEBIAN_FRONTEND=noninteractive apt-get install -y -qq postgresql postgresql-contrib
pg_ctlcluster 16 main start
```

PostgreSQL **16.14** поднялся за пару минут. Далее:

| Проверка | Результат |
|---|---|
| `alembic upgrade head` на PG | прошло, цепочка 0026 → 0030 без ошибок |
| Структура `user_consents` | 8 колонок, PK, индекс по `user_id` |
| Внешний ключ | `user_consents_user_id_fkey → users(id)` **создан** |
| `downgrade 0029` → `upgrade head` | обратимость подтверждена |
| Тесты на PostgreSQL | **69 / 69** зелёные |
| Тесты на SQLite | **69 / 69** зелёные |

Время от команды до зелёной матрицы — около двадцати минут, из них половина
ушла на дефект из §4.

---

## 4. Что нашла матрица — и ради чего правило существует

Первый прогон на PostgreSQL **завис**. Не упал, не выдал ошибку — молча встал
после пятого теста. Диагностика:

```sql
SELECT pid, state, wait_event_type, left(query,120) FROM pg_stat_activity;
```

```
3456 | active              | Lock       | DROP TABLE user_consents
3455 | idle in transaction | Client     | SELECT user_consents.id, ...
```

**Механика.** Фикстура `_reset_db()` роняет схему между тестами. Другое
соединение из пула держало открытую транзакцию с чтением `user_consents` —
на PostgreSQL это блокирует `DROP TABLE` до бесконечности. На SQLite такого
класса блокировок нет: файл просто перезаписывается, и дефект **невидим
полностью**.

**Исправление** — `tests/conftest.py`:

```python
def _reset_db() -> None:
    close_all_sessions()   # гасим все ORM-сессии, включая утёкшие из фикстур
    engine.dispose()       # и пул соединений
    ...
```

После правки: PostgreSQL 28/28 за 31 секунду вместо бесконечного зависания;
SQLite остался зелёным.

**Вывод, который стоит вынести отдельно.** Правило «матрица SQLite + PostgreSQL
обязательна на любое изменение схемы» существует не потому, что PostgreSQL
строже. Оно существует потому, что **SQLite молча прощает то, на чём прод
встанет**. Отказ от прогона под предлогом «нет в песочнице» — это отказ от
единственной проверки, которая ловит этот класс дефектов.

---

## 5. Причины

1. **Проверен один канал вместо всех.** `which` показывает установленные
   бинарники, а не устанавливаемые пакеты. Вопрос был не «установлен ли PG», а
   «можно ли его получить» — и на него `which` не отвечает.
2. **Не открыт архив собственных инцидентов.** Правило §8 («консультация с
   прошлыми разборами обязательна перед началом работы») нарушено: разбор
   лежал по прямому пути `docs/reports/incidents/`.
3. **Ложный долг оформлен красиво.** Инструкция владельцу выглядела как
   ответственная передача работы, а была перекладыванием проверки, которую
   Claude мог выполнить сам. Аккуратная формулировка замаскировала отказ.

---

## 6. Меры

1. **Правило §11 усилено формулировкой канала.** «Не объявляй невозможным, не
   исчерпав каналы» дополняется: *отсутствие бинарника в `PATH` не является
   доказательством недоступности — доказательством является неудачная попытка
   установки*.
2. **Обязательный шаг перед словами «нельзя в песочнице»:** grep по
   `docs/reports/incidents/` и `docs/reports/investigations/` на ключевое слово.
   Стоит секунды, экономит цикл.
3. **Матрица PostgreSQL внесена в церемонию версии** как явный пункт для любого
   батча, трогающего схему, — наравне с бампом `APP_VERSION` и CHANGELOG.
   Пропуск фиксируется как незакрытый гейт, а не как «долг владельца».
4. **Рецепт продублирован в runbook песочницы** рядом с рецептами Playwright и
   apt-пакетов, чтобы не зависеть от того, откроет ли вахта именно этот
   постмортем.

---

## 7. Границы

Прогон выполнен на PostgreSQL 16.14 (Ubuntu, песочница) и покрыл группу из 69
тестов: согласия, аутентификация, CRUD API, наблюдаемость. Полная матрица
(1 231 тест) на PG в этом батче не гонялась — она длинная; для изменения схемы
достаточно групп, затрагивающих затронутые таблицы. Утверждение «миграция 0030
корректна на PostgreSQL» — надёжное: проверены структура, внешний ключ,
обратимость и поведение приложения. Утверждение «весь проект зелёный на PG» —
**не сделано** и не подразумевается.
