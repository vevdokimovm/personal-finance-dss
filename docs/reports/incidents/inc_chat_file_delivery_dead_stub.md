# INC-DELIVERY-STUB — «мёртвая заглушка»: файл выдан в чат, кнопка есть, скачивание падает

**Дата:** 2026-07-02 · **Статус:** ЗАКРЫТ (корень подтверждён: путь Tor Browser → file-CDN)
**Область:** канал доставки артефактов Claude (present_files → чат)

## Симптом

`present_files` отрабатывает штатно, в чате появляется карточка файла с кнопкой скачивания,
но скачивание стабильно падает с ошибкой. Внешне выглядит как «файл выдали, затем бекенд его
удалил/потерял, а заглушка в чате осталась». Повторная выдача тем же вызовом обычно решает.

## Хронология 2026-07-02 (три случая за день)

1. **Утро:** из трёх загруженных Василием файлов до песочницы доехал один (`банки_pdf.zip`) —
   зеркальная проблема канала «вверх».
2. **~12:30, v5.12.0:** чекпоинт выдан, у Василия карточки не появились вообще; повторный
   `present_files` тех же путей — доставилось.
3. **~17:30, v5.14.0:** карточки есть, скачивание падает ошибкой у обоих файлов (архив + вотчлог) —
   классическая «мёртвая заглушка».

## Гипотеза механизма

Платформенная: артефакт после выдачи получает ссылку в UI, но бэкенд-хранилище либо не завершило
аплоад, либо зачистило файл (GC/ретенция), а карточка-ссылка осталась. Не зависит от размера
(падали и 9.5 МБ zip, и 50 КБ md). Управлять этим из песочницы нельзя — только обходить.

## Диагноз (дополнено после третьего эпизода, ~20:30)

**Что проверяемо изнутри песочницы — проверено, чисто:** файлы в `/mnt/user-data/outputs/`
целы (unzip -t OK), sha256 зафиксированы, права штатные, после выдачи файлы не модифицируются.
Значит, отказ живёт **вне песочницы**: на пути «хранилище платформы → браузер владельца».

**Отягчающие факторы на стороне канала (корреляции, не доказательства):**
1. **Tor Browser** — весь трафик через exit-ноды: медленные/рвущиеся цепочки валят скачивание
   ~10 МБ; file-эндпоинты за WAF нередко режут Tor-выходы (симптом — мгновенный тост
   «Failed to download files»).
2. **Session-limit/suspend** — карточки, выданные до заморозки сессии, после неё могут
   ссылаться на мёртвый бэкенд-объект («заглушка»).
3. **Наш собственный вклад (исправлено):** первый вариант протокола предписывал «пересборку
   свежим файлом», и она была сделана **по тому же пути** (cp/mv поверх выданного) — это
   противоречит правилу «выданное не трогать» и могло инвалидировать привязку карточки.
   Протокол v2 ниже устраняет противоречие: выданный путь неприкасаем, ретрай — только под
   новым именем.

**Эпизод №4 (~22:00):** фейлят ОБЕ выдачи (v5.14.0 и свежая v5.15.0 под новым именем) уже и при
включённом VPN у владельца → клиентская вариативность почти исчерпана, канал признаётся мёртвым
до подтверждения. Активирован железный обход: **git-ветка из песочницы** (github.com из sandbox
доступен, проверено HTTP 200) — владелец даёт fine-grained PAT (Contents RW, только этот репо,
TTL 1 день), вахта пушит ветку `sync/vX.Y.Z`, владелец забирает `git fetch`, токен сразу revoke.

## Протокол-обход v2 (канонизирован как PIT-009)

1. Доставка считается **НЕПОДТВЕРЖДЁННОЙ**, пока владелец не скачал. Формулировки «архив у тебя» —
   запрещены; писать «выдан, подтверди скачивание».
2. Файлы в `/mnt/user-data/outputs/` **не удалять и не перезаписывать** до подтверждения — они
   нужны для мгновенной перевыдачи.
3. Ошибка/пропажа → **повторный `present_files` тех же путей** (каждый вызов = новый аплоад).
4. Повторный фейл → собрать копию **ПОД НОВЫМ ИМЕНЕМ** (суффикс `_r2`, `_r3` …) и выдать её;
   исходный выданный путь не трогать. Каждую выдачу сопровождать **sha256 в чате** — любая
   успешная закачка сверяема.
5. Хронический фейл в сессии → отдать критический минимум отдельно (WATCHLOG как .md — лёгкий и
   доезжает чаще) и зафиксировать в §0, чтобы следующая вахта перевыдала архив первым делом.

## Развязка (эпизод №5, 2026-07-02 поздний вечер) — корень подтверждён

Владелец открыл тот же чат в **Safari при том же VPN** — все карточки (полный `_r2`, слим,
вотчлог) скачались с первого раза; конфигурация больше не менялась. Эмпирика замыкается:
объекты на бэкенде живы, ломался **клиентский путь Tor Browser → file-CDN** (Tor Browser гонит
трафик через Tor-сеть даже при системном VPN; file-эндпоинты режут Tor-выходы). Эпизоды 1–4
объясняются тем же путём. **Правило владельцу: артефакты качать в обычном браузере + VPN;
Tor Browser для скачивания файлов не использовать.** Протокол v2 (sha256, неприкасаемые пути,
`_r2`-ретраи, git-ступень) остаётся штатной страховкой канала.

## Обход на стороне владельца (Tor)

Перед скачиванием: **новая цепочка Tor** для claude.ai (New Circuit for this Site / New Identity);
качать файлы **поштучно** кнопкой Download (не «Download all»); пробовать **сразу после выдачи**,
не спустя часы. Хронический фейл большого zip → запросить у вахты слим-архив без бинарных
ассетов (~1–2 МБ) — короче передача, меньше шанс обрыва цепочки.
