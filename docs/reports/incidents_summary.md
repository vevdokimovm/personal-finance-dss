# Реестр инцидентов FINPILOT

Краткие сводки по каждому **инциденту** — был дефект в продуктовом коде и/или влияние на
пользователя/систему. Расследования, где дефекта в коде НЕ оказалось (внешняя причина, артефакт
теста, недопонимание), — в отдельном парном реестре `docs/reports/investigations_summary.md`.

Полные разборы (post-mortem) лежат в `docs/reports/incidents/` (веха 5: репозиторий самодостаточен, отчёты версионируются с кодом). Формат разбора —
`docs/reports/incident_postmortem_guide.md`; шаблон карточки дефекта — `docs/reports/bug_report_template.md`. В каждой
записи — не только корень, но и **решение / шаги** (а если не закрыто — что опробовано и что дальше).

### CI-RED-41-DAYS — блокирующий гейт CI был красным 41 день, 65 релизов не проверены (SEV2)

- **Когда обнаружено:** 2026-08-19, по прямому вопросу владельца. **Период:** 2026-07-09 →
  2026-08-19 (41 день), `v5.25.0` … `v8.25.1` (65 тегированных версий, точная цифра из
  `gh api .../actions/runs`, 274 прогона разобраны).
- **Симптом:** `revision_check`/`preflight` падал на КАЖДОМ пуше/теге — регистро-чувствительность
  путей к `docs/glossary.md` (сначала ссылки строчные vs файл заглавный, после неполного фикса
  v8.4.1 — наоборот), невидимая на macOS (регистронезависимая APFS, вся разработка ведётся
  здесь), видимая только на Linux-раннере CI. Гейт падал ДО запуска `pytest` — весь
  unit+integration+property набор не выполнялся в CI ни разу за 65 версий, ни на SQLite, ни на
  PostgreSQL.
- **Корень (процессный):** ритуал сдачи батча требует локального `preflight`, но нигде не
  сверяется с реальным статусом GitHub Actions — «локально зелёно» считалось эквивалентом «CI
  зелёно» без механизма, который бы это подтверждал.
- **Решение:** технический фикс регистро-чувствительности — v8.25.1;
  `timeout-minutes`/health-check/декоративный гейт `full` — v8.25.2. Процессный фикс (сверка
  статуса CI как часть церемонии сдачи батча) — НЕ сделан, action item на будущее.
- **Полный разбор** — `docs/reports/incidents/ci_blocking_gate_red_41_days.md`.

### CONSENT-GATE-NO-UI — гейт согласия на финданные не имел UI, каждый новый пользователь упирался в тупик (SEV1, near miss)

- **Когда обнаружено:** 2026-08-19, владелец, по итогам разбора в отдельном чате («независимый
  эксперт»). **Окно риска:** 26 дней, `v7.5.0` (2026-07-30, гейт введён на бэкенде) →
  `v8.25.2` (момент фикса), 15+ версий, включая весь батч CRUD-паритета (v8.25.0).
- **Симптом:** `require_financial_consent` (шесть роутеров — transactions/obligations/goals/
  liquid_assets/budgets/telemetry) корректно возвращал 403 на любую попытку доступа без
  согласия. Замысел UI был явно зафиксирован в CHANGELOG [7.5.0] («фронт покажет экран
  согласия»), но экран не существовал НИ РАЗУ — `POST /api/consents/{consent_type}` был
  сгенерирован SDK и не вызывался ниоткуда во фронтенде. Эмпирически подтверждено (Playwright,
  реальная регистрация → `GET /api/obligations` → 403, `/profile` без единого слова про
  согласие): каждый новый пользователь блокировался НАВСЕГДА, без обходного пути в UI.
- **Фактическое воздействие: ноль** (продукт не запущен публично) — near miss, не реальный
  инцидент. Потенциальное воздействие при публичном запуске — SEV1-эквивалент: полная
  блокировка единственной функции продукта для 100% новых пользователей.
- **Корень (процессный):** замысел, зафиксированный только в прозе CHANGELOG, никогда не стал
  явным чекбоксом плана вехи 8; ни одна проверка (design-critic/a11y-auditor/ручной прогон) не
  тестировала путь «пользователь с нуля» — все шли по демо-режиму (сознательно не гейтится) или
  аккаунтам, заведённым до введения гейта.
- **Решение:** рабочий минимум UI согласия реализован в этой же сессии (v8.25.3):
  `entities/consents`, `ConsentRequiredPanel` на всех четырёх списках, блок «Согласия» в
  `ProfilePage` — design-critic/a11y-auditor прогнаны, находки починены до сдачи. Процессный
  фикс (новый обязательный класс тестов «полный эмпирический путь нового пользователя») — НЕ
  сделан в этом батче, action item + `docs/ROADMAP.md` §9.0 пункт E.
- **Полный разбор** — `docs/reports/incidents/consent_gate_no_ui_dead_end_incident.md`.

### INC-PG-FALSE-DEBT — PostgreSQL-проверка объявлена невозможной в песочнице (ПОВТОР)

- **Когда:** 2026-07-30, v7.2.0. **Повтор** `postgres_incident_postmortem.md` (миграция 0018).
- **Симптом:** матрица PostgreSQL по миграции 0030 не прогнана, задача помечена долгом владельца.
- **Корень:** проверен ОДИН канал — пустой вывод `which psql`. Вопрос был не «установлен ли PG»,
  а «можно ли его получить»; `which` на него не отвечает. Плюс не открыт собственный архив
  инцидентов, где лежал разбор той же ошибки с готовым рецептом.
- **Решение:** PostgreSQL 16.14 поднят двумя командами apt; миграция проверена на структуру,
  внешний ключ и обратимость; матрица зелёная на обеих СУБД.
- **Что нашла матрица:** PG-only взаимную блокировку в фикстурах — `DROP TABLE user_consents`
  против соединения `idle in transaction`. Прогон не падал, а ЗАВИСАЛ. На SQLite этот класс
  дефектов невидим полностью. Исправлено `close_all_sessions()` + `engine.dispose()`.
- **Мера:** отсутствие бинарника в `PATH` не является доказательством недоступности —
  доказательством является неудачная попытка установки. Разбор — `incidents/postgres_false_debt_repeat.md`,
  счётчик рецидивов — `docs/reports/recurrence_ledger.md`.

### INC-NULL-DEADLINE — «чеховское ружьё» под NOT NULL: три латентных дефекта на бессрочных целях

- **Суть:** канон допускал бессрочную цель (`deadline: null`), колонка была `NOT NULL`. Ограничение схемы работало предохранителем и прятало три дефекта: (D1) `/spending-advice` падал бы с `TypeError` — `round(None)` и сортировка `float` против `None`, детерминированный 500; (D2) `ORDER BY deadline` без `NULLS LAST` — SQLite ставит бессрочные первыми, PostgreSQL последними (тихое расхождение матрицы); (D3) бессрочная цель объяснялась как «до дедлайна ~12 мес» из-за фолбэка `_months_left → 12.0` — и этот дефект **уже работал** в демо-витрине.
- **Корень:** `NOT NULL` использовался как источник истины о домене; допущение «дедлайн есть всегда» нигде не было выражено — ни типом, ни тестом. Канон и схема БД не сверяются автоматически (дыра в гейтах).
- **Решение / шаги:** миграция 0029 (batch-режим), явная семантика бессрочной цели в ядре (`urgency_of` / `months_left_or_none`, `u_s = 1.0` отдельным правилом), `nullslast()` в `get_goals`, None-safe spending-advice, UI + B2B-контракт, снят костыль «дедлайн +10 лет» в демо. 14 тестов (`tests/test_goals_open_ended.py`) на матрице SQLite + PostgreSQL 16. Правило — PIT-010.
- **Статус:** закрыт (v6.5.0), near miss — в прод не вышло. Разбор: `docs/reports/incidents/inc_null_deadline_latent_defects.md`. Открытый хвост: ось ревизии «канон ↔ схема БД» — предложение владельцу.

### INC-A11Y-DEADTEST — live-a11y тест молча скипался (мёртвый axe из-за CSP)

- **Суть:** предрелизный live-a11y тест (`tests/full/test_a11y_axe.py`, axe-core) скипался во ВСЕХ прогонах (и в CI), потому что axe грузился с внешнего CDN, а CSP приложения (`script-src 'self' 'unsafe-inline'`) внешние скрипты режет. Прогон был «зелёным» за счёт `skip`, а не `pass` — тест фактически не проверял доступность ни на одной странице. Near miss (приложение не в проде).
- **Корень:** тест зависел от внешнего ресурса (CDN), недоступного из-за СОБСТВЕННОЙ же security-политики приложения, И деградация маскировалась молчаливым скипом вместо падения. 5 Whys — в полном разборе.
- **Решение / шаги:** axe-core 4.12.1 вендорен (`tests/full/vendor/axe.min.js`) + inline-инъекция (`add_script_tag(content=...)`, проходит по `'unsafe-inline'`, не зависит от сети). Тест расширен до 14 страниц × 2 темы, critical=0 жёстко + serious-ratchet. Починенный тест сразу вскрыл реальный дефект `nested-interactive` (см. батч доступности).
- **Статус:** тест-инфраструктура закрыта. Вскрытые дефекты доступности — в батче доступности. Полный разбор — у владельца (правило §12). Action item на будущее: критичный тест не должен молча скипаться при недоступности обязательного ресурса (вендорить или фейлить) + сделать число скипов видимым сигналом.

### INC-CBR-KEYRATE-PARAM — кнопка «получить ставку с ЦБ» всегда отдавала дефолт при живом cbr.ru

- **Суть:** `/api/planning/key-rate` всегда возвращал статический fallback (0.16), хотя cbr.ru доступен (локально, РФ-IP, HTTP 200). Реальная ставка не доходила до пользователя; r_bench (порог Avalanche «гасить кредит или копить») считался от устаревшего дефолта → потенциально неверный совет.
- **Корень:** SOAP-метод KeyRate у cbr.ru ASMX чувствителен к регистру имён параметров — ждёт `<fromDate>` + `<ToDate>` (заглавная T). В коде была строчная `<toDate>` → ASMX не распознал параметр → `ToDate` ушёл в `DateTime.MinValue` (0001-01-01) → диапазон `сегодня−N … 0001` пустой → ноль строк `KR` → парсер `None` → fallback. Маскировалось тем, что симптом (fallback) совпадал с историей INV-CBR-403 (внешний 403) — «решили», что это то же внешнее ограничение, и не посмотрели `detail`.
- **Решение / шаги:** (1) фикс регистра `<ToDate>` (подтверждён первоисточником — шаблон запроса cbr.ru); (2) durable БД-кэш last-known-good (`cbr_key_rate_cache`, миграция 0026, модель `CbrKeyRate`) — переживает перезапуск процесса и прод-403 на датацентровом IP; (3) устойчивый парсер (регистр/namespace/fault, извлекает дату вступления); (4) самодиагностика — начало ответа в `detail` при 200-но-не-извлечь; (5) `refresh_key_rate()` для прогрева кэша на проде (RU-IP cron). v4.24.0, +24 теста, матрица SQLite+PostgreSQL.
- **Живая проверка (честная граница):** финальное подтверждение (cbr.ru отдаёт реальную ставку из приложения) — на машине с РФ-IP. POST к cbr.ru из песочницы недоступен (bash-egress 403 — та же граница, что в INV-CBR-403; при этом `web_fetch` cbr.ru достаёт, чем и подтверждён первоисточник). Самодиагностика в `detail` делает верификацию однозначной.
- **Что запомнить:** graceful fallback маскирует реальный баг, если симптом совпадает с известным внешним ограничением — смотреть `detail`/корень, а не списывать на «то же самое». «cbr.ru ответил (200)» ≠ «cbr.ru недоступен»: пустой-200 и сетевой сбой — разные ветки, разная обработка.
- **Статус:** код закрыт (фикс + кэш + тесты зелёные); живая верификация на РФ-IP — у владельца. Полный разбор — у владельца (правило §12). Связан с INV-CBR-403 (тот же домен; там — внешний 403 для курсов валют, здесь — отдельный реальный дефект ключевой ставки).

### BUG-026 — datetime.now() (локальное время сервера) вместо UTC в «сейчас»-логике

- **Суть:** после унификации `datetime.utcnow()` (v4.25.2) в коде остались 13 прямых `datetime.now()` — это локальное время процесса, не UTC. В песочнице/CI (TZ=UTC) совпадает с UTC, дефект невидим; на прод-VPS в РФ (обычно MSK, UTC+3) — стабильный сдвиг между «сейчас»-логикой и UTC-хранилищем. Severity Minor (узкие границы), Priority P0 (чиним до прод-запуска). Найден код-ревью до проявления.
- **Корень:** `datetime.now()` без аргумента возвращает naive-локаль; колонки и записанные даты — naive-UTC. Заметнее всего на месячном бакетинге трат (`spending.current_period`/`_min_period` по локальным часам против UTC-`txn.date` → разъезд на стыке месяца) и в fallback-датах импорта (`statement_parser`, `bank_api`), писавшихся в локали в UTC-naive колонки. Окна «последних N дней» (`crud`) и расчёт «месяцев выплачено» (`obligation`) сдвинуты на оффсет.
- **Решение / шаги:** 13 вызовов → helper `utcnow()` (naive UTC, контракт naive↔naive — риск naive/aware исключён) в `spending.py`/`statement_parser.py`/`bank_api.py`/`obligation.py`/`crud.py`. Aware-вызовы `datetime.now(timezone.utc)` в `cbr_rate`/`cbr_fx`/`security` — корректный UTC, не тронуты. Костыль `obligation.replace(tzinfo=None)` оставлен (гасит aware-вход Pydantic — отдельная история). v4.25.3, новый `tests/test_clock_unification.py` (7 тестов, red→green: мок `utcnow`, проверка привязки к нему, а не к системным часам). Миграций нет, fast-набор зелёный (884 passed).
- **Почему не поймали раньше:** ни один тест не эмулировал не-UTC окружение — на UTC-CI локальное и UTC «сейчас» неотличимы. Закрыто классом тестов, мокающих `utcnow` и проверяющих привязку результата к нему; при появлении новых `datetime.now()` такой тест их поймает. Полная корректность таймзон (зона юзера → локальный календарь) — отдельный заход в слое паттернов (поле `tz` у User ещё нет).
- **Статус:** закрыт (v4.25.3). Полный разбор / карточка — у владельца (правило §12).

### BUG-028 — календарная мина: хардкод даты фикстуры против окна от реальных часов

- **Суть:** `test_expense_record_date` хардкодил транзакцию `2026-01-10` против окна «последние 6 месяцев» от `utcnow()`. До 2026-06-30 январь входил в окно (тест зеленел с v4.25.4), 1 июля окно сдвинулось на `2026-02` — фикстура выпала из выборки, advisor получил пустой список, тест покраснел без единого изменения кода. Дефект фикстуры, продуктовый код корректен. Severity Minor, Priority P0 (красный гейт).
- **Корень:** календарная константа в фикстуре, проходящей через оконную логику от реальных часов. Класс родствен BUG-026 (часы приложения), но для тестовых фикстур правила не существовало; обычный CI такой дефект не ловит — тест честно зелёный до порога.
- **Решение / шаги:** дата фикстуры → относительная `utcnow() − 5 дней`, period-ассерты выводятся из неё. Свип всего оконного домена «машиной времени» (`tools/timewarp/warp.py`, сдвиг `utcnow` на +90/+370 дней): вторая находка — `test_obligation_term` строил фикстуру от `datetime.now()` (локаль) вместо `utcnow()` (нарушение контракта часов ADR-002 в тестах, edge-flaky на MSK) — переведён на `utcnow()`. Контроль: +370 дней — 153/153 зелёные. v5.11.0.
- **Почему не поймали раньше:** мина взрывается календарём, а не коммитом. Закрыто правилом (QA.md: даты фикстур с окнами — только относительные/замороженные) + периодической варп-приёмкой (раз в веху). Полный разбор — `incidents/bug_028_calendar_fixture_bomb.md`.
- **Статус:** закрыт (v5.11.0).

### INC-FWD-BUILD-WIPEOUT — репозиторий стёрт до огрызка при forward-build публикации

- **Суть:** коммиты/теги/релизы v5.20.0–v5.23.0 на GitHub содержали почти пустое дерево (6 файлов, `deploy/systemd`) вместо ~623 — публикация каждой версии стирала проект.
- **Корень:** архивы v5.20.0+ паковались без корневой обёртки `finpilot_vX_Y_Z_intl/`; публикатор искал обёртку, при её отсутствии fallback `find | head -1` выхватывал случайную папку (`deploy/`), а `rsync --delete` делал репо равным ей. v5.19.0 уцелел случайно (в его архиве была ровно одна папка-обёртка).
- **Решение / шаги:** публикатор укреплён — надёжный поиск корня (обёртка / содержимое в корне / единственная папка) с приёмом только по маркерам `app/`+`CHANGELOG.md`, иначе **fail-loud** (репо не трогается). Архивы приведены к единому формату с обёрткой. Добавлен восстановитель `tools/publish/finpilot_restore.sh`. Данные не потеряны — деревья в архивах целы.
- **Статус:** причина найдена, доказана (воспроизведена), исправление и восстановление выданы. Полный разбор — `incidents/forward_build_wipeout_incident.md`.
