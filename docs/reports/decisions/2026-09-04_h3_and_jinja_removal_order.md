# Порядок: остаток H3 и снос Jinja-остатка

**Статус:** ПРИНЯТО вахтой по прямому поручению владельца («сделай ресерч и прими взвешенное
решение как лучше»), 04.09.2026
**Дата разбора:** 04.09.2026
**Вопрос:** остаток H3 (`banks_router`, `plaid_router` под `_FIN`) — вместе со сносом
Jinja-остатка или отдельным батчем?

## Короткий ответ

**Ни то, ни другое в исходной формулировке.** Разбор по диску показал, что оба вопроса
поставлены на неверных допущениях:

1. **H3 — это не одна задача, а две разного риска.** `plaid_router` можно закрыть немедленно,
   `banks_router` — нет.
2. **Снос Jinja-остатка не может быть следующим батчем.** Условия его снятия НЕ выполнены,
   хотя выглядят выполненными.

## Что проверено на диске (не по памяти)

### `plaid_router` — потребителей ноль

```
grep -rn "api/plaid" frontend/static/js/app.js frontend/src → ничего
routes_plaid.py:4  «иначе любой вызов отвечает 404 „не активировано" (РФ-сборка, KEEP-06)»
```

Его не зовёт ни Jinja, ни React, и в РФ-сборке он отвечает 404 на всё. Решение владельца
от v8.27.0 («гейт ставится только вместе с фронтом») защищало от того, что экран покажет
403 без объяснения. **У `plaid_router` экрана нет вообще** — защищать нечего.

### `banks_router` — потребитель ровно один, и это Jinja

```
frontend/static/js/app.js:635  POST /api/banks/sync/{bankId}
frontend/static/js/app.js:650  POST /api/banks/sync
frontend/static/js/app.js:717  POST /api/banks/upload      ← импорт выписки
grep -rl "listBanksApi…|uploadStatementApi…|triggerSyncAllApi…" frontend/src (без generated) → 0
```

React не обращается к `banks_router` ни разу. Экран `/banks` в React — это `pages/assets`,
он работает с `liquid_assets_router`, который под `_FIN` с v8.27.0.

### Jinja не умеет показать отказ гейта

```
grep -n "403\|consent" frontend/static/js/app.js → ни одного совпадения на 2658 строк
```

`app.js` проверяет только `res.ok && data.status === 'success'`. Гейт вернул бы 403 с JSON-телом,
и человек увидел бы невнятную ошибку без слова «согласие» — **ровно SEV1
`CONSENT-GATE-NO-UI`**, о котором и предупреждало решение v8.27.0.

### Условия сноса Jinja-остатка — НЕ сняты

Разбор `2026-08-14_jinja_frontend_removal.md` разложил остаток на две группы. Проверено:

**Группа 1 (`legal/*`, `contacts`, `validation`).** Формально L2/L3/L5/L6/L7 закрыты в v8.40.0
и v8.41.0. Но:
- `docs/legal/compliance_register.md` — чекбоксы L2/L5/L6/L7 **пустые**, а обновлённый реестр
  прямо назван частью гейта Э6;
- 🔴 **футер ссылается на `/legal/privacy`, `/legal/terms`, `/legal/cookies` — это и есть
  Jinja-роуты.** Снести их значит превратить требование L7 в мёртвые ссылки. Тот самый класс
  H12, который чинился весь батч v8.36.0–v8.37.0: ссылка есть, адреса нет.

Снос Группы 1 требует **сначала** перенести тексты документов в React.

**Группа 2 (`planning.html` и соседи).** CRUD-паритет 5/5 закрыт (v8.25.0–v8.30.0), но второе
условие — интерактивные контролы плана — нет:

```
frontend/templates/planning.html:19-24  выбор риск-профиля, 5 кнопок
frontend/templates/planning.html:37     слайдер l_min
frontend/templates/planning.html:51     слайдер r_bench
React: ни одного места, где меняется risk_tolerance / l_min / r_bench
```

**Риск-профиль — центральный параметр матмодели** (пять профилей, веса SAW, `docs/math_model.md`).
Пользователь React-версии не может настроить план под себя вообще; `planning.html` — единственный
способ. Снос убрал бы не полировку, а управление моделью — ровно та ошибка, которую разбор
14.08.2026 уже совершил и исправлял откатом.

## Решение

**1. `plaid_router` под `_FIN` — немедленно, в ближайшем батче.**
Риск нулевой: ноль потребителей, 404 в РФ-сборке. Это чистая гигиена периметра 152-ФЗ.
Оговорка решения v8.27.0 к нему не относится — она про экран, которого нет.

**2. `banks_router` под `_FIN` — вместе с переносом ИМПОРТА ВЫПИСКИ в React**, а не «вместе
со сносом Jinja» вообще. Формулировка уточняется: как только импорт живёт в React (где
`ConsentRequiredPanel` работает с v8.27.0), `banks_router` теряет единственного потребителя,
и гейт ставится в том же батче без окна незащищённости.

Так узкий и понятный шаг («перенести импорт выписки») заменяет расплывчатый («снести Jinja»),
и гейт приезжает вместе с ним, а не ждёт всего сноса.

**3. Снос Jinja-остатка — НЕ следующий батч.** Перед ним:
- контролы плана в React (риск-профиль, `l_min`, `r_bench`) — Группа 2;
- импорт выписки и синхронизация банков в React — Группа 2, и тот же батч закрывает `banks_router`;
- тексты юридических документов в React — Группа 1, иначе футер L7 ведёт в никуда;
- `compliance_register.md` обновлён — формальный гейт Э6.

**4. Следующий батч — контролы плана.** Из четырёх пунктов он единственный, который двигает
не только снос, но и сам продукт: сейчас пользователь не может выбрать риск-профиль вообще,
а это главный параметр рекомендации.

## Чего это решение НЕ делает

Не отменяет решения владельца от v8.27.0 — уточняет область его применения по факту с диска:
оговорка «только вместе с фронтом» защищает от отказа без объяснения, и там, где фронта нет
вовсе, защищать нечего.

Не назначает срок сносу Jinja. Он остаётся последним шагом Э6 с прежними условиями; здесь
только зафиксировано, что условия **пока не выполнены**, хотя после закрытия юрблока выглядят
выполненными.

## Что изменило бы решение

- Если владелец решит, что риск-профиль в React не нужен (модель считает по умолчанию 3) —
  Группа 2 сокращается до импорта выписки, и снос ближе на батч.
- Если тексты документов решено оставить на Jinja навсегда как статические страницы —
  Группа 1 закрывается без переноса, футер продолжает на них ссылаться, снос сужается.
  🔴 Это решение владельца: оно меняет обещание «оставь только API».
