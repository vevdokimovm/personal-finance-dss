# Backup & Restore — runbook

> Планка финтеха: потеря данных пользователей недопустима, восстановление — отработанная
> процедура, а не надежда. Прод — PostgreSQL (веха 9, VPS); dev — SQLite.

## Что бэкапим

1. **PostgreSQL** — вся пользовательская и доменная БД (28 таблиц).
2. **`.env`-секреты** — НЕ в бэкап-архив БД; хранятся отдельно (менеджер секретов/зашифрованное
   хранилище владельца). Потеря `FERNET_KEY` = невосстановимость зашифрованных полей — ключи
   бэкапятся отдельным защищённым каналом.
3. Статика/код — не бэкапим (восстанавливается из git).

## Расписание и retention

- **Ночной полный дамп**: `pg_dump -Fc` (custom format, сжатие) в 03:00 MSK, cron на VPS.
- **Retention**: 30 ежедневных + 12 еженедельных (воскресенье) + 6 ежемесячных.
- **Хранение**: локальный диск VPS + офсайт-копия (S3-совместимое хранилище РФ-юрисдикции —
  требование 152-ФЗ о локализации). Обе копии шифруются.

## Команды (шаблон)

```bash
# дамп
pg_dump -Fc "$DATABASE_URL" -f "finpilot_$(date +%F).dump"
# шифрование офсайт-копии (age; ключ у владельца)
age -r "$BACKUP_AGE_RECIPIENT" -o finpilot_$(date +%F).dump.age finpilot_$(date +%F).dump
# восстановление (staging/новый инстанс)
createdb finpilot_restore
pg_restore --no-owner -d finpilot_restore finpilot_YYYY-MM-DD.dump
alembic current   # сверить голову миграций
```

## Проверка восстановимости (без неё бэкап — фикция)

Ежемесячно: восстановить последний дамп в staging-БД → `alembic current` совпадает с репо →
smoke: логин тестового пользователя, `/api/planning/calculate` на его данных → результат в
`docs/reports/testing/` одной строкой. Автоматизация проверки — веха 9.

## RPO / RTO (цели MVP)

- **RPO ≤ 24 ч** (ночной дамп); после запуска нагрузки — WAL-архивирование и RPO ≤ 15 мин.
- **RTO ≤ 4 ч** — развернуть VPS из плейбука (веха 9) + restore + смена DNS.

## 152-ФЗ

Дампы содержат ПДн (`docs/pdn_data_map.md`) → хранение только в РФ-юрисдикции, доступ — только
владелец, шифрование при хранении и передаче. Удаление пользователя по праву на забвение — see
процедура в карте ПДн: затрагивает и активную БД, и попадание в новые бэкапы (старые истекают
по retention — это допустимо при зафиксированном сроке, вопрос юристу №7).
