# Реестр частых ошибок (pitfalls) FINPILOT

Повторяющиеся ошибки в рабочем процессе разработки: кривые команды, привычки, грабли воркфлоу.
Это **третий тип** разбора рядом с инцидентами и расследованиями, но самого лёгкого веса.

Чем отличается от соседей:

- **Инцидент** (`docs/reports/incidents_summary.md`) — был дефект в продуктовом коде и/или влияние на
  пользователя/систему. Полный разбор — отдельным файлом (правило §12).
- **Расследование** (`docs/reports/investigations_summary.md`) — дефекта в продуктовом коде НЕ оказалось
  (внешняя причина, артефакт теста, недопонимание); причина была неочевидна, её искали.
- **Pitfall (этот файл)** — повторяющаяся ошибка в воркфлоу самого Claude. Причина известна сразу,
  мистики нет, продукт не затронут. Это **не** отдельный файл-разбор, а ОДНА строка-урок:
  симптом → корень → как правильно → правило.

Граница с рунбуком: `docs/sandbox_runbook.md` описывает **свойства окружения** (как работать в
песочнице). Этот файл — про повторяющиеся **ошибки** (чего НЕ делать). По правилу §15 каждая запись
становится переиспользуемым правильным паттерном, чтобы не выводить его заново каждую сессию.

Заполняется АВТОМАТИЧЕСКИ по правилу §14 — как только ошибка воркфлоу повторилась, строка сюда, не
дожидаясь просьбы.

**С v7.3.0 у каждой записи есть счётчик повторов**, и он определяет тип контрмеры. Правило
эскалации — `docs/reports/recurrence_ledger.md` §1: 1 повтор → текст, 2 → правило и чек-лист,
**3 → обязательная автоматическая проверка** (проза дважды доказала неэффективность),
4+ → менять процесс, а не добавлять правило. Понижать уровень нельзя.

Лидерборд по числу повторов и топ-3 в шапке WATCHLOG — там же. Механические проверки
уровня 3 — `tools/preflight.py`.

### PIT-001 — `grep` в цепочке `&&` обрывает выполнение; счётчик/итоги «не выводятся»

> **Повторов: ≥5 · Уровень 3 · Автопроверка: `tools/preflight.py::grep_in_and_chain`**

- **Симптом:** команда вида `... && grep -c X file && next` — `next` молча не выполняется; счётчик
  тестов или строка `TOTAL` покрытия «не выводится». Повторялось много раз.
- **Корень:** `grep` с НУЛЁМ совпадений возвращает код выхода `1` → оператор `&&` обрывает весь
  остаток цепочки. Усугубление: иногда греп идёт по файлу, который фоновый прогон ещё дописывает
  (гонка) — в тот момент совпадений нет; и кириллический вывод в пайпе мог дать битый UTF-8 и оборвать
  команду.
- **Как правильно:**
  1. не чейнить `grep` через `&&` — использовать `;` либо `grep ... || true`;
  2. дожидаться завершения по маркер-файлу (`EXIT=` в `/tmp/*.done`), а не грепать на ходу;
  3. счётчик/итоги брать из ГОТОВОГО файла: `tail -n3 /tmp/reg.txt` (там строка `N passed`) —
     не хрупким `grep -oE "[0-9]+ passed"`;
  4. вывод с кириллицей читать через `python3` или `tail`, не через `grep` внутри `&&`-цепочки.
- **Правило:** §15 — повторная ошибка кодифицируется один раз; правильная команда переиспользуется,
  а не выводится заново.

### PIT-002 — `DATABASE_URL=sqlite:///:memory:` ломает тесты с видимостью между коннекшенами

- **Симптом:** при ручном `export DATABASE_URL="sqlite:///:memory:"` падает группа scope/lifecycle-тестов
  (изоляция данных, видимость общих строк семьи, роспуск с возвратом строк) — хотя на дефолтной
  конфигурации те же тесты зелёные. Выглядит как регрессия или баг мёржа, провоцирует винить код.
- **Корень:** in-memory SQLite даёт ОТДЕЛЬНУЮ БД на каждое соединение — данные, записанные в одном
  запросе/коннекшене, не видны из другого. Тесты, которые пишут данные одним субъектом и читают другим
  (cross-connection scope), на `:memory:` ломаются по построению. `conftest.py` именно поэтому при
  отсутствии внешнего `DATABASE_URL` поднимает изолированный SQLite-**файл** (`tempfile`), а не `:memory:`.
  Ручной override `:memory:` перебивает этот намеренный выбор → ложные падения.
- **Как правильно:**
  1. не переопределять `DATABASE_URL` на `:memory:` для полного набора / scope-тестов — дать `conftest.py`
     поднять файловый SQLite самому (просто `unset DATABASE_URL` / не задавать);
  2. для PG-половины матрицы задавать `DATABASE_URL=postgresql+psycopg://...` — это валидный override,
     `conftest` его уважает и гоняет тот же набор на PG;
  3. падение именно группы scope/cross-request тестов при «ускоряющем» `:memory:` — сигнал «среда, не баг»:
     сверить дефолтную конфигурацию прежде чем винить код.
- **Правило:** §11 — «ложная тревога»: подозрение на дефект сначала проверяется дифференциально (та же
  среда на заведомо рабочем дереве); среда/конфиг исключаются раньше кода.

### PIT-003 — полный fast одной командой/в фоне тратит время; гонять синхронными группами

> **Повторов: 2 · Уровень 2**

- **Симптом:** `pytest -m fast` целиком (~850 тестов) одной командой → `returncode -1`/`124`, XML
  пустой. Уход в `setsid`-фон с опросом маркера — фоновый процесс умирает между опрос-командами,
  `*.done` не появляется, время уходит на бесконечный опрос. Повторялось несколько прогонов подряд.
- **Корень:** (1) полный прогон дольше лимита инструмента (~3-4 мин) → обрыв до записи XML;
  (2) `setsid`-фон в этой песочнице не переживает завершение шелла предыдущего вызова bash_tool —
  процесс прибивается, маркер не пишется.
- **Как правильно:** гонять **синхронно группами по ~14-15 файлов** (`awk 'NR%5==N'`), каждую с
  `timeout 160 ... --junitxml=/tmp/pN.xml`, по 1-2 группы на вызов; итог суммировать из XML. Группа
  упёрлась в timeout → в ней тяжёлый файл (property/forecast/pdf), разбить её пополам. Полная
  процедура с командами — `docs/sandbox_runbook.md` §7.
- **Правило:** для полного fast — синхронные группы из рунбука §7, НЕ одна команда и НЕ `setsid`-фон.

### PIT-004 — отказы интермиттентно по ВСЕМ инструментам сразу = канал сессии, а не команда

- **Симптом:** сначала падает `bash_tool` (списываешь на спецсимволы/долгую операцию), затем на тех же
  безобидных вызовах начинает падать и `view`. Обходы (другой синтаксис, дробление команды, вывод в
  файл) дают всё более редкий успех — каждый следующий вызов превращается в лотерею.
- **Корень:** отказывает не отдельная команда и не bash как таковой, а **труба отправки самой сессии** —
  транспортный слой между моделью и песочницей. Когда падает РАЗОМ и bash, и view (инструменты с разной
  механикой), причина общая для них — канал, а не содержимое вызова. Изнутри сессии это не чинится:
  ты дёргаешь тот же отказывающий канал, которым шлёшь любой инструмент.
- **Как правильно:** не биться в канал повторными вызовами (это ровно то, что усугубляет). Зафиксировать
  состояние и сделать **чистый hand-off**: что готово и лежит в файлах, что на середине, точная спека
  «доделать в N шагов». Затем перезапуск в свежем чате с архивом — на чистом канале работа идёт гладко.
  Признак, что пора: ДВА разных инструмента отказывают подряд на безобидных вызовах.
- **Правило:** одиночный отказ инструмента — ретрай/обход (TLS-таймауты РФ, гонка маркеров — PIT-001/003).
  Отказ ДВУХ разных инструментов подряд на простых вызовах — это канал: hand-off + рестарт, не долбёжка.
- **Подвид «вызов вышел текстом» (частый, лечится РЕРАНОМ, не рестартом):** вместо исполнения вызов
  попадает в ответ видимым текстом (`court` + сырой `<invoke>`/`<parameter>`) и ход обрывается, НО
  песочница жива (следующий ход bash работает). Триггеры: завершение хода тул-коллом; сложная команда
  (heredoc/вложенные кавычки); **заражение паттерном из истории** (сломанные хвосты в контексте →
  воспроизводятся как текст). Лечение: не завершать ход вызовом, игнорировать сломанные образцы из
  истории, весь батч за один ход, при обрыве — реран с проверки состояния. **Полный разбор всех кейсов и
  протокол — `docs/tool_call_channel_failures.md`.**

### PIT-005 — при сбое сессии «уже сделано» в hand-off ≠ доехало; верь только архиву

- **Симптом:** прошлая сессия упёрлась в сбой канала (PIT-004) и в финальном hand-off перечислила
  как готовое: «`revocation.py` создан, тесты JWT написаны, PIT-004 заведён». В новой сессии этих
  файлов в архиве `v4.25.4` НЕТ. При этом `ADR-002` (закоммиченный в предыдущем релизе `v4.25.3`)
  доехал нормально. Потерялось ровно то, что создавалось ПОСЛЕ сборки архива.
- **Корень:** рабочая директория песочницы стирается между сессиями; в архив попадает только то, что
  упаковано на момент его сборки. Работа после `present_files`/сборки живёт лишь в активной сессии.
  Сбой инструмента тут ни при чём — он не «теряет» работу сильнее, чем обычное завершение сессии: она
  и так не персистится. Иллюзия «почти доделано» возникает из доверия к описанию вместо проверки.
- **Как правильно:** (1) hand-off о незавершённом батче должен содержать не «что сделано», а **точные
  шаги воспроизведения** (что в этом случае и спасло — план собрал фичу с нуля за заход). (2) Заступая
  на вахту, СНАЧАЛА грепнуть реальное наличие в архиве каждого артефакта, который hand-off зовёт
  готовым (`grep -c`, `ls`), и только потом продолжать. (3) Собирать архив-чекпойнт по ходу батча, а
  не только в конце, чтобы окно потенциальной потери было минимальным.
- **Правило:** доехало только то, что лежит в архиве. «Уже сделано» в hand-off — гипотеза, проверяемая
  грепом, а не факт. (Родственно PIT-004: тот — как распознать сбой канала в моменте, этот — как
  безопасно возобновиться после него.)

### PIT-006 — `cd X && <job> &` фонит ВЕСЬ пайплайн вместе с `cd`; foreground остаётся не в той папке

> **Повторов: 2 · Уровень 2 · Последний: 2026-07-30 (эта же ошибка допущена при прогоне матрицы)**

- **Симптом:** одной командой делаешь `cd /path/proj && setsid bash -c '…' &` (запуск долгой задачи в
  фоне), а следом в том же вызове `bash_tool` идут `sed`/`grep`/`ls` по `app/...` — и они падают
  «No such file or directory», хотя проект на месте. Кажется, что директорию стёрло.
- **Корень:** оператор `&` имеет МЕНЬШИЙ приоритет, чем `&&`, поэтому `cd X && job &` фонит весь
  список `(cd X && job)` целиком — `cd` исполняется в **фоновом субшелле**, а не в текущем. CWD
  foreground-шелла не меняется, и последующие команды того же вызова работают в исходной папке
  (`/home/claude`), а не в `X`. Директорию никто не стирал — это про область видимости `cd`.
- **Как правильно:** не сцеплять `cd` с фоновым джобом через `&&`. Разнести на отдельные операторы —
  `cd` в foreground, `&` только на долгой команде:
  ```sh
  cd /home/claude/proj                       # foreground: CWD меняется и держится до конца вызова
  setsid bash -c '…' > /tmp/job.log 2>&1 &    # фоним ТОЛЬКО долгую задачу
  echo ...; sed -n ... app/...                # уже в proj
  ```
  Если фоновому субшеллу тоже нужна папка — дать ему свой `cd` внутри: `setsid bash -c 'cd /path && …' &`.
- **Правило:** `&` фонит всё слева до него (приоритет ниже `&&`/`;`). Хочешь фонить один процесс — ставь
  `&` только на нём, а `cd` держи отдельным оператором в foreground. Симптом «файлов нет, хотя они есть»
  после фонового запуска → первым делом проверить, не утащил ли `&` твой `cd` в фон.

### PIT-007 — «docs-батч» добавил .py вне app/ → полный flake8-гейт не гонялся, нарушения копятся

- **Симптом:** приём вахты v5.10.0: `flake8 .` (скоуп CI) даёт 12 нарушений в `tools/survey_analysis/`, хотя WATCHLOG заявляет ноль. Файлы заехали в v5.1.0 docs-батчем с пометкой «код/гейты не тронуты».
- **Корень:** «не трогали код» понималось как «не трогали app/», но добавление ЛЮБОГО `.py` в дерево меняет результат `flake8 .`. Повтор класса граблей v4.30.2 (ручной скоуп уже, чем CI-скоуп).
- **Как правильно:** любой батч, добавляющий/перемещающий `*.py` (включая `tools/`), обязан гнать `flake8 .` перед упаковкой — независимо от того, «docs» это батч или нет.
- **Правило:** гейт руками = гейт CI ровно тем же скоупом; «docs-батч» определяется по диффу (`git diff --name-only` / список файлов архива), а не по намерению.

### PIT-008 — `find … && echo ЕСТЬ` лжёт: find возвращает 0 и БЕЗ находок

- **Симптом:** проверка наличия файла `find . -iname "x.md" && echo "ЕСТЬ" || echo "НЕТ"` печатает
  «ЕСТЬ», хотя файла нет. На этом при передаче вахты была принята ложная посылка «методичка доехала
  через форк» (вскрыто в v5.13.0: `roadmap_methodology.md` в форке отсутствовал).
- **Корень:** exit-code `find` = 0, если сам обход прошёл без ошибок; количество найденного на код
  возврата не влияет, поэтому `&&` срабатывает всегда.
- **Как правильно:** судить по ВЫВОДУ, а не по коду возврата: `test -f путь` для конкретного файла,
  `[ -n "$(find …)" ]` или `find … | grep -q .` для шаблонов.
- **Правило:** «инструмент завершился успешно» ≠ «инструмент что-то нашёл». Родня PIT-004
  («уже сделано» — гипотеза): доверяй файлу на диске и непустому stdout, не зелёному коду возврата.

### PIT-009 — доставка файлов в чат: «мёртвые заглушки» (корень подтверждён: Tor Browser)

**Симптом:** `present_files` отработал, но у владельца либо нет карточек, либо кнопка есть,
а скачивание падает ошибкой (файл на бэкенде умер, заглушка осталась). Зеркально ломается и
канал «вверх» (загруженный файл не доезжает до `/mnt/user-data/uploads/`).

**Правило (v2):** доставка НЕ подтверждена, пока владелец не скачал. **Выданный путь
неприкасаем** — не удалять, не перезаписывать, не cp/mv поверх (замена файла по тому же пути —
кандидат в причины «мёртвой заглушки»). Лестница: повторный `present_files` тех же путей →
копия **под новым именем** (`_r2`, `_r3`…) → критический минимум (WATCHLOG отдельным .md) +
пометка в §0. Каждая выдача — с **sha256 в чате**. Владелец на Tor: новая цепочка перед
скачиванием, файлы поштучно, качать сразу после выдачи. Ступень 5 (канал чата мёртв
совсем): **git-ветка из песочницы** — PAT владельца (fine-grained, Contents RW, один репо, TTL
1 день) → push `sync/vX.Y.Z` → владелец `git fetch` → revoke токена. Tor Browser гонит трафик
через Tor даже при включённом системном VPN — для скачивания использовать обычный браузер + VPN. Загрузки владельца в начале сессии проверять `ls`-ом фактического наличия
(не верить списку в сообщении). Разбор: `docs/reports/incidents/inc_chat_file_delivery_dead_stub.md`.
- **Упаковка архива — ВСЕГДА с корневой обёрткой** `finpilot_vX_Y_Z_intl/` (имя обёртки = имя zip без `.zip`): `mv <дерево> finpilot_vX_Y_Z_intl && zip -r finpilot_vX_Y_Z_intl.zip finpilot_vX_Y_Z_intl`. НИКОГДА `zip archive.zip .` (содержимое без обёртки) — публикатор ждёт обёртку, при её отсутствии старый fallback выхватывал случайную папку и `rsync --delete` сносил весь репозиторий. Дополнительно: любой `rsync --delete` — только после проверки маркеров корня (`app/`+`CHANGELOG.md`), иначе fail-loud. Разбор: `docs/reports/incidents/forward_build_wipeout_incident.md` (INC-FWD-BUILD-WIPEOUT).

### PIT-010 — ограничение схемы (`NOT NULL`) — это предохранитель на коде, а не описание домена

**Симптом.** Плановое снятие `NOT NULL` с `goals.deadline` (канон давно допускал бессрочные цели)
одновременно снимало предохранитель: три латентных дефекта в коде-потребителе выстрелили бы разом —
детерминированный 500 на `/spending-advice` (`round(None)`, сортировка `float` против `None`),
расхождение порядка целей SQLite↔PostgreSQL (`ORDER BY` без `NULLS LAST`) и ложь в объяснении плана
(«до дедлайна ~12 мес» у цели без срока).

**Правило.** Ослабление любого ограничения (`NOT NULL`, `CHECK`, FK, уникальность) — операция **по
коду**, а не по БД. Порядок: сначала `grep` по **имени колонки** во всём `app/` (не по модели — она
не покажет потребителей) и обход каждого места «а что здесь при NULL», потом миграция. Частичная

### PIT-012 — проверка через heredoc-экранирование молча инвертируется

> **Повторов: 1 · Уровень 1**

- **Симптом:** проверка отвечает уверенно и всегда одинаково, независимо от содержимого файла.
  Конкретно: `b'\r\n' in data` в скрипте, переданном в Python через shell-heredoc, отвечал
  «CRLF нет» на файлах, где CRLF был в каждой строке — и на этом основании был написан ложный
  раздел отчёта с рекомендацией восстанавливать эталоны из тегов.
- **Корень:** экранирование удваивается на границе shell → Python. До интерпретатора долетает
  литерал из четырёх символов `\r\n`, а не два байта. Такая последовательность в данных не
  встречается никогда, поэтому проверка даёт стабильный ложноотрицательный результат.
- **Как правильно:** проверку, проходящую через слой экранирования, обязательно прогнать на
  **заведомо положительном** примере. Если контроль не срабатывает там, где обязан, — виноват
  контроль, а не данные. Плюс читать файл целиком и **считать** вхождения, а не проверять
  вхождение в срезе: `d.count(b"\r\n")` информативнее, чем `in d[:300]`.
- **Правило:** любой булев чек через heredoc сопровождается контрольным примером с известным
  ответом. Одна лишняя строка в скрипте против ложного вывода в отчёте.

### PIT-016 — фоновый прогон через `| tail -N` (без `-f`) не стримит, прячет прогресс до конца

> **Повторов: 1 · Уровень 1**

- **Симптом:** долгий `pytest` полной суитой запущен в фоне как
  `... -m pytest ... | tail -30` под `run_in_background`. Файл вывода стоял 0 байт всё время
  выполнения (10+ минут) — со стороны неотличимо от зависшего процесса; пришлось руками
  проверять `ps aux`/CPU% вместо того, чтобы видеть прогресс по числу пройденных тестов.
  Владелец поймал: просил раньше зафиксировать механизм живого прогресса для таких
  процессов — записи об этой просьбе не нашлось ни в WATCHLOG, ни здесь, значит она не
  доехала с прошлой сессии (родня PIT-005: то, что «уже сделано» в hand-off, не значит
  доехало).
- **Корень:** `tail -N` без `-f` не потоковый — он читает ВЕСЬ input до EOF и только тогда
  печатает последние N строк. В связке с фоновым запуском это полностью прячет прогресс
  ровно там, где видимость нужнее всего: пока процесс ещё идёт. Отдельно и независимо в этом
  случае усугубила перегрузка машины (`uptime` load average 62–87 от параллельных сессий на
  других аккаунтах) — но она объясняет только медленность, не нулевой вывод; нулевой вывод
  был бы и без перегрузки.
- **Как правильно:** для «сообщи, когда закончится» (процесс неважен по ходу) — голая
  команда под `Bash(run_in_background: true)` БЕЗ пайпа через `tail` вообще: харнесс сам
  уведомляет по завершении, урезание вывода на входе не нужно и вредно. Для «покажи прогресс
  по ходу» — инструмент `Monitor`, не `Bash`+`tail`: команда должна писать построчно и без
  буферизации (`python -u -m pytest -v ... 2>&1 | grep --line-buffered -E "PASSED|FAILED|
  ERROR|===`) — каждая строка станет отдельным уведомлением.
- **Правило:** `| tail -N` без `-f` в связке с фоновым запуском — красный флаг сам по себе,
  вне зависимости от загрузки машины. Долгий прогон = либо голая фоновая команда (итог в
  конце), либо `Monitor` с небуферизованным построчным выводом (прогресс по ходу) — третьего
  варианта («в фон и через tail») в этом проекте нет.
- **Контрмера уровня 1** (первый повтор — текст, см. правило эскалации §0 файла).

### PIT-023 — защитный хук судит по СЛОВУ в команде, а не по тому, что она делает

  лишнего отказа, и снижать его чувствительность ради удобства нельзя. Обходить его
  переформулировкой — тоже: это тот же обход, только незаметный.
- **Контрмера уровня 1** (текст). Ужесточать разбор не стоит: хук про необратимые
  действия, и «слишком осторожно» здесь верная сторона ошибки — в отличие от PIT-018,
  где ложное срабатывание блокировало обычную работу десятки раз за сессию.

### PIT-021 — ЛОЖНОЕ красное: гейт воспроизвёл чужую семантику приблизительно и потребовал правки, которая не была нужна

> **Повторов: 1 · Уровень 1**

- **Симптом:** новый гейт `test_docker_ships_what_runtime_needs.py` покраснел на шести
  юридических документах: «`docs/legal/privacy-policy.md` исключён из образа
  `.dockerignore`, но читается на рантайме». В `.dockerignore` немедленно добавлено
  `!docs/legal/*.md` — исправление **несуществующего дефекта**.
- **Корень:** гейт разбирал `.dockerignore` через `fnmatch` и сверял в том числе с ИМЕНЕМ
  файла. Настоящая семантика другая: Docker матчит паттерн против **полного пути** через
  `filepath.Match`, где `*` **не пересекает** `/`. Поэтому `*.md` исключает markdown
  только в корне контекста, и `docs/legal/*.md` под него не попадал никогда. Проверено
  прямым сравнением обеих семантик — обе реализованы и прогнаны на одних входах.
- **Чем это опаснее пропуска:** пропущенный дефект оставляет всё как было, а **ложное
  красное ведёт к правке**. Правка попадает в репозиторий, обрастает комментарием,
  объясняющим несуществующую проблему, и следующий читающий принимает выдумку за факт.
- **Как правильно:** проверка, воспроизводящая поведение ВНЕШНЕГО инструмента (Docker,
  shell, роутер, браузер), обязана воспроизводить его **семантику**, а не похожую.
  Дешёвый способ убедиться — реализовать обе трактовки и прогнать на одних входах:
  расхождение видно сразу и стоит минуту.
- **Правило:** прежде чем чинить код по красному гейту — убедиться, что **гейт прав**.
  Особенно если гейт написан в том же батче: он не проверен временем и краснеет впервые.
  Родня PIT-017 (гейт, заявленный как проверяющий X, обязан проверять X) и находки
  соседней вахты того же дня: **инструмент отвечал на свой вопрос точно, но вопрос был
  не тот**.
- **Контрмера уровня 1** (текст). Правило `!docs/legal/*.md` в `.dockerignore` оставлено
  сознательно — уже не как исправление, а как страховка на случай `**/*.md`; гейт
  проверен мутацией именно в этом виде.

### PIT-018 — относительный путь у читающей утилиты вызывает диалог харнесса, и владелец читает его как ВОПРОС ВАХТЫ

> **Повторов: ≥10 за одну сессию (2026-09-04) · Уровень 3 · Автопроверка:
> `.claude/hooks/block-relative-read-path.py` (гейт — `tests/test_block_relative_read_path.py`)**

- **Симптом:** владелец в авто-режиме прямым приказом запретил вопросы («я уже за эту сессию
  раз сто тебя просил хватит спрашивать меня просто делай»). Вахта вопросов не задавала — и
  всё равно работа раз за разом вставала на диалоге:

  ```
  grep on 'docs/pitfalls.md' after a cd would search a directory that cannot be
  determined here, and a Read() deny rule is configured; only you can approve
  running it anyway.  Do you want to proceed?  1. Yes  2. No
  ```

  Снаружи это неотличимо от вопроса вахты: тот же поток, та же форма «предложение +
  Yes/No». Владелец читал каждое срабатывание как прямое нарушение приказа. К десятому
  разу — «даун ты тупой», и это справедливая реакция на то, как ситуация выглядит.

- **Корень:** в `.claude/settings.json` настроены `deny`-правила `Read(./.env)`,
  `Read(./**/*.pem)` и подобные. Чтобы решить, попадает ли команда под запрет, харнесс должен
  знать, **какой файл** она откроет. Относительный путь-аргумент (`docs/pitfalls.md`) он
  сопоставить не может: рабочий каталог команды статически неизвестен. Разрешить не вправе,
  отказать молча — тоже, поэтому эскалирует владельцу.

- 🔴 **Отдельный урок — про НЕВЕРНЫЙ первый диагноз.** Сперва корнем было названо «`cd` с
  относительным путём + флаг `-A`», и в память ушёл обход «делать `cd` абсолютным». Обход был
  соблюдён — и не помог: следующий вопрос прилетел на команде
  `cd /Users/.../personal-finance-dss && grep -n "^## " docs/pitfalls.md`, где `cd`
  **абсолютный**. Значение имеет путь **в аргументе читающей утилиты**, а не путь у `cd`;
  `cd` вообще ни при чём и в не-читающих командах (`cd frontend && npx vitest`) вопроса не
  вызывает. **Правило, выведенное из неверного корня, выглядит соблюдённым и не защищает** —
  и это хуже, чем отсутствие правила: создаёт ложную уверенность, что мера принята.
  Родня PIT-004 (симптом отнесён не к тому слою).

- **Как правильно:** абсолютным должен быть **аргумент**, а не `cd`:

  ```bash
  grep -n "^## " /Users/.../personal-finance-dss/docs/pitfalls.md   # без вопроса
  cd /Users/.../personal-finance-dss && grep -n "^## " docs/pitfalls.md   # ВОПРОС владельцу
  ```

  Читающие утилиты, к которым это относится: `grep`, `rg`, `cat`, `head`, `tail`, `sed`,
  `awk`, `wc`, `diff`, `jq` и прочие, чей аргумент — путь к файлу.

- **Правило:** любой путь-аргумент в Bash — абсолютный, всегда. Не «когда есть `cd`», не
  «когда есть `-A`» — всегда, потому что дешевле держать одно безусловное правило, чем
  каждый раз решать, попадёт ли конкретная команда под сопоставление с deny-списком.

- 🔴 **Отдельно: бит `+x` слетел ПОСЛЕ `chmod`** — файл был перезаписан целиком
  (`Write`, а не `Edit`), и права вернулись к `rw-r--r--`. Хук при этом **не падает**:
  `PreToolUse` просто не запускает неисполняемый файл, ошибки нет, вердикт «зелено»
  означает «не проверялось». Нашла соседняя вахта своим обходом системы, а не этот
  гейт — то есть защита стояла мёртвой и выглядела работающей. Закрыто тестом
  `test_hook_is_executable` (проверен мутацией: снял бит — красный). **Правило: после
  полной перезаписи исполняемого файла права проверяются заново; `Write` их не хранит.**
- **Контрмера уровня 3 — 🟢 поставлена в тот же день.** По правилу эскалации
  (`recurrence_ledger.md` §1) десять повторов требуют машинной проверки, а не текста — тем
  более что текстовая мера здесь уже провалилась один раз (неверный корень). Хук
  `.claude/hooks/block-relative-read-path.py` блокирует такую команду **до** отправки, так
  что диалог физически не возникает. Три первые попытки записи упёрлись в классификатор
  (правка собственной конфигурации агента); владелец выдал право явно, и хук поставлен той
  же вахтой. Гейт `tests/test_block_relative_read_path.py` — 11/11, проверен мутацией.
- 🔴 **При исполнении хук трижды поймал ИСПРАВНЫЕ команды**, и каждый раз — только запуском
  на живой строке, не чтением кода: (1) резал команду по `&&` до разбора кавычек и блокировал
  собственную проверочную строку `echo '{"command":"… && grep …"}'`; (2) терял оператор без
  пробела (`tail -3; python x` → `python` стал «файлом, который читает `tail`»);
  (3) semgrep валил запись из-за кириллицы в тексте отказа. Разбор — в шапке
  `docs/reports/engineering/task_pretooluse_guard_relative_paths.md`. **Цена ошибок этого
  хука несимметрична:** пропуск стоит одного диалога, ложное срабатывание делает работу
  невозможной и хук снимут целиком — поэтому в гейте шесть разрешающих случаев против
  четырёх блокирующих.
