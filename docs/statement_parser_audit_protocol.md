# Протокол независимого аудита парсера выписок

**Статус:** действующий · **Зачем:** получить честную, воспроизводимую оценку точности импорта
операций **не от того, кто его писал**.

---

## 1. Проблема, ради которой существует этот документ

Парсер, тесты к нему, генератор синтетики и сам механизм сверки написаны **одним исполнителем**.
Все опубликованные цифры («сверено 10 из 11», «покрытие 92.7%», «625 синтетических выписок») — это
самооценка. Она полезна, но у неё есть три встроенных изъяна:

1. **Замкнутый круг.** Генератор синтетики знает ровно те шаблоны, что и парсер. Он не может
   сгенерировать формат, о котором автор не догадывается.
2. **Слепое пятно на своих же допущениях.** Все найденные дефекты имели один корень — неверное
   представление о формате банка. Тот же человек с тем же представлением не найдёт следующий.
3. **Свидетель на своей стороне.** Разработчик выбирает, какие свидетели подключать и где ставить
   порог. У Сбера свидетеля «изменение остатка» я отключил обоснованно — но проверить это
   обоснование должен кто-то другой.

Аудит нужен не потому, что кому-то не доверяют, а потому что **изнутри системы её ошибку не видно**.

## 2. Кто проводит

**Требования к аудитору (жёсткие):**
- **не читал код парсера** и не участвовал в его разработке;
- не имеет доступа к `app/services/statement_parser.py`, `statement_reconcile.py`,
  `tools/statement_templates/synth.py` и к тестам до окончания аудита;
- знает предметную область (умеет читать банковскую выписку глазами).

**Как это организовать практически.** По ритуалу независимого эксперта: чистая сессия ИИ, которой
**не даётся** контекст проекта — только выписки, запущенное приложение (или CLI) и этот протокол.
Либо живой человек. Принимающий вахту разработчик участвовать не может: он читал код и загрязнит
результат.

## 3. Материал: holdout — главное условие честности

**Аудит проводится ТОЛЬКО на файлах, которых парсер никогда не видел.** Всё, на чём он уже
чинился (11 PDF, CSV, XLSX, 1C из текущего набора), для аудита непригодно: на них он подогнан.

Требования к holdout-набору:

| Параметр | Минимум | Зачем |
|---|---|---|
| Файлов | 15–20 | меньше — статистика ни о чём |
| Банков | ≥ 5, из них ≥ 2 не из шести знакомых | проверка гипотезы «универсальный парсер держит хвост» |
| Форматов | PDF, CSV, XLSX, 1C | у каждого свой путь в коде |
| Типы счетов | дебетовый, кредитка, накопительный | у кредитки «остаток» = лимит, поведение другое |
| Периоды | разные, в т.ч. месяц с 200+ операциями | пагинация, повтор шапки |
| Негативные | справка, реквизиты, скан, битый PDF, пустой счёт | проверка честного отказа |

**Файлы holdout не показываются разработчику до конца аудита и не попадают в фикстуры.** Как только
файл использован для починки — он перестаёт быть holdout навсегда.

## 4. Что именно проверяется

| # | Гипотеза | Как проверить | Порог приёмки |
|---|---|---|---|
| H1 | Суммы и знаки прочитаны верно | сверка с контрольными итогами выписки | 100% на файлах, где банк печатает итоги |
| H2 | Набор операций полон (ничего не пропущено и не задвоено) | счётчик операций банка; ручной пересчёт строк | 100% |
| H3 | Описание и дата каждой операции верны | **ручной ground truth** (§5, этап 2) | ≥ 99% полей |
| H4 | Нет тихих ошибок: неверный импорт невозможен | негативные кейсы + сверка | **0 тихих ошибок** |
| H5 | Ошибка пользователя не ломает импорт | загрузить выписку, выбрав в форме ЧУЖОЙ банк | банк определяется по файлу |

H4 — самая важная. Тихая ошибка (импортировали, показали «успех», данные неверны) хуже отказа:
пользователь получит финансовый совет, посчитанный по мусору, и не узнает об этом.

## 5. Процедура

**Этап 0. Подготовка.** Владелец собирает holdout (§3), передаёт аудитору файлы и этот протокол.
Код не передаётся. Фиксируется версия приложения.

**Этап 1. Слепой прогон.** Аудитор по каждому файлу запускает:
```
python -m tools.statement_audit.reconcile <файл>
```
и/или загружает файл в приложение. Записывает в таблицу: файл → банк (определён приложением) →
число операций → статус сверки → сообщение.

**Этап 2. Ручной ground truth — единственная проверка описаний и дат.**
Аудитор берёт **2–3 небольшие выписки (до 15 операций)** и **вручную, глазами**, выписывает каждую
операцию: дата, тип, сумма, описание. Делает это **до** того, как посмотрит на вывод парсера
(иначе сработает якорение). Затем сравнивает поле в поле.

Это дорого и не масштабируется, поэтому — только на 2–3 файлах. Но это **единственный** способ
проверить то, чего сверка сумм не проверяет.

**Этап 3. Негативные и adversarial-кейсы.** Проверить, что приложение честно отказывается и
объясняет причину, а не показывает «импортировано 0 операций»:
- справка об остатке / реквизиты / справка о задолженности;
- PDF-скан (картинка без текстового слоя);
- битый/обрезанный PDF;
- выписка пустого счёта (0 операций — это КОРРЕКТНО, не дефект);
- выписка одного банка с выбором другого банка в форме (H5);
- файл вообще не выписка (договор, чек).

**Этап 4. Отчёт.** Таблица результатов + метрики §6 + список расхождений. Расхождения фиксируются
как факты, **без попыток починить по ходу**: правка во время аудита обесценивает выборку.

## 6. Метрики

| Метрика | Формула | Целевое |
|---|---|---|
| M1 — покрытие сверкой | файлов со статусом `ok` / файлов с контрольными итогами | 100% |
| M2 — **тихие ошибки** | импортов с неверными данными и статусом «успех» / всех импортов | **0** |
| M3 — построчная точность | верных полей / всех полей (ручной ground truth) | ≥ 99% |
| M4 — честный отказ | распознанных негативных кейсов / всех негативных | 100% |
| M5 — доля читаемых файлов | файлов с операциями > 0 / выписок с операциями | замер, не порог |

**M5 намеренно без порога.** Если незнакомый банк не читается — это ограничение, о котором
пользователю сказано честно; это не то же самое, что прочитать неверно. Смешивать M5 и M2 —
главная ошибка при оценке парсера.

## 7. Как не обмануться (антипаттерны аудита)

1. **Не использовать `tools/statement_templates/synth.py`.** Генератор построен на тех же
   допущениях, что и парсер: круг замкнётся, всё будет зелено, смысла ноль.
2. **Не показывать аудитору код.** Иначе он проверит соответствие коду, а не реальности.
3. **Не чинить во время аудита.** Сначала весь прогон и отчёт, потом правки.
4. **Не переиспользовать holdout.** Файл, на котором чинились, для следующего аудита мёртв.
5. **Не считать «0 операций» дефектом по умолчанию.** Справка и пустой счёт — законные нули.
   Дефект — это тихая неверность (M2).
6. **Не заменять ручной ground truth сверкой сумм.** Они проверяют разные вещи.
7. **Не усреднять по банкам.** «97% в среднем» бессмысленно: важно, есть ли банк, который читается
   неверно молча.

## 8. Что делать с результатом

- Каждое расхождение → карточка дефекта (`docs/reports/bug_report_template.md`) с приложением
  обезличенной фикстуры, воспроизводящей формат.
- M2 > 0 → это блокер выпуска: тихая ошибка в финансовом продукте недопустима.
- M3 < 99% → разбор по полям (чаще всего страдает описание, а не сумма).
- После правок — **повторный аудит на НОВОМ holdout**, старый уже сгорел.
- Итог аудита — отчёт в `docs/reports/audits/`, строка в реестре.

## 9. Минимальная версия аудита (если сил мало)

Если на полный протокол нет ресурса, минимум, который уже даёт честный сигнал:

1. 5 свежих выписок, которых парсер не видел, желательно от 2 незнакомых банков.
2. Прогнать `tools.statement_audit.reconcile`, записать статусы.
3. **Одну** выписку на 10 операций пересчитать вручную и сверить поле в поле.
4. Подсунуть одну справку и одну выписку с неверно выбранным банком.

Это займёт час и ответит на главный вопрос: **бывает ли тихая неверность**.
