# Методичка: контекст на трёх уровнях — запрос, чат, Проект

Собрано 01.08.2026. Исходник — `raw/06_context_management_2026-08-01.md`.
Метки: [Ф] факт · [О] оценка · [Г] гипотеза · «данных нет» — публично не существует.

---

## 1. Две стены, которые легко спутать

Это главное. Сообщения похожи по тону, но природа разная, и лечение противоположное. [Ф]

| | Стена контекста | Стена лимита |
|---|---|---|
| Сообщение | «This conversation is too long to continue. Start a new chat, or remove some tools…» | «You're out of usage credits… wait until 3:00 AM…» |
| Природа | исчерпано окно **этого чата** | исчерпан лимит **плана** |
| Новый чат помогает | **да** | нет |
| Покупка кредитов помогает | **нет** | да |
| Само пройдёт | никогда | через ~5 ч (окно) или в день недельного сброса |

Практический вывод: прежде чем что-то делать, прочитать, какая именно стена. Покупка кредитов
в первом случае — деньги на ветер; ожидание во втором — потерянные часы.

## 2. Один переключатель, который меняет всё

**Code Execution включён → чат почти не умирает.** Дословно из справки: «For users on paid
plans with code execution enabled, Claude automatically manages your conversation context» —
при приближении к лимиту ранние сообщения суммируются, и это **не расходует лимит плана**. [Ф]

Выключен — автосжатия нет, чат упирается в жёсткую стену без восстановления. [Ф]

Проверить и включить: настройки → возможности. Это первое, что стоит сделать.

## 3. Из чего складывается контекст чата

Каждое сообщение отправляет **весь накопленный контекст заново**. Крупные статьи расхода: [Ф]

- **Описания коннекторов** — самая недооценённая: GitHub ≈26 000 токенов, Slack ≈21 000,
  Jira ≈17 000. Anthropic приводит собственный случай: определения инструментов занимали
  134 000 токенов до оптимизации. Одиннадцать включённых коннекторов способны уронить
  **новый** чат сразу. Отсюда и формулировка «remove some tools to free up space».
- **Вложенные файлы** — остаются в контексте навсегда и пересылаются с каждым сообщением.
  Отсюда правило: не переприкреплять уже загруженное.
- **История сообщений** — линейно растёт, в длинном чате главный потребитель.
- **База знаний Проекта** — до включения RAG грузится целиком в каждый чат.

**Индикатора заполнения контекста чата в вебе нет.** Settings → Usage показывает лимиты плана,
а не контекст. [Ф — данных нет по индикатору]

## 4. Размер окна

| Модель | Окно в чате claude.ai |
|---|---|
| Opus 5, Sonnet 5 | 1 000 000 |
| Opus 4.8 / 4.7 / 4.6, Sonnet 4.6 | 500 000 |
| Остальные (в т.ч. Haiku 4.5) | 200 000 |

Окно в чате **меньше**, чем у той же модели в Claude Code: там до 1M, но Pro-пользователю для
1M на Opus нужно включить usage credits. [Ф]

## 5. Что теряется при сжатии

Порог срабатывания — около **83,5%** окна. [О] Сжатие сохраняет смысл, но теряет точность:
конкретные числа, дословный код, ранние инструкции, связи между файлами. После двух-трёх
проходов понимание проекта заметно деградирует — идёт «сжатие сжатия». [Ф]

Признаки, что это уже произошло: Claude забыл раннюю договорённость, противоречит принятому
решению, заново спрашивает отвеченное, отвечает общо. Anthropic признаёт прямо: «as a
conversation grows, response quality degrades». [Ф]

**Вывод:** не дожидаться автосжатия. Своя сводка на 70% лучше машинной на 95%.

## 6. Проект и порог RAG

Официально RAG включается при приближении к лимиту окна и расширяет ёмкость до 10×. [Ф]
Но независимый тест (баг-репорт #25759) зафиксировал включение RAG **при 13 файлах и 2%
ёмкости** — то есть порог сработал по **числу файлов**, а не по объёму. При 10–12 файлах —
прямая загрузка, при 13 — RAG; удаление самого крупного файла режим не вернуло. [Ф]

По качеству — **конфликт источников**: Anthropic заявляет сохранение точности, тот же тест
сообщает обратное (частичные фрагменты, потеря связей между файлами, падение следования
инструкциям). Помечено как конфликт, а не разрешено в чью-то пользу.

**Практика:** держать **немного крупных файлов** вместо множества мелких, имена описательные.
Инструкции Проекта — до ~8 000 символов, применяются к каждому чату и расходуют его контекст. [Ф]

## 7. Архивы кода в чат — почему это не работает

Zip официально **не входит** в список поддерживаемых типов. [Ф] Даже если пройдёт по размеру,
70 МБ кода при распаковке в текст дают сотни тысяч токенов — превышает даже окно в 1M. [О]
И этот текст летит в окно **с каждым сообщением**.

Правильные пути: GitHub-коннектор с выбором только нужных файлов; база знаний Проекта;
вставка нужного фрагмента текстом; для крупной кодовой базы — **Claude Code**, где файлы
читаются локально, а не живут в контексте.

## 8. Эстафета между чатами

Начинать новый чат на **~70%**, а не на стене. Что переносить обязательно:

1. Цель и текущая веха.
2. Ключевые архитектурные решения и договорённости.
3. Стек и жёсткие ограничения.
4. Что сделано, что осталось.
5. Открытые вопросы.

Хранить это файлом в базе знаний Проекта и обновлять в конце сессии — тогда эстафета
занимает одну вставку, а не полдня восстановления контекста. Для FINPILOT такой файл уже
есть по смыслу: WATCHLOG §0 «RESUME POINT».

## 9. Спасение умирающего чата

1. Пока Claude ещё отвечает — попросить свести всё: цель, решения, код, числа, остаток.
2. Скопировать наружу; при риске — Settings → Privacy → Export data (zip с JSON, до 24 ч).
3. Новый чат в том же Проекте, вставить сводку, переприкрепить файлы.

История умершего чата **не удаляется** — читать и копировать можно, писать нельзя. [Ф]

## 10. Что из этого меняется в работе над FINPILOT

- Включить Code Execution — превращает жёсткую стену в мягкое сжатие.
- Выключать лишние коннекторы перед длинной сессией: десятки тысяч токенов на пустом месте.
- Перестать возить 70-мегабайтные архивы в чат; для кода — Claude Code.
- База знаний Проекта — мало крупных файлов, не много мелких.
- Эстафета на 70%, а не на стене; сводка — в WATCHLOG.
