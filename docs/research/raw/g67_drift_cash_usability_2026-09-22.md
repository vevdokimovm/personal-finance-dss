### Вызов 2 — WebSearch: «справочник MCC-кодов версии обновление классификатор платёжных систем»

Результат: MCC — 4-значный код, стандартизован международно (Visa/Mastercard/Amex/Мир),
«один и тот же код используется... независимо от эмитента и платёжной системы» — то есть
базовый международный список MCC (ISO 18245) относительно стабилен как СТАНДАРТ, но
конкретные привязки «торговая точка → MCC» меняются постоянно на стороне эквайера/банка.
Найдены народные справочники (mcc-codes.ru, mcc-cod.ru, infotables.ru, merchantpoint.ru) —
без версионирования, без дат обновления на уровне сниппета. Отдельно найден официальный
документ НСПК СБП: «Стандарт ОПКЦ СБП. Требования к присвоению кодов категорий ТСП»
(sbp.nspk.ru/file/trebovaniya-prisvoeniyu-kodov-kategorij-tsp.pdf) — целевой источник для
регламента присвоения кодов в РФ, требует открытия.
Ссылки: mcc-codes.ru, mcc-cod.ru, infotables.ru/produkty-pitaniya/1112-kody-mcc,
merchantpoint.ru/mcc, sbp.nspk.ru/file/trebovaniya-prisvoeniyu-kodov-kategorij-tsp.pdf,
sravni.ru/text/mcc-kody---proveryaem-chtoby-poluchit-keshbek, htmlweb.ru/other/mcc_bank_terminal_code.php.

но правила ПРИСВОЕНИЯ и группировки — российская надстройка НСПК/СБП, которая живёт своей
версионностью отдельно от международного ISO 18245.

Это прямой ответ для Б-02 по классу «отсутствующее значение в справочнике»: официальный

присваивает их) это не является прямым правилом отказа — но задаёт отраслевую норму:
«при отсутствии эталона — не выдумывать, регистрировать/эскалировать разрыв».

**Раздел 2.7 «Ответственность Участника СБП» — дословно (сжато):**
«Все Участники СБП несут ответственность... за то, чтобы каждое ТСП было зарегистрировано
в ОПКЦ СБП с МСС, наиболее соответствующим его виду деятельности... ОПКЦ СБП имеет право
потребовать от Участника СБП... применить иные меры воздействия».
Это регламент ответственности НА СТОРОНЕ ЭКВАЙЕРА/БАНКА за корректность присвоения — не за
дрейф справочника у потребителя данных (как FINPILOT). Отрицательный результат: в документе
НЕТ раздела про поведение получателя данных (не участника СБП) при столкновении с MCC,
которого он не знает или который изменил группу задним числом.

**Раздел 2.4** (побочная находка, релевантна для качества данных): MCC «нигде более не
классифицированные»/«прочее» — «должны присваиваться ТСП только в случае, когда никакой
другой MCC не применим... Участнику СБП запрещается присваивать» их, если есть более точный
код. Это объясняет, почему «мусорные» MCC в выписках — признак либо старого договора ТСП,
либо нарушения регламента эквайером, а не случайность.

автоматического фолбэка без человеческого контроля — $440 млн убытка.
🔴 Это ПРЯМО применимо к формулировке правила для фолбэк-числа 0,14 в каноне FINPILOT: сейчас
у числа «прочерк» в графе источника и, судя по формулировке задачи, нет явного лога «когда и
почему сработал фолбэк» — отраслевая норма требует именно это, не просто наличие запасного
числа.

### Вызов 25 — WebFetch: `eodhd.com/.../real-time-market-data-reliability-stale-price-detection-rest-fallback-and-websocket-recovery`

🔴 **Дословная модель состояний свежести данных (адаптируется под класс актива):**
«LIVE: quote age is 3 seconds or less» → «DEGRADED: 3–10 seconds» → «STALE: above 10 seconds»
(пороги конкретно для рыночных котировок реального времени — не переносимы буквально на
месячный цикл FINPILOT, но САМА МОДЕЛЬ трёх состояний переносима).
Обязательная маркировка источника каждого значения: «Every price should be labeled as
`websocket`, `rest_fallback`, `cached`, `previous_close`, or `market_closed`» — то есть отрасль
требует, чтобы ПОТРЕБИТЕЛЬ данных (не только источник) знал, откуда взято текущее значение и
насколько оно свежее, а не просто получал число.
Путь деградации, дословно: «LIVE → DEGRADED... DEGRADED → STALE... STALE → FALLBACK... FALLBACK
→ RECOVERING... RECOVERING → LIVE (после 3+ подтверждённых обновлений)... STALE → DEAD при
отказе fallback». Ключевой защитный механизм: «Отказ использовать кэшированные значения для
торговых сигналов» — то есть кэш годится для ОТОБРАЖЕНИЯ (не вводить пользователя в заблуждение
тишиной), но НЕ годится как основание для действия/решения без явной пометки.

**Синтез вахты по этим двум источникам для Б-02 (не решение, наблюдение):** отраслевая практика
за пределами РФ различает три разных вопроса, которые канон FINPILOT сегодня смешивает в одно
число 0,14: (а) сколько ждать, прежде чем считать значение устаревшим; (б) чем заменить —
кэш/последнее известное/консервативная оценка; (в) как ПОМЕТИТЬ результат расчёта, чтобы
пользователь и лог знали, что использован фолбэк, а не свежий источник. У 0,14 есть только (б).
