# Г66 / Б-04 — СВОЙ ЗАМЕР: на сколько должен ошибиться вход, чтобы сменился совет

Дата: 22.09.2026. Вахта J. Без агента — замер на собственном коде.
Скрипты дословно рядом: `_b04_sensitivity.py` (смена альтернативы) и `_b04_magnitude.py`
(величина сдвига). Среда: `.venv` проекта, Python 3.13.15.

**Откуда пункт.** Аудит покрытия № 7, ось Б: связка «ошибка входа → смена решения» не
исследовалась ни разу. Г40 мерил чувствительность к **весам** (#5: смена нормализации меняет
план в 41 % портретов) и к **сетке** (#21: шаг 1 % вместо 10 % меняет план в 22,5 %), Г20 мерил
точность разбора выписки саму по себе. Цепочки между ними не было.

## Метод

400 синтетических портретов, генератор с фиксированным зерном `20260922`: доход из шести
уровней 45–250 тыс. ₽, расходы 45–80 % дохода, 1–3 обязательства со ставками 5,5–35 %
и платежом 2–5 % от тела, 1–2 цели со сроком 4–48 мес., ликвидный остаток 0,2–4,0 месячных
дохода, риск-профиль 1–5 случайно.

Полный конвейер продукта на каждом прогоне: `generate_alternatives` → `evaluate_alternative`
→ `filter_alternatives` → `rank_alternatives`, победитель по лексикографике
`(floor_level, utility)` — то есть ровно то, что увидит пользователь.

Возмущается **оценка расходов** (сумма e_j) на ±ε, берётся худшая из двух сторон. Это
моделирует то, что реально делает парсер: не распознал часть операций, отнёс не в ту
категорию. Портретов с допустимым решением — **274 из 400** (у остальных ресурс ≤ 0 или
фильтр отсёк всё).

🔴 **Первый прогон был неверным, и это стоит записи.** Я сравнивал победителей **по рублям**
(`x_obligations`, `x_reserve`, `x_goals`) и получил «100 % при ошибке 0,5 %». Рубли меняются
всегда, раз меняется сам поток Rt — сравнивать надо **доли** (идентификатор альтернативы).
Ошибка поймана до записи вывода; правильное сравнение — по `id` альтернативы.

## Результат 1. Как часто вообще меняется рекомендация

| Ошибка в расходах | Сменилась альтернатива |
|---:|---:|
| **0,5 %** | **56 из 274 — 20,4 %** |
| 1 % | 62 — 22,6 % |
| 2 % | 64 — 23,4 % |
| 3 % | 62 — 22,6 % |
| 5 % | 68 — 24,8 % |
| 10 % | 94 — 34,3 % |
| 15 % | 98 — 35,8 % |
| 20 % | 102 — 37,2 % |

Ни при одном возмущении до 20 % не сменился совет у **125 портретов (45,6 %)**.
Сменился уже при ошибке ≤ 2 % — у **70 (25,5 %)**.

Немонотонность (22,6 → 23,4 → 22,6 %) не дефект замера: каждое ε проверяется независимо,
и «сменился при 2 %» не обязано влечь «сменился при 3 %».

## 🔴 Результат 2. Насколько ДАЛЕКО уезжает план — здесь главное

Сдвиг считается как половина суммы модулей разностей долей, то есть **какая доля потока
переехала в другое русло**: 0 пп — план тот же, 100 пп — полностью противоположный.

| Ошибка в расходах | Медиана сдвига | p90 | Максимум | Сдвиг ≥ 10 пп |
|---:|---:|---:|---:|---:|
| **0,5 %** | **0,0 пп** | **20,0 пп** | **90,0 пп** | **15,3 %** |
| 2 % | 0,0 пп | 30,0 пп | 90,0 пп | 21,5 % |
| 5 % | 0,0 пп | 50,0 пп | 100,0 пп | 23,4 % |

🔴 **Распределение двухрежимное, и это ответ на вопрос пункта.** У типичного пользователя
(медиана) ошибка входа не меняет ничего вовсе. Но у заметного меньшинства план
переворачивается целиком: при ошибке всего **0,5 %** шестая часть портретов уезжает
на 20 пп и более, а максимум — **90 пп**, то есть почти полная смена направления денег.
При ошибке 5 % встречается сдвиг **100 пп** — противоположный план.

**Почему так, а не плавно.** Это прямое следствие дефекта Г40 #4: решение в 91 % случаев —
угол симплекса, то есть план не «немного смещается», а **перескакивает** из одного угла
в другой, когда полезности двух углов сравниваются. Рядом с точкой равенства сколь угодно
малая ошибка входа даёт максимально возможный сдвиг плана. Настоящая причина
чувствительности — не арифметика ошибки, а **геометрия решения**.

## Что из этого следует (материал, не решение)

1. **Требования к точности парсера теперь выводимы из требования к решению.** Раньше цель
   точности была «чем выше, тем лучше». Замер даёт связку: чтобы удержать долю
   переворачивающихся планов ниже 15 %, ошибка оценки расходов должна быть **меньше 0,5 %** —
   а это заметно строже, чем даёт разбор PDF на практике.
2. **Класс тестов, которого нет.** Все тесты ядра проверяют правильность формулы на точном
   входе. Теста «решение устойчиво к возмущению входа» нет ни одного. Готовый стенд —
   скрипты рядом с этим файлом.
3. **Экран «данных слишком мало, советовать не будем» получает основание.** Не общий принцип
   осторожности, а число: если сверка сальдо показывает расхождение выше порога, попадание
   в двухрежимный хвост становится вероятным.
4. **Связь с Б-01.** При переносе разбора на устройство точность парсера меняется вместе
   с языком и библиотекой. Этот замер — инструмент, которым надо мерить последствия той
   замены, а не только совпадение рёбер.

## Границы замера — что он НЕ доказывает

- Портреты **синтетические**; распределение параметров задано мной, а не снято с популяции.
  Доли (20,4 %, 15,3 %) верны для этого генератора, а не для реальных пользователей.
- Возмущался **только** агрегат расходов. Ошибка в доходах, в ставках и в платежах
  не проверялась; ошибка категоризации (перенос суммы между категориями при неизменном
  итоге) — тоже.
- Профиль риска выбирался случайно, разбивки по профилям нет.
- 274 портрета — достаточно для порядка величины, мало для доверительных интервалов.
