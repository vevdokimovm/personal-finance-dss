## П4.1. Faktura.ru — живой формат выгрузки 🟢 ДОБЫТ (главный пробел прохода 3 закрыт)

**Вывод словами.** Дыра «нет ни одного образца Faktura» закрыта. Оказалось, что ручная выгрузка
Faktura.ru — **не `.xlsx`, а XML Spreadsheet 2003** (тот самый «Excel 2003 XML», который Excel
открывает как книгу и который в интерфейсе подписан «Excel»). Мы три прохода искали не тот файл:
искали `.xlsx`/`.xls`, а банк отдаёт XML с namespace `urn:schemas-microsoft-com:office:spreadsheet`.
Плюс сверх ожидания найден **живой HTTP/JSON API Faktura** — то есть у этой платформы выписку можно
брать вообще без файла.

### П4.1.1. Источник и его честный статус

- Репозиторий `mrflxxxme/dds2-sandbox` (GitHub, найден через `gh api search/code`,
  запрос `faktura.ru statement export`).
- Парсер: `backend/etl/parsers/faktura.py`, класс `FakturaParser` —
  `https://github.com/mrflxxxme/dds2-sandbox/blob/HEAD/backend/etl/parsers/faktura.py`
- Образец: `tests/fixtures/faktura_wb_bank_sample.xml`, 9 184 байта, 10 операций —
  скачан в `~/raw-originals/finpilot-data/statements/_platform_faktura/live_sample/faktura_wb_bank_sample.xml`
- 🔴 **Честно про класс материала:** это **тестовая фикстура**, а НЕ выгрузка из банка. Суммы, ИНН
  контрагентов и номера счетов синтетические. Но **вёрстка (порядок и имена колонок) снята с реальной
  выгрузки** — парсер написан против живого банка и работает в проде проекта (`faktura_statement_sync.py`
  в планировщике, 4 синхронизации в сутки). То есть структура — первичная, содержимое — нет.
  По нашей шкале это класс «живая вёрстка, синтетическое содержимое», а не «живой файл».

### П4.1.2. Точная структура листа (первичные данные)

Корень `<Workbook xmlns="urn:schemas-microsoft-com:office:spreadsheet">`, директива
`<?mso-application progid="Excel.Sheet"?>`, кодировка `utf-8`. Один лист: **`ss:Name="Выписки"`**.
Первая строка — шапка, ровно 11 колонок в этом порядке:

| # | Заголовок в файле | Что внутри | Тип ячейки |
|---|---|---|---|
| 1 | `Плат.пор. №` | `Плат.пор. № 101 от 05.03.2026` — номер И дата одной строкой | String |
| 2 | `Дата` | `05.03.2026` — **ДД.ММ.ГГГГ** | String |
| 3 | `Корреспондент` | имя второй стороны (`ИП Иванов А.П.`) | String |
| 4 | `ИНН` | ИНН контрагента | String |
| 5 | `КПП` | может быть пустым (ИП) | String |
| 6 | `Счёт` | счёт контрагента, 20 знаков | String |
| 7 | `БИК` | БИК банка контрагента | String |
| 8 | `Вх.остаток` | входящий остаток | **Number** |
| 9 | `Оборот Дт` | расход | **Number** |
| 10 | `Оборот Кт` | приход | **Number** |
| 11 | `Назначение платежа` | назначение | String |

🔴 **Четыре ловушки формата, каждая проверяется по файлу:**
1. **Идентификатора операции НЕТ.** Ни `id`, ни `absOperationId` в файле нет — только номер платёжного
   поручения внутри текстовой строки колонки 1. Дедупликацию придётся строить на хеше
   (дата + сумма + счёт + назначение), как это и сделано у автора (`make_txn_id`).
2. **Направление — двумя колонками** `Оборот Дт` / `Оборот Кт`, в незадействованной стоит `0`, а не пусто.
   Отдельного признака дебет/кредит нет (та же болезнь, что у `iBank2` из прохода 3).
3. **Суммы — `ss:Type="Number"`, точка как десятичный разделитель** (XML-число, не локаль).
   То есть здесь запятая НЕ встречается — поправка к предположению прохода 3
   («Faktura-Excel — рубли с запятой, предположительно»).
4. **`ss:Index` — разрежённые строки.** Excel 2003 XML пропускает пустые ячейки атрибутом
   `ss:Index="N"`; наивный `findall` ломает выравнивание колонок. Автор парсера написал под это
   отдельный метод `_row_cells_indexed`. Для нас — обязательное требование к разборщику.
   Плюс: `Корреспондент` — это **другая сторона**, не мы; поле «мы» в файле отсутствует.

### П4.1.4. 🔴 Сверх задания: у Faktura есть читаемый API выписки

`backend/integrations/faktura_api.py` того же репозитория — клиент приватного HTTP/JSON API,
по словам автора «reverse-engineered from the official 1C extension (Faktura-DirectBank)»,
READ-поверхность «verified live»:

- Хост `business.faktura.ru`, префикс `/erpws/2.0`.
- Аутентификация: `POST /erpws/2.0/login/authByUsernamePassword`,
  `application/x-www-form-urlencoded`, `username=f2b-<login>&password=<password>` → `{"token": "<JWT>"}`,
  дальше `Authorization: Bearer <JWT>`.
- Счета: `GET /erpws/2.0/accounts` → `{"accountList": [...]}`.
- Движения: `GET /erpws/2.0/accounts/{id}/motions?fromDate&toDate&skipRecords`
  → `{"data": {"operationInfo": [...]}, "hasNext": bool}`, пагинация по `hasNext`.
- Форма операции: `id`, `absOperationId`, `dc` (**bool**: `true` = списание, `false` = поступление),
  `date` в **ISO `YYYY-MM-DD`** (а не `ДД.ММ.ГГГГ`, как в файле), `payDoc.<тип>.{sum, purpose, payer{…}, payee{…}}`.

🔴 **Значение для FINPILOT.** Это первое найденное за четыре прохода доказательство, что у
российской платформы ДБО есть **машинный канал выписки помимо файла** — и в API идентификатор
операции (`id`, `absOperationId`) **есть**, в отличие от файла. Но: (а) канал приватный, не публичная
документация, договором не гарантирован; (б) это `business.faktura.ru` — **юрлица**, не физлица;
(в) логин/пароль в чужую систему — для нас неприемлемый способ доступа к деньгам пользователя
(и по 152-ФЗ, и по здравому смыслу). Записываем как факт о рынке, не как план интеграции.

### П4.2.1. `iBank2` — словарь тегов из чужой реализации 🟢

Источник: `n-gribov/cyberft_terminal`, файл
`app/src/addons/edm/models/IBankStatement/IBankStatementType.php`
(`https://github.com/n-gribov/cyberft_terminal/blob/HEAD/app/src/addons/edm/models/IBankStatement/IBankStatementType.php`).
CyberFT Terminal — терминал юридически значимого документооборота с банками, то есть код писался
против живых выгрузок, а не против PDF-спецификации.

Разбор: строки режутся `/[\r\n]+/`, блоки `$OPERS_LIST … $OPERS_LIST_END` пропускаются как рамка,
операция — между `$OPERATION` и `$OPERATION_END`, внутри `ТЕГ=значение` (`explode('=', …, 2)` —
значение может содержать `=`). **Теги сравниваются без учёта регистра** (`mb_strtolower`).
Неизвестный тег — пропускается, не ошибка.

**Шапка (8 тегов):** `ACCOUNT`, `BEGIN_DATE`, `END_DATE`, `IN_REST`, `OUT_REST`, `CREDIT`,
**`DEBET`** (🔴 именно так, не `DEBIT` — опечатка вендора, закреплённая в формате), `LAST_OPER_DAY`.

**Операция (39 тегов).** Ключевые:
`OPER_ID`, `OPER_DATE`, `OPER_CODE`, `DOC_NUM`, `DOC_DATE`, `AMOUNT`, `RUR_AMOUNT`, `CODE`,
`OPER_DETAILS` (назначение), `QUEUE` (очерёдность), `INCOME_BANK_DATE`, `CREDIT_DATE`, `VALUE_DATE`,
`KEY_ID`, `SIGN_TS`, `SIGN` (подпись).
Две стороны — **симметричными семействами**: `CORR_*` (корреспондент: `CORR_INN`, `CORR_NAME`,
`CORR_ACCOUNT`, `CORR_BANK_BIC`, `CORR_BANK_ACC`, `CORR_BANK_NAME`, `CORR_KPP`) и `CLN_*`
(клиент: `CLN_INN`, `CLN_NAME`, `CLN_ACCOUNT`, `CLN_BANK_BIC`, `CLN_BANK_ACC`, `CLN_BANK_NAME`, `CLN_KPP`).
Налоговый блок: `CHARGE_CREATOR`, `CHARGE_KBK`, `CHARGE_OKATO`, `CHARGE_BASIS`, `CHARGE_PERIOD`,
`CHARGE_NUM_DOC`, `CHARGE_DATE_DOC`, `CHARGE_TYPE`.

🔴 **Поправка к проходу 3.** Проход 3 записал: «в `iBank2` нет поля дебет/кредит — направление
выводится из счетов». Первая половина верна, вторая — **не единственный способ**: в формате есть
**`OPER_ID` — идентификатор операции** (проход 3 его не отметил), а направление надёжнее берётся
из того, чей счёт (`CLN_ACCOUNT`) совпадает со счётом шапки `ACCOUNT`, при этом `CORR_*` — всегда
вторая сторона. Плюс в шапке есть контрольные итоги `CREDIT` / `DEBET`, по которым выписку можно
**сверить на сходимость** — этого рычага у нас до сих пор не было.

**Опознание файла и кодировка.** Тот же репозиторий, `helpers/FormatDetectorIBank.php` +
`models/IBank/V1/IBankV1Parser.php` и `V2/IBankV2Parser.php`:
- iBank **документы** версии 1: первая строка по `^#1\|([a-z0-9]+)(_)?([a-zA-Z]+)?(?:_v(\d+))?$`
  (пример: `#1|payment`).
- iBank **документы** версии 2: первая строка `Content-Type=doc/<тип>`; составные поля —
  `ИМЯ.<индекс>.КОЛОНКА=значение` (регулярка `^(\w+)\.(\d)\.(.+)=(.+)$`).
- 🔴 **Кодировка в обеих версиях жёстко `windows-1251`** (`iconv('windows-1251','UTF-8', …)`),
  никакого UTF-8. Пустое значение = `null`, не пустая строка.
- Выписка (`$OPERS_LIST`) — третий, отдельный диалект, опознаётся по своей первой строке.

То есть у БИФИТ **три разных текстовых диалекта**, а не один: `#1|` (док v1), `Content-Type=doc/`
(док v2), `$OPERS_LIST` (выписка). Проход 3 знал только третий.

### П4.2.2. BSS — живого файла нет, но нашлось, где BSS сидит 🔴

Прямой поиск выгрузки BSS дал пусто: `gh api search/code` по `bssys выписка` — 7 попаданий,
ни одного с файлом; по `"ДБО BS-Client"` — 21 попадание, все это **списки «программа банка»
внутри конфигураций 1С** (`infostart-hub/infostart-erp-community`, `VSydorenko/SMP_BankExchange`,
`RG-Soft/riet-test` и др.), то есть упоминание названия в выпадающем списке, не файл;
по `RESTS DOCUMENTS выписка банк парсер` — **0**.

🔴 **Зато главное:** в том же `cyberft_terminal` лежит аддон **SBBOL** (Сбербанк Бизнес Онлайн),
и схема запроса выписки `app/src/addons/SBBOL/resources/schema/request/account-statement.xsd`
объявлена в пространстве имён **`http://bssys.com/upg/request`** —
`https://github.com/n-gribov/cyberft_terminal/blob/HEAD/app/src/addons/SBBOL/resources/schema/request/account-statement.xsd`.
`bssys.com` — домен компании BSS, `UPG` — её Universal Payment Gateway.
**Вывод: корпоративный канал Сбербанка (СББОЛ) построен на шлюзе BSS.** Это меняет счёт охвата BSS:
проход 3 насчитал 7 подтверждённых банков и не включал Сбербанк.

**Из той же XSD — первичные данные о форматах выписки Сбера для юрлиц.** Атрибут `statementFormat`
ограничен перечислением ровно из трёх значений:

```
<xs:enumeration value="XML"/>
<xs:enumeration value="MT940"/>
<xs:enumeration value="1C"/>
```

Комментарий в схеме дословно: «Формат предоставляемой выписки ('XML' , 'MT940' (англ)). Если тег
не указан, то 'XML'». Плюс атрибут `lastRequestTime` (`xs:dateTime` с часовым поясом) — инкрементальная
догрузка. То есть по СББОЛ **XML — формат по умолчанию**, а MT940 и 1С — по запросу.
Для нас это подтверждает, что пункты 1 (1С), 9 (MT940) и XML-семейство списка парсеров прохода 3
для Сбера обязательны все три.

## П4.7. Правовой рычаг: обязан ли банк отдать выписку МАШИНОЧИТАЕМО

**Вывод словами, коротко.** **Нет. На 17.09.2026 такой обязанности в законе нет** — ни в 353-ФЗ,
ни в Законе о защите прав потребителей. Оба закона говорят про *содержание* информации и про
*доступность формы для человека*, а не про формат файла; способ доставки прямо отдан **договору**,
то есть банку. Но рядом появился рычаг совсем другой природы: ЦБ **19.12.2025 ввёл комплекс
стандартов Открытых API**, в котором выписка физлица описана как REST-ресурс, **дата введения
2026-10-01**. Обязательным он станет только после отдельного федерального закона, который на
момент проверки ещё не принят.

### П4.7.1. 353-ФЗ «О потребительском кредите (займе)», статья 10 — дословно

Источник: Федеральный закон от 21.12.2013 № 353-ФЗ, ст. 10 «Информация, предоставляемая заёмщику
после заключения договора потребительского кредита (займа)», действующая редакция —
`https://www.consultant.ru/document/cons_doc_LAW_155986/3d235479b90308b2e7d05ca02b5429cf015cd1f6/`
(добыто через `r.jina.ai`, HTTP 200, 7 202 байта).

- **ч. 1:** «кредитор обязан направлять **в порядке, установленном договором**, заёмщику следующие
  сведения **или обеспечить доступ к ним**: 1) размер текущей задолженности…; 2) даты и размеры
  произведённых и предстоящих платежей…; 3) иные сведения, указанные в договоре».
- **ч. 2** (кредит с лимитом кредитования, то есть карта): «…в порядке, установленном договором…,
  но **не реже чем один раз в месяц**, если в течение предыдущего месяца у заёмщика изменялась сумма
  задолженности, **бесплатно**… или обеспечить доступ к ним», плюс п. 3 — «доступная сумма
  потребительского кредита (займа) с лимитом кредитования».
- **ч. 3:** «заёмщик вправе получать по запросу **один раз в месяц бесплатно и любое количество раз
  за плату** информацию, указанную в части 1».
- **ч. 4:** о просроченной задолженности — бесплатно, «способом и в срок, которые предусмотрены
  договором…, но **не позднее семи дней** с даты возникновения просроченной задолженности».
- **ч. 5** (введена ФЗ от 07.03.2018 № 53-ФЗ): после каждой операции по ЭСП кредитор-КО обязан
  информировать о текущей задолженности и доступной сумме — **внутри уведомления по ч. 4 ст. 9
  161-ФЗ** «О национальной платёжной системе».

🔴 **Разбор для владельца.** Ключевые слова во всех частях — «в порядке, установленном договором».
Закон задаёт **что сообщить** и **как часто**, и ни разу — **чем**. Формулировка «или обеспечить
доступ к ним» прямо разрешает банку ограничиться показом в личном кабинете. Машиночитаемости нет.
Единственное, что 353-ФЗ нам даёт практически: **право раз в месяц бесплатно получить состав долга
и график платежей** — это опора для пользовательского сценария «принеси нам данные по кредиту»,
но не для автоматической выгрузки.

Редакция: от 28.12.2025, с изм. от 17.02.2026 (Постановление КС РФ № 7-П), с изм. и доп., вступ.
в силу с 01.09.2026 — `https://www.consultant.ru/document/cons_doc_LAW_305/` (через `r.jina.ai`,
HTTP 200). Текст статей взят из официально размещённого полного PDF закона
`https://gblangepas.gosuslugi.ru/netcat_files/8/9/Zakon_RF_ot_07.02.1992_N_2300_1_red._ot_28.12.2025_s_izm..pdf`
(consultant отдал через прокси только оглавление и преамбулу — постраничная навигация закрыта).

- **ст. 8 ч. 2** (в ред. ФЗ от 24.06.2025 № 168-ФЗ): информация «**в наглядной и доступной форме**
  доводится до сведения потребителей при заключении договоров… способами, **принятыми в отдельных
  сферах обслуживания потребителей**, **на русском языке**…».
- **ст. 10 ч. 1:** «обязан своевременно предоставлять потребителю необходимую и достоверную
  информацию о товарах (работах, услугах), обеспечивающую возможность их правильного выбора.
  По отдельным видам товаров (работ, услуг) **перечень и способы доведения информации до потребителя
  устанавливаются Правительством Российской Федерации**».
- **ст. 10 ч. 2** — обязательный состав информации: цена в рублях и условия приобретения, «в том
  числе при оплате… через определённое время после их передачи…, **полную сумму, подлежащую выплате

🔴 **Разбор.** «Наглядная и доступная форма» — норма **про человека**, не про машину: её удовлетворяет
PDF и даже бумага. Единственная зацепка — ст. 10 ч. 1: Правительство **вправе** установить способы
доведения информации по отдельным видам услуг. То есть теоретический путь к обязательному
машиночитаемому формату лежит через **постановление Правительства**, а не через сам закон.
Действующего постановления, обязывающего банк выдать выписку файлом заданного формата, не найдено.

**Практический вывод для FINPILOT.** Ставка на файловые парсеры на горизонте 2026–2027 остаётся
единственной рабочей: обязательного API не будет ни в 2026, ни, судя по переносу, в 2027 для
кого-либо кроме системно значимых банков. Но **внутреннюю модель транзакции имеет смысл уже сейчас
свести к полям ОД-2894** — тогда переход на Открытые API, когда он случится, будет переключением
источника, а не переписыванием ядра.

## П4.8. ГОСТ Р ИСО 20022-1-2013 — 🟢 текст ДОБЫТ, и он про выписку НЕ ГОВОРИТ ВООБЩЕ

**Вывод словами.** Стандарт открыт целиком и прочитан. **В нём нет ни слова про выписку по счёту.**

### Главное одной страницей (для владельца)

1. **Формат Faktura найден — и мы три прохода искали не тот файл.** Выгрузка Faktura.ru — это

3. **Обязанности отдать выписку машиночитаемо в законе НЕТ.** 353-ФЗ и Закон о защите прав
   потребителей говорят «в порядке, установленном договором» и «в наглядной и доступной форме».
   Формат — на усмотрение банка. Единственная теоретическая дверь — постановление Правительства
   по ст. 10 ч. 1 ЗоЗПП, и она сегодня закрыта.
4. **Зато ЦБ 19.12.2025 ввёл стандарты Открытых API, и выписка физлица там описана целиком** —
   `GET /accounts/{accountId}/transactions`, дата введения **01.10.2026**. В модели есть всё, чего
   нет в файлах: `transactionId`, `creditDebitIndicator`, ISO-даты с зоной, комиссия отдельно и
   **MCC торговой точки**. Но обязательным это станет только после отдельного ФЗ, которого ещё нет,
   и сроки уже сдвинуты «позже 2026 года».
5. **ГОСТ Р ИСО 20022-1-2013 к выписке отношения не имеет вообще.** Прочитан целиком:
   «выписка» — 0 вхождений, `camt` — 0. Это стандарт про метамодель и UML. Строку можно вычеркнуть.

### Поправки к проходам 1–3 (собраны в одно место)

1. **Faktura-Excel — это XML Spreadsheet 2003, не `.xlsx`.** Проход 3 предполагал «рубли с запятой»;
   на деле суммы — `ss:Type="Number"` с точкой, локали нет. (П4.1.2)
2. **В `iBank2` ЕСТЬ идентификатор операции — тег `OPER_ID`.** Проход 3 записал «направление
   выводится из счетов» и про `OPER_ID` не знал. Также есть контрольные итоги шапки
   `CREDIT`/`DEBET` — выписку можно сверять на сходимость. (П4.2.1)
3. **У БИФИТ три текстовых диалекта, а не один:** `#1|<тип>` (документы v1),
   `Content-Type=doc/<тип>` (документы v2), `$OPERS_LIST` (выписка). Кодировка во всех —
   жёстко `windows-1251`. Тег `DEBET` пишется именно так, с опечаткой. (П4.2.1)
4. **Список форматов экспорта iBank шире:** добавляются **DBF, ISO 20022, MT103, MT202, Excel**;
   MT940 вендором не назван (назван MT950). **ISO 20022 в РФ уже отдаётся в проде** — опцией iBank. (П4.5-добор)
5. **Сбербанк — клиент BSS** (namespace `bssys.com/upg`), проход 3 его в BSS не считал.
   Форматы выписки СББОЛ: XML / MT940 / 1C, по умолчанию XML. (П4.2.2)
6. **ГОСТ Р ИСО 20022-1-2013 про выписку не говорит вообще.** Проход 3 делал вывод по названию —
   вывод был завышен. Реквизиты: приказ Росстандарта 08.11.2013 № 1407-ст, введён 01.10.2014,
   159 страниц, ТК 122, идентичен ISO 20022-1:2013. (П4.8)
7. **HandyBank:** проход 3 писал «статус неизвестен, сайт 401». Теперь — компания жива, Правила

   «более 50», после — данных нет. InfoWatch купил 80 % в 2018, **к 2025 уже не владелец**. (П4.4-добор)
8. **+1 банк к охвату Faktura: ВБ Банк** (ООО «Вайлдберриз Банк», ИНН 9707021650). (П4.1.3)
9. **Новое, чего в проходах 1–3 не было вовсе:** комплекс стандартов Открытых API ЦБ
