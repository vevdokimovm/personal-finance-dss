- `docs/legal/consent-personal-data.md:32`: отзыв согласия — «через интерфейс Сервиса (удаление учётной записи)». `docs/legal/README.md:51` помечает **L9 «Удаление аккаунта и данных по запросу» как ✅**, обоснование — `crud.delete_user`, то есть функция, а не путь пользователя. `docs/legal/compliance_register.md:75` честно пишет, что L9 в гейт не входит.
- `docs/ROADMAP.md:1209` утверждает, что Jinja-`profile` снесён «с ПОЛНЫМ функциональным паритетом в React», а `:1218` в том же файле признаёт, что React-профиль read-only, «без форм смены пароля/удаления аккаунта».

Тупик того же класса, что инцидент `CONSENT-GATE-NO-UI`, только на этот раз реализованное право — L9. Вторично: скомпрометированный пароль сменить из интерфейса нельзя (только «забыли пароль» через SMTP).

### 2. Гость пишет реальные финансовые данные в ОБЩИЙ на всех посетителей анонимный пул, и продукт активно его туда ведёт
- `app/dependencies.py:103-107` — `get_current_user_id` возвращает `None` гостю; `app/database/crud.py:92-93` — `user_id=None` → фильтр `model.user_id IS NULL`, то есть **один глобальный пул на всех неавторизованных**.
- `app/api/_consent_guard.py:65-66` — гейт согласия для `user is None` пропускает молча (обоснование в докстринге: «демо-данные не относятся к определённому субъекту»).
- Фронт при этом не guard'ит ни один роут: `frontend/src/routes/transactions.tsx:4-6` (и остальные) — просто `component`, без `beforeLoad`. Гость получает 200 на `/transactions` и видит полностью рабочий CRUD.
- Более того, продукт **ведёт** его туда: `frontend/src/pages/dashboard/ui/DashboardEmpty.tsx:33-36` — primary-CTA «Внести операции →» показывается и гостю (`isGuest` влияет только на песочницу ниже), а `frontend/src/pages/transactions/TransactionsPage.tsx:93` в пустом состоянии подсовывает импорт выписки. `app/api/routes_banks.py:89` — `upload_statement` берёт `get_current_user_id`, то есть **реальная банковская выписка** гостя уезжает в тот же общий пул.

**Сценарий A (утечка):** посетитель Б открывает сайт и видит операции/цели/кредиты, которые внёс посетитель А десять минут назад. **Сценарий B (порча):** гость А загрузил демо-портрет (`/demo/load` вызывает `_clear_all`) и стёр данные гостя Б. **Сценарий C (мимо песочницы):** новый гость вообще не увидит вход в демо, потому что `DashboardPage.tsx:72` (`income===0 && expense===0`) даст «не пусто» из-за чужих данных, и `DemoSandbox` не отрисуется — при том что README рекламирует «Демо за 30 секунд», а v8.46.0 закрыт как «песочница вернулась».

### 5. «Семейный доступ» ничего не делает общим: сущность нельзя положить в семейный котёл ни из одного экрана
- Схемы принимают `household_id`: `app/schemas/transaction.py:17`, `obligation.py:23`, `goal.py:30`, `budget.py:10`, `liquid_asset.py:15`.
- Грep `household_id` по `frontend/src` (без `generated/`) даёт **только** `entities/households/api/useHouseholds.ts` — в path-параметрах управления самой семьёй. Ни одна форма (`TransactionForm`, `GoalForm`, `ObligationForm`, `AssetForm`, `BudgetForm`) поля не имеет.
- Хуже: `app/api/routes_transactions.py` вообще не упоминает `household` — `payload.household_id` игнорируется даже на уровне API. Проверку роли `can_write_household` вызывает **только** `app/api/routes_goals.py:42`.
- А UI обещает обратное: `frontend/src/pages/households/HouseholdsPage.tsx:99` «Общий план для нескольких человек», `:156` «…всей семьи», `:318` «{кто} перестанет видеть общий план», `:365` «Участник — вносит данные».

**Сценарий:** пользователь создаёт семью, шлёт супруге ссылку, та регистрируется и принимает приглашение — и не видит ни одной операции, цели или кредита. Обе стороны решат, что приглашение не сработало. Плюс отложенный риск: роль `viewer` нигде, кроме целей, не проверяется на запись — как только UI для шаринга появится, «наблюдатель» сможет править общие данные.

## Средняя правдоподобность

### 7. Истечение сессии выглядит как «проверьте соединение», и выйти из этого состояния штатно нельзя
- `app/config.py:83` — `JWT_TTL_HOURS = 168`, refresh-токена в проекте нет. То есть 401 в середине работы — регулярное, а не экзотическое событие.
- 401 разбирает **только** профиль: `frontend/src/entities/profile/api/useProfile.ts:32` (`NotAuthenticatedError`). Все остальные экраны — `TransactionsPage.tsx:65-75`, `GoalsPage`, `ObligationsPage`, `AssetsPage`, `PlanningPage`, `DashboardErrorState` — показывают «Проверьте соединение и попробуйте ещё раз» с кнопкой «Повторить», которая будет возвращать 401 бесконечно.
- Одновременно `frontend/src/widgets/app-nav/AppNav.tsx:30` (`if (!data || error) return null`) **убирает навигацию целиком** — экран визуально «ломается» без объяснения.
- В формах 401 приходит баннером «Требуется аутентификация.» (`extractErrorMessage` возвращает `detail` как есть) — без ссылки на вход и без сохранения введённого.

**Сценарий:** через неделю после входа пользователь заполняет форму кредита, жмёт «Сохранить», получает непонятный баннер, шапка теряет меню — и единственная подсказка «Войти» прячется в топбаре.

### 8. Подтверждение email: бейдж-проблема без действия, ссылка из ответа выброшена
- `frontend/src/pages/profile/ProfilePage.tsx:104-105` рисует бейдж «не подтверждён», но кнопки повтора нет — `POST /api/auth/resend-verification` (`app/api/routes_auth.py:355`) фронтом не вызывается нигде.
- `app/api/routes_auth.py:157-161` в self-hosted режиме (`email_enabled=False`) отдаёт `verification_url` прямо в ответе, а `RegisterPage.tsx:42` вместо этого показывает «Проверьте почту, чтобы подтвердить email». `docs/DEPLOY.md:278-279` описывает режим «без SMTP подтверждение идёт по ссылке в ответе» — фронт этот режим не поддерживает.

**Сценарий:** первый деплой без рабочего SMTP (а `docs/deploy_owner_checklist.md` прямо предупреждает, что SMTP может не быть к вечеру деплоя) — все новые аккаунты навсегда «не подтверждён», и починить это из интерфейса нельзя.

### 9. MFA: включить нельзя, а войти с включённым — тоже
- `frontend/src/pages/auth/LoginPage.tsx:19-30` — при `mfa_required` показывается только уведомление; поля кода нет. Комментарий обосновывает это тем, что «в UI пока нет способа включить MFA вообще, ветка практически недостижима».
- Но способы включить MFA существуют вне SPA: `app/api/routes_auth.py:430-508` (`/mfa/enroll`, `/mfa/confirm`) открыты обычному пользователю, а раньше был Jinja-профиль (снесён v8.23.0).

**Сценарий:** аккаунт, у которого MFA когда-либо включали (тест, ранняя версия, прямой вызов API), после снятия Jinja заперт: вход невозможен, выключить MFA нельзя — `/mfa/disable` требует уже аутентифицированной сессии.

открыты любому пользователю, а войти с включённым вторым фактором было нельзя — аккаунт
запирался **навсегда**: `/mfa/disable` требует уже аутентифицированной сессии, то есть
выключить фактор может только тот, кто вошёл. Восстановление оставалось правкой базы руками.
Перед публичным запуском это блокер, и оценка «средняя» его недооценила.

**Что это говорит о самой процедуре.** Из одиннадцати гипотез подтвердились восемь,
включая две из трёх «средних». Разделение на категории правдоподобности предсказывает
не важность, а лишь уверенность агента — и гипотеза 9 показала, что низкая уверенность
не означает низкой цены. Оставлять «средние» непроверенными нельзя.
