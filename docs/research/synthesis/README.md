## Зачем отдельный слой

В `docs/research/` три слоя, и они разные по назначению:

| Слой | Что лежит | Правило |
|---|---|---|
| `raw/` | первичный материал **дословно**: отчёты агентов, цитаты источников с реквизитами | пишется ДО выжимки (правило §9 CLAUDE.md), не редактируется задним числом |
| `competitors/` | выжимки по конкретным продуктам и рынку | одна тема — один файл |
| `synthesis/` | **сквозные выводы по всем темам сразу** и порождённые ими решения | пишется ПОСЛЕ закрытия очереди |

Разрыв, который закрывает третий слой: сырьё копится (36 файлов), выводы расползаются
по пунктам ROADMAP и записям CHANGELOG, а вопрос «что вся эта работа означает для продукта
в целом» не задан нигде. Решения из-за этого принимаются по последней прочитанной теме,
а не по совокупности.

## 🔴 Обязательный вход в синтез, добавлено 16.09.2026

**Качество нашего кода на числах выглядит лучше, чем оно есть.** Пилот мутационного
тестирования ядра (`docs/reports/mutation_pilot_2026-09-16.md`) дал балл **68,7 %** при гейте
покрытия ≥90 %: треть намеренных порч ядра тесты не заметили, включая исчезновение порядка
погашения долгов по ставке. Владелец 16.09.2026, дословно: «это очень плохо что столько ошибок
но хорошо что нашли… в синтезе в роадмапе учти такие вещи. что код далеко не такой безошибочный
как кажется на числах у нас».

Что из этого следует для синтеза:
1. Любое утверждение вида «проверено тестами» в итоговых документах требует указания, ЧЕМ
   проверено: покрытие — не доказательство проверки поведения.
2. План работ после синтеза обязан содержать укрепление тестов ядра, а не только новые фичи.
3. Тот же скепсис применить к остальным нашим числам: гейты, аудиты, оценки готовности —
   батчи Г33, Г34, Г35 как раз сверяют наши методики с внешними нормами.
4. 🔴 **Главное следствие, которое синтез обязан превратить в план:** вид проверки выбирается
   под вид кода, а у нас почти везде один вид — обычный тест с эталонным значением. Ядро
   модели требует инвариантов и метаморфических отношений; парсер чужого формата — эталонных
   файлов и фаззинга; слой данных — дифференциального прогона на паре SQLite/PostgreSQL;
   HTTP-контур — контрактных тестов; интерфейс — браузерных. Владелец 16.09.2026: «это надо
   исправлять, именно поэтому я и начал этот разговор — чтобы качественно повысить наш
   продукт во всех сферах». Раскладка по модулям — в `docs/ROADMAP.md`.

## 🔴 Вход в синтез, добавлено 17.09.2026 (Г31.4): замкнутая петля в валидации модели

**Найдено:** подушка 3–6 месяцев, нижняя граница 2 месяца, веса SAW, горизонты 12/36 и кромка
ПСК 300 % взяты из экспертного консенсуса — то есть из **дескриптивного факта** («так считают
эксперты») — и работают как **норматив**. Само по себе это законно. Проблема в другом:
**метрика сертификации модели — тоже согласие с экспертами.** Проверка по построению не способна
поймать ошибку, общую для всех четырёх экспертных движков.

Канон это частично знает: полоса L∈[1;2) уже переопределена как «зона отсутствия консенсуса»
(амплитуда 66 п. п.). Но методологический вывод не сделан.

**Что синтез обязан сделать:**
1. Разделить пороги на три класса: **нормативные извне** (ПДН 0,40 — норма ЦБ), **выведенные
   из данных** (требуют указания выборки и года) и **экспертные** (требуют внешней проверки
   другим методом, а не согласием тех же экспертов).
2. Для третьего класса назвать внешний критерий проверки. Кандидаты уже добыты: набор EMH
   (поток > 3 % расходов, постоянные расходы ≤ 65 %, неипотечный долг < 15 % дохода,
   резерв ≥ 200 % расходов), ступени MaPS, американские эталоны резерва 2–6 месяцев.
3. 🟢 Чистыми от петли остаются: **ПДН 0,40, Rt ≥ 0, Avalanche** — у них основание вне
   экспертного консенсуса.
