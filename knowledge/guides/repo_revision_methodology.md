# Методология ревизии репозитория (docs ↔ code up-to-date)

> **Зачем.** Проект большой и ведётся на нескольких аккаунтах — доки дрейфуют от кода:
> протухают ссылки после реоргов, счётчики (таблицы/пути) отстают от схемы, в тексте
> оседают legacy-параметры мат-модели, календарные константы в тестах взрываются со
> временем. Ревизия — регулярная сверка «доки соответствуют коду», часть которой **гоняется
> как тест перед релизом** (`tests/test_repo_revision.py`, инструмент `tools/revision/`).
>
> Первый полный проход — v5.11.0 (`docs/reports/audits/repo_revision_2026_07.md`); дельта —
> v5.22.1 (`…/repo_revision_2026_07_delta.md`). Эта методичка формализует процесс, чтобы
> следующие проходы шли по чек-листу, а не с нуля.

## Принцип: живое vs замороженное

Ключевое различие всей ревизии. **Живой** источник (ROADMAP, WATCHLOG, справочники, гайды,
ADR, README) обязан быть актуальным — его чиним. **Замороженный** (CHANGELOG аппенд-онли,
отчёты `reports/{incidents,investigations,merges,releases,audits,testing}`, `roadmap_archive/`,
научный `science/replication_package`) — точка-во-времени: его ссылки были верны на своей
версии, **править = переписывать историю** (запрещено, правило §5 #15 WATCHLOG). Инструмент
классифицирует источник по `FROZEN_HINTS` и замороженные не роняет.

## Шесть осей ревизии

| Ось | Что проверяет | Автоматизировано? |
|---|---|---|
| 1. Ссылки | Битые ссылки на файлы репо в живых доках | **Да** — `LinkChecker` |
| 2. Актуальность | Счётчики структуры (таблицы/миграции/пути API) + legacy мат-модели в тексте | **Да** — `CountChecker` + `LegacyModelChecker` |
| 3. Календарь | Календарные мины (дата против относительного окна от `utcnow`) | **Да, отдельно** — `tools/timewarp` (нужен pytest) |
| 4. Диаграммы | Не разошёлся ли mermaid-источник `diagrams.md` с кодом | Нет — ручная сверка (PNG-превью — внешний блок, Mac) |
| 5. Нейминг | Файлы против `docs/naming_convention.md` | Нет — ручная сверка |
| 6. Суть/дедуп | Дубли и протухшие куски в `knowledge/` (вредят RAG вдвойне) | Нет — ручная сверка |

Оси 1–3 закрыты инструментом (быстро, детерминированно, гоняются как гейт). Оси 4–6 —
ручной проход раз в веху или при крупном реорге.

## Инструмент `tools/revision/revision_check.py`

Три статические проверки, все возвращают CLEAN/DRIFT и общий exit-код:

1. **`LinkChecker`** — regex-скан всех `.md`, извлечение ссылок на файлы репо
   (`docs|knowledge|tools|app|tests|…/*.ext`), проверка существования. Живые битые → FAIL;
   замороженные → пропуск; известно-приемлемые → `LINK_ALLOWLIST` (пара «файл→ссылка» + причина).
2. **`LegacyModelChecker`** — скан живых доков на паттерны v2.x (`21 альтернатив`, `шаг 20%`,
   `flow-based`, `L_min=0.30`, `CI 95%`). **Контекстно-осознан:** строки с маркерами перехода/
   негации (`устар`, `→`, `v2`, `не использ`, `прежн`…) пропускаются — упоминание legacy как
   истории/«не использовать» легитимно. Файлы-объяснения перехода — в `LEGACY_ALLOWLIST_FILES`.
3. **`CountChecker`** — считает таблицы (`__tablename__`), миграции (`alembic/versions/*.py`),
   пути OpenAPI (`docs/api/openapi.json`), сверяет с пинами `EXPECTED_COUNTS`. Рассинхрон → FAIL
   (форсирует синк доков при изменении схемы/API).

Запуск: `python -m tools.revision.revision_check` (exit 0 = CLEAN, 1 = DRIFT). Как тест —
`pytest tests/test_repo_revision.py` (в fast-тире и CI).

### Когда правишь инструмент, а не доки

- **Схема/API выросли легитимно** (новая таблица/миграция/эндпоинт) → обнови `EXPECTED_COUNTS`
  И соответствующие доки/диаграммы. Падение пина — это сигнал «синкни доки», не баг.
- **Новая известно-приемлемая битая ссылка** (плановый форвард-ассет, снапшот внешнего источника)
  → добавь в `LINK_ALLOWLIST` с причиной. Не добавляй, если ссылку можно просто починить.
- **Новый файл-объяснение перехода v2→v3** → в `LEGACY_ALLOWLIST_FILES` (редко; обычно хватает
  контекстных маркеров).

## Ось 3 отдельно: timewarp (календарные мины)

Динамическая, нужен pytest → не в статическом инструменте. Детектор `tools/timewarp/warp.py`
сдвигает `utcnow` на `WARP_DAYS` (единая точка времени, ADR-002). Гонять по **оконному домену**
(тесты с датой против относительного окна: транзакции/аналитика/spending/expense/obligation/
temporal/import), НЕ по auth/JWT/MFA (их `iat`/`exp` на реальных часах → ложные падения):

```sh
env SECRET_KEY=test PYTHONPATH=tools/timewarp WARP_DAYS=370 \
  ./.venv/bin/python -m pytest <файлы оконного домена> -p warp -m fast -p no:warnings -q \
  --junitxml=/tmp/warp.xml
```

Прогон на `baseline / +90 / +180 / +370` — 0 падений = мин нет. Класс мины: `test_expense_record_date`
(BUG-028 — дата против 6-мес окна, взорвалась без коммита). Правило дат — `docs/QA.md`.

## Когда запускать

- **Гейт (оси 1–3, автомат):** каждый прогон fast-тестов + перед релизом в прод. Красный =
  дрейф, чинить до релиза.
- **Полный проход (оси 1–6):** раз в веху, после крупного реорга файлов/переименований, перед
  заморозкой канона (напр. мат-модели перед вехой тестирования). Оформляется отчётом в
  `docs/reports/audits/` (реестр — `reporting_policy.md`).

## Флаги, которые инструмент НЕ чинит сам

Дрейф источника — когда протухли **реальные project-инструкции** (их снапшоты в
`knowledge/project_meta/`), а не репо: правка нужна в настройках проекта Claude, не в снапшоте.
Инструмент такие держит в `LINK_ALLOWLIST` и выносит в отчёт как флаг владельцу.
